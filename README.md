# Love, College & Agent

> 一个面向大学生活的个人 Agent。她能够处理实际事务，拥有持续的记忆和自己的日常；你们在工作、安静共处和彼此参与中，逐渐形成一段独有的关系。

这是为学校首届黑客松准备的新项目。名字借用了《爱，死亡和机器人》的命名形式，目前使用工作名 **Love, College & Agent**。

本文保存产品讨论的共识，作为后续讨论、取舍和开发的起点。日期：2026-09-30；2026-10-11 按主办方破冰会发布的规则更新赛事约束，并记录当日技术讨论的结论。

## 为什么用户会打开它

**工作能力提供启动理由，共同经历和逐渐形成的关系提供长期使用的理由。**

用户可以请她整理校园信息、处理资料、协助学习，并在实际工具能力范围内推进其他工作。她会记住有来源的共同经历，也可以在用户希望安静时做自己的事情，在合适的休息时刻分享作品、近况或邀请用户提供一点帮助。

番茄钟是相处的节奏，2026-10-11 用户确定不砍。用户输入计划，她排成番茄：专注时她安静陪伴，同时在后台干活、做自己的事；休息时她交付成果、开口交流。计时由确定性代码负责，她通过工具使用番茄钟（见 [技术方案](docs/tech-design.md) §3.5）。项目的核心仍是有实际执行能力的 Agent，以及围绕这个 Agent 建立的连续生活体验，不缩减成番茄钟应用。

## 已经确定的产品方向

### 1. 她能够实际帮忙

以用户魔改的 AIRI 为主要设计参考，保留聊天、工具执行、harness、记忆和长期任务等有用思想，精简复杂的 Live2D 控制和不必要的插件。

默认校园能力以扩展后的 Student Hub 为参考。工作可以持续多个步骤：理解请求、读取资料、调用工具、观察结果、调整行动、必要时向用户求助，并清楚说明结果和未完成部分。

运行平台已确定，首个任务需贯通校园信息和实际资料处理；具体来源、输入资料和首发工具仍待选定。不能把参考项目已有的工具清单直接当作本项目范围。

### 2. 打破“你说一句，她说一句”

她可以依据实际事件、已接受的目标和自己的活动主动行动或交流，不要求每一步都由用户发送新消息触发。

主动性包括开始一次获准的工作、继续先前的事情、私下记下想法，以及决定暂时不说话。消息数量不是主动性的衡量标准。

### 3. 工作、陪伴和交流属于同一个角色

| 相处情境 | 预期行为 |
| --- | --- |
| 用户请她帮忙 | 推进任务，呈现必要的进展和结果，遇到真正缺失的信息时求助。 |
| 用户希望安静陪伴 | 降低打扰，在允许的时间和资源范围内进行自己的活动。 |
| 用户休息或主动交流 | 聊共同经历、分享她的近况，或邀请用户参与小事。 |

三种情境共享身份、记忆和活动状态。“安静”与“暂停所有后台活动”需要能分别表达；切换情境也不应丢掉正在做的事情。

首版用番茄钟的阶段串起三种情境：专注段对应安静陪伴，休息段对应交流；界面上用门牌切换情境，用“熄灯”表示全部暂停（[体验设计](docs/experience-design.md) §2）。

### 4. 她有自己的生活

用户提出用“世界泡”来描述一个持续存在的角色生活空间。这个概念来自用户参与舒月 official 内测的体验转述；本文不推断该产品内部实现。

可能的活动包括学习、写小说、整理笔记、喝茶和休息。她可以提前规划一天，跨上下文记住进展，并在后续对话中延续这些事情。

世界泡需要保存环境、当前活动、目标、进展和产物。学习笔记、小说草稿等可以是真实文件；喝茶、望向窗外等可以是场景中的叙事活动。内部数据应能区分实际执行、虚构世界事件、提议和计划。

2026-10-11 用户同意：首版世界泡只在番茄钟的专注段推进，用户不在时不推进；她每天列一份自己的当日安排，每个专注段推进一项，预算按段计（[技术方案](docs/tech-design.md) §3.4、§3.5）。用户对她计划的影响程度仍需设计。

### 5. 大家应该有自己的聪音

角色与场景创作是项目的重要方向：用户上传一张主体和背景清晰的图片，系统协助拆分、补全和生成人物表情／动作差分、背景变化及必要事件。

表现参考视觉小说的立绘差分、有限动作与场景演出，包括用户提到的《Blue Archive》剧情呈现方式。生成素材应能预览、调整、统一打包和导入导出。

Image 2.5 等图像生成工具是候选能力来源，尚未选定供应商或验证成功率。单图拆分包含对被遮挡内容的补画；输入图像限制、一致性、图层定位、光照和遮挡关系需要实际实验。

角色包、场景包与个人存档在概念上分开：角色可以分享，每位用户的聊天记忆、共同经历和校园数据不默认随角色分享。

首版（2026-10-11）：做角色包导入，缺素材时逐项回退；“上传一张图自动生成差分”不做，路演中作为路线图讲（[体验设计](docs/experience-design.md) §8）。桃子的人设改编自用户赛前为 AIRI fork 写的原创角色卡 ReLU（主题词“克制”）。原卡含私人信息，不进仓库，赛前已提交指纹；改编在赛中做，提交时注明来源（[美术规格](docs/art-spec.md) §5）。

### 6. 可以带走和恢复共同经历

项目数据导出、人物形象与素材备份、记忆和聊天会话备份／恢复，已进入明确的产品规划。私人存档与用于公开分享的角色／场景包分别设计；格式、首版范围和恢复验证方式见 [技术方案](docs/tech-design.md) §5，实现与验证在赛中完成。

视频中将用“书页散落后，凭她送出的羽毛笔重新找到她”表达这一方向。这个意象不代表当前已有恢复实现，也不承诺恢复未曾保存的数据。

上下文超出窗口后的压缩本身会丢失信息。若要让恢复取回被压缩的内容，原始聊天与记忆需要在压缩之外独立保存，备份不能只包含压缩后的摘要。视频中“静风”一层即表达这种逐渐流失（见创意脚本 §5）。

已设计（2026-10-11）：对话与执行事件写入 append-only 日志，压缩只改变投影，不删除原始事件；私人存档包含日志（[技术方案](docs/tech-design.md) §3.2、§4.1）。

### 7. 工具可以被扩展与改造

用户希望借鉴其所称 deepseek-harness 的“一切皆插件”原则，使工作插件与工具可由用户或 Agent 在相应权限与约束内修改、组合。视频用“书写者画出零件，桃子接住并自行组装新电脑”表现这一构想；接口、修改权限和验收方式仍待设计。

首版（2026-10-11）：harness 只是一个薄循环，能力全部以内置工具、MCP server 和 Markdown skills 接入；由她自己编写代码插件不做（[技术方案](docs/tech-design.md) §3.1、§7）。

用户明确不将 AIRI 的 Minecraft 复合插件搬入本次参赛项目，以避免大幅拼装已有工程。可以让她学习玩双人网球作为候选自主活动。视频中类似 Minecraft 的延展沙滩指空间表现，不表示接入 Minecraft。2026-10-11 用户提出另一条路：展位上经 MCP 接入用户魔改的 mcpfabric（MIT 开源 mod），让同学和她各开一个客户端一起玩。这是标准的 MCP server，只靠配置接入，不搬代码；有余力才做，只用在展位上（[技术方案](docs/tech-design.md) §3.8）。

### 8. 她送的礼物：把共同经历做成实物

2026-10-11 用户确定：她会把你们一起经历过的事做成小小的 3D 物件送给你。礼物由 Agent 通过 MCP 工具调用影眸 Rodin 生成，每件礼物绑定它所来自的那段经历记忆。

- 羽毛笔是第一件礼物，对应视频第 13 镜的赠笔，也是私人存档在应用里的实体：导出时出现，恢复时颜色从笔尖晕开。
- 之后的礼物在运行时生成，摆上礼物架。点开一件，可以看到它来自哪段经历。
- 礼物进私人存档，恢复后，架子上的礼物随之回来。
- 礼物是关系反馈的主要形式，让用户看到自己的参与留下了什么。是否另设好感度数值仍未决定。

设计与首版范围见 [技术方案](docs/tech-design.md) §3.7、§7。3D 桃子（类 VRChat 路线）不做。

## 记忆、记事本与日记

记忆用于保持身份、事实和经历的连续性，不能仅依赖当前聊天窗口。

| 内容 | 用途 |
| --- | --- |
| 事实与经历记忆 | 保存用户明确表达的信息、共同经历及有来源的工作结果，支持检索和纠正。 |
| 任务与世界状态 | 保存正在做什么、做到哪一步、等待什么；不能只靠自然语言记忆推断。 |
| 记事本与灵感 | 保存计划、问题、创作素材和待发展的想法。 |
| 日记 | 将已有经历整理成角色口吻的可读回顾，允许主观表达，但不凭空制造已发生事实。 |

用户可以查看她的日记，也可以在休息时接受她的邀请，帮忙整理记事本、评价草稿或提供建议。这些参与应该有后续结果，例如草稿修改、笔记整理完成，或建议影响了之后的安排。

日记是面向用户的叙事产物，不是模型内部推理记录。日记中的感想也不能未经区分地重新写成客观事实。

首版记忆设计改编自用户 AIRI fork 的记忆设计（继承原作者 Neko 的 DevLog），保留抽取、重排、晋升和取代关系，去掉情绪相关的部分，见 [技术方案](docs/tech-design.md) §4.2。用户说明（2026-10-11）：这部分设计不是赛中现做，但属于原创，提交时如实注明来源。

## 关系与正向激励：仍在探索

希望借鉴 galgame 的正向反馈，让用户感到自己的参与留下了变化。尚未决定是否采用显式好感度，以及是否需要关系阶段、解锁或数值。

2026-10-11 起，礼物（见上文“她送的礼物”）是已确定的反馈形式。好感度、阶段和解锁仍待讨论。

已讨论的候选包括：

- 共同经历影响关系，她更愿意分享作品和计划。
- 用户的建议影响她之后的日常、学习和创作。
- 世界泡中的场景、物品或活动出现持续变化。
- 用好感度表达她接受建议、调整生活安排的倾向。

“信任增加后更愿意商量”是讨论中的建议，不是已经定稿的好感度规则。作为助手的基本工作质量，不应依赖用户先刷关系。

## 两条相互连接的体验过程

**现实工作：** 用户提出需要 → 她实际帮忙 → 留下结果和共同经历 → 更了解用户 → 下次协作更顺畅。

**她的生活：** 她制定计划 → 产生作品或变化 → 适时分享 → 用户选择参与 → 后续生活留下用户的影响。

校园事务提供持续变化的现实内容；个人生活提供交流的另一端；记忆将它们连接起来。

## 展示叙事与视频构思

实际演示拟以“和她的一日假期”为主题，用真实日程串联校园信息、资料处理、安静共处和她自己的活动；具体任务与数据仍待选定。

视频完整构思已形成三部分：**创造与相识 → 共处、探索与赠予 → 失去、寻找与重逢**。采用书写者全程第一人称和手绘风格，以书代表记忆，以线稿到完整上色表现时间与培养。演示角色暂称“桃子”，不改变用户可以自定义角色的产品方向，也不表示照搬参考角色的外观。

前半段以她整理校园邮件、向右页推来日程纸体现工作能力；中段表现形象编辑、工具改造与自己的生活；结尾用羽毛笔和日记串起备份恢复与更深的信任。整体乐观，失去服务于重逢；本项目是个人 Agent 产品，不是悲剧游戏。

详见 [完整视频创意脚本](docs/pv-creative-script.md)。该文档保存完整创意母版，尚未锁定镜头时长、旁白、配乐或最终三个图标。最初约两分钟的视频设想与五分钟路演的具体取舍仍待决定；路演剪辑版另行安排，不先删掉母版的叙事。按主办方答复，画面全部在赛中制作。用户决定（2026-10-11）在赛中冲刺完整母版，分档制作，先保路演剪辑版。

## 从参考走向独立 Demo

本项目是新的参赛工程。按用户提供的规则，可以合理参考开源项目并注明来源，但不能拿已有项目组装。两个参考项目用于理解有价值的机制、接口和失败经验，不能将整体拼装、换皮或直接迁移作为参赛实现路径。

采用独立实现的方向，按新产品需要重新确定模块和接口。具体代码引用仍需符合来源许可和赛事规则；新实现、外部依赖和素材来源需要能说明。若后续获得官方细则，以明确细则修正记录，不将当前转述扩张成对任意复用的许可。

48 小时内优先证明一条完整的工作过程和一段有连续性的相处过程。大量 AI 辅助不能免除集成、调试、素材检查和现场演示所需时间。

## 后续讨论与验证方式

下一步在已确定的平台和贯通任务方向内，选定实际来源与资料，以及一个与工作相接的安静陪伴／休息交流场景，再确定最小实现。角色素材生成可先做单独的小实验，验证同一角色的差分切换是否稳定。

供后续讨论的一条演示草案：从校园通知识别一项任务 → 读取相关资料 → 产出可检查的整理文件或学习安排 → 记录工作结果与共同经历 → 进入安静陪伴 → 休息时分享她自己的笔记或创作进展。这是待细化的场景草案，不表示已选定具体平台、课程、资料或全部步骤。

上述顺序是当前建议，不是已排定的开发批次。暂不以完整复刻 AIRI、所有校园平台接入或成熟游戏的素材规模作为首版目标。

后续记录需分清产品设想、代码实现、自动化测试和真实使用证据。跨上下文、重启恢复、跨天推进也应分别验证；加速时钟或预先准备的场景可以用于 Demo，但不证明真实跨天运行已经通过。
