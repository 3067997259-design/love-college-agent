## 响应等待的证据与限制

第 79 次请求在约 362 ms 收到 HTTP 200，但未记录完整向量校验成功。原探针的 `elapsedMs` 在收到响应头时先写一次、整个向量完成时再覆盖，因此这次的 362 ms 不能视为完整请求耗时。最后一次额度预留与报告最终落盘相隔约 3,075 ms。

生产查询通过 `embedWithInteractionBudget` 给可选向量工作 3,000 ms；底层 HTTP 向量请求另有 30,000 ms 上限。查询先超时后，较晚返回的向量不会进入这次查询。原探针只检查临时的 `embeddingError` 再抛出通用错误，没有保存其分类，因此原始实测的确切错误已无法从报告恢复。不能将本例定性为数据库故障、供应商空响应或已证实的网络故障。

使用失败运行的合成数据库副本、生产引擎和 ManualClock 做了零网络对照：响应头均在 362 ms 到达，完整向量分别在 2,500 ms 和 3,500 ms 到达。前者完成查询；后者在 3,000 ms 返回等待超时，较晚向量被丢弃，数据库仍为 ready。原数据库、状态与操作日志的前后 SHA-256 一致。这个对照支持等待上限解释，但不能替代原实测缺失的错误证据。

本次仅修改测试探针：响应头耗时、完整向量成功时间和请求结束耗时分别记录；未结束的字段保留 null。查询退出前保存数据库可用性和固定错误码，区分等待超时、向量运行失败与数据库不可用；未知供应商错误不写原文。新增辅助文件纳入预检及授权的来源哈希。产品代码、3 秒上限、评分规则和候选包均未修改。
