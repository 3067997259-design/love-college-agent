## 上轮为何失败

本轮后对第一次尾段保存的 DSH session 做只读结构审计，按现有审计工具的方法逐帧解压 zstd，没有读取连接凭据，也没有输出请求上下文、推理或工具参数。找到明确记录：

1. 上轮上游流有两个 SSE 帧和 `[DONE]`，网关未见 `finish_reason`，记录的 usage 为输入 0、输出 0。旧网关把终止标记当作成功依据。
2. DSH 记录 `TRANSPORT: Stream ended without finish_reason`，并在约 495 毫秒后启动第一次内部重试。
3. 新 HTTP 尝试没有对应的新应用准入回执，旧票据已消费，测试网关以 `APPLICATION_ADMISSION_AMBIGUOUS` 拒绝该请求，没有再次访问 provider。
4. DSH 最后记录 `AUTH: 403 status code (no body)`，产品因此显示 configuration-failed。这个 403 来自本地网关，不是 provider 的密钥失效回应。

因此目前能确认的是“**流缺少结束原因 → DSH 内部重试 → 缺少新准入而被本地拒绝**”。最初看到的末端 403 掩盖了前面的流格式错误。之前依据空流合成复现提出的“空响应”不能当成原始载荷的确定描述；本次 DSH 记录把错误进一步定位到了缺少 `finish_reason`。

原始上游响应正文没有保存，仍不能确定它为什么缺少该字段，也不能把服务排队、模型故障、转发故障或某种特定响应内容写成已证实根因。同一候选、存档和已保存连接在本轮通过，与偶发上游异常相容，但不能仅据此证明服务商内部原因。
