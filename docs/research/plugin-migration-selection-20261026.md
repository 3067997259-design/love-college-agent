| 顺序 | 最小完整能力与评审 | 推荐路线 | 相比从头开发 | 当前决策 |

## 3. 公平的成本口径

下面是**规划估算，未通过实现计时验证**。假设一名熟悉 LCA 的开发者、Windows 单平台、已有开发环境，范围严格等于各评审的第一阶段；包含源码裁剪、LCA 接线和本地合成正反测试。真实服务授权 / 账号准备、法务或作者沟通、正式安装升级矩阵及长期维护不在工期内，分别列为外部条件。1 人日是工作量单位，不是日历承诺。

| 能力 | 推荐路线拆分：复用处理 + LCA 接入 + 本地验证 | 同范围原生实现 | 持续成本 / 不确定性 |
| --- | --- | --- | --- |
| 两源学术检索 | 0.5–1.5 + 1.5–2.5 + 1–2 = **3–6 人日** | **4–7 人日**，同样要处理请求、归一化与来源 | 少量接口变化；估算重叠，不能声称已证实省一半 |
| collection 级 Zotero 只读 | 0.5–1.5 + 2–3 + 1.5–2.5 = **4–7 人日** | **4–8 人日**，同样包含库绑定与来源授权 | Zotero 实例 / API 版本、分页和私有摘要；共享宿主改造可能占主要成本 |
| Agent Browser 任务内文本与截图（后续补评） | 2–3 + 5–8 + 2–3 = **9–14 人日** | 使用 Playwright **11–17 人日**；直接写 CDP **16–25 人日** | 主比较为成熟库自建，预期中位省约 2–3 人日且区间重叠；来源、图像、授权公共工作都不能省略 |
| BrowserSkill 单页文本观察 | 1–2 + 3–5 + 2–3 = **6–10 人日** | **15–25 人日**，仅估同范围本地 extension / IPC / 生命周期后端，不是复刻全部 BrowserSkill | CLI / 扩展 / 浏览器三者版本配合；若用户只需公开网页，直接 web_fetch 的成本会更低 |
| 指定桌面窗口观察 | 独立实现预计 **4–7 人日**；从 Coopanion 抽取并替换宿主预计 **6–10 人日**，另有未决许可工作 | 同左，优先比较原生 Windows 窗口捕获路线 | 遮挡、缩放、多屏、窗口身份和图像投影；目前未证明任何后端达到目标窗口隔离 |

Coopanion 全量输入控制不与“只看窗口”的 4–7 人日比较：它还增加系统输入、前台焦点、用户抢占、部分执行、权限对象与风险动作分类。源码信息不足以给出可信的完整控制总价，需在窄观察验证后另估。

公共接入工作不能重复算成四份：来源退役、有限软件对象授权、图像投影等若先形成接口，后续只计增量。但也不能为了未来复用，先建一个泛化平台再称其成本为零。各记录列出实际需要的最小接口。

已定位一个实际宿主缺口：[execution.ts](../../src/main/dsh/execution.ts) 的 `sourceOf(templateId)` 当前只识别邮件、资料、Student Hub、MCP 等前缀，普通新插件工具并不自动得到第三方来源；bridge 收到显式 null 也不能视为已经正确分类。学术检索第一阶段必须补并验证这条接线，不能只做新 manifest。这里是源码观察，未通过真实插件运行复现；成本已纳入 LCA 接入项。

## 4. 当前规格经过这轮评审后是否合适

v0.1 的能力拆分、职责归属、迁入路线、证据和许可分离有效：它让检索包落到组件复用，让浏览器后端落到外围适配，也阻止把 Coopanion 的截图接口误认为已经是 LCA 的窗口授权接口。仍有六处需要补充；本轮先在实例中试用，不静默改变 v0.1 判据。

| 暴露的问题 | 本轮证据 | 建议补充的固定字段 |
| --- | --- | --- |
| “有价值”缺少频率和替代方案 | 没有 Zotero 库时，Zotero 排第二没有意义；公开网页读取也未必需要 BrowserSkill | 用户任务频率、是否已有目标软件、当前替代、改变优先级的条件 |
| 太容易把单机权限等同于项目权限 | Zotero collection、浏览器 tab、Windows 窗口都不是项目路径 | 外部对象身份、允许操作、所属用户 / 项目、观察版本、授权失效条件；新授权对象同时记录 F3 子范围，不能只标新增 UI 的 F2 |
| “取消”过于笼统 | CLI 结束不等于 daemon 动作撤回；输入可能已经打了半段 | 请求停止、资源清理、动作核对分别记录；是否可幂等重试由具体动作判断 |
| 读操作仍有两个授权环节 | 本地 Zotero 查询无远端流量，结果交模型则可能外发；截图还会包含其他应用内容 | 获取数据权限与发送给模型权限分开，并画出完整传输链 |
| 工时比较易偷换范围 | 全功能浏览器后端不能与一个 fetch 工具比；全桌面控制不能与窗口截图比 | 同一验收场景的三方案比较、共享成本、外部等待、估算区间与置信度 |
| 阶段门槛容易把所有研究都标成阻塞 | 尚未指定维护人不妨碍决定下一个验证对象；未安装也不妨碍源码判断 | 区分研究结项、可进入实现、可发布；维护认领与发布义务保留，不把“先验证”理解为没有结论 |

另需澄清：业务调度和授权有效期走 LCA Clock / Scheduler；驱动的 I/O deadline、按键之间的技术等待不是第二套业务调度。浏览器命令队列、OS 驱动子进程也不等于另一个 agent 循环。应检查谁在决定工作与调用模型，避免机械地拒绝所有 timer、子进程或事件循环。

## 5. 建议的第一个有界验证

选择学术检索的 **Crossref + arXiv，search + get，两源最多合计 8 条结果**。先从来源归一化和请求映射抽取最小代码，替换请求边界；不带五源全开、下载 PDF、引文网络、自动综述或新 UI。

首轮成功条件：同一查询返回可核实标识符和来源；一个源失败不会伪装成无结果；预先取消不发请求，中途取消不启动重试；外部摘要下一轮及重启后退役；用户未授权的私有查询不会发出。先用本地合成源完成这些反例，再在后续明确授权下做两源各少量公开查询。若只保留了 DOI 查询且抽取维护成本与自写相当，就切换 M4，不为保留“来自 DSH 市场”的标签维护 fork。

这项验证既能交付一个有用的小能力，也能检验“原始插件 → 差异清单 → LCA 来源工具 → 运行证据”的流程。BrowserSkill 与 Coopanion 的外部对象授权继续作为下一层设计输入，本轮不建设这些接口、不安装后端。
