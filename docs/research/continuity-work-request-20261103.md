## 改动与边界

- 主进程从本 root 当前回合已送达的用户原文确定请求。多个工作之间需要原文中的 workId、明确声明的唯一任务名称或完整标签；不按最近活动猜测，也不把旧任务中的输出值当成名称。单个未结束工作仍可承接隐含指代，泛化的“改一下”需要补充具体内容。
- 拒绝结果明确返回 `applied:false` 和澄清要求。同一请求不能在尝试修改后改用新建绕过；相同原文重复开工返回已有工作，已用于补充的原文不能另建任务，重开后仍按持久决定去重。
- 新建 objective 来自当前用户原文与有效澄清，验收条目只保留用户逐字要求；模型的任务改写和其他工作的 decisionIds 不再充当新授权。历史决定仍可用于解释原工作。
- 同回合已提交的非审批回答可以补齐请求；原请求和回答原子进入同一目标版本，保留各自事件 ID。撤回、未提交问题、旧回合回答和权限批准均不能补足授权。
- 多问题回答的模型题目标题保留在可读对话日志里，但不进入工作决定或成功输入采集。前台与 Worker 使用同一回答内容和事件 ID，防止题目建议变成用户要求或重复经历。
- 离线模型现在故意重放 `query → 猜测 update → 额外 create`，并在用户撤回后再次调用修改，验证主进程实际拒绝。含糊场景比较整个工作集合、版本、代次及状态，并检查是否真正提出澄清；另外走通正常的多问题澄清。

对应原计划阶段 3 的工作路由、阶段 4 的决定交接与经历去重，以及阶段 5／6 的恢复和验收。没有扩展世界泡，也没有改变日记规则。名称和路由词检查是保守规则，不是通用自然语言语义证明；无法绑定的名称需要澄清。真实模型是否自然地澄清、准确说明拒绝结果，仍需单独验证。
