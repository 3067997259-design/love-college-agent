# P5：普通委派与团队如何进入 LCA

2026-10-23。状态：**源码核对后的设计建议，尚未实现或完成运行验收**。承接 [1.2 计划](v1.2-development-plan-20261023.md)、[P0 / P1 探针](v1.2-p0-p1-20261023.md)与 [P2 安全边界](v1.2-p2-20261023.md)。本次只修改文档，没有修改随附 DSH、依赖锁文件、生产代码或美术素材。

用户补充：在 DSH 使用普通子代理与 Team 时，模型缺少选择依据；Team 有稳定身份和共享任务板，但 8 个席位用完后无法回收换人。LCA 应改善这两种能力的配合，并避免因修改上游包增加打包维护成本。此前确认的能力保留、左页全房间方向及美术共同调整要求继续有效。

## 固定版本的事实

核对对象为本仓库随附的 `@deepseek-ai/dsh@0.2.1-rc.2`，不是对上游最新版本的判断。

| 问题 | 本地随附代码的行为 | 对 LCA 的含义 |
| --- | --- | --- |
| Team 最多 8 人？ | `dsh-experimental-agent-team-profile/cordis.patch.yml` 配置 `maxMembers: 8`；服务自身默认 16，配置没有写死 8 的上界。计数来自队员名册，不包含 lead。 | 调整数值不需要 fork，但加大数值不能解决名册累积；本设计不主动提高限额。 |
| 停止后释放席位？ | `TeamRoster.spawnAdmitted` 按持久 `state.members.length` 检查容量，并拒绝曾用名字；先记 provisioning，再创建。创建失败会记 failed，仍占名册项。interrupt 只停止当前运行，不删名册、不清待收消息。 | “停止”“从当前画面收起”“卸载运行实例”“删除名册身份”是不同操作。不能显示虚假的释放席位或把旧名字重新指向新人。 |
| 队员能继续用？ | Team 的 `sendMessage` 可以继续已有队员的工作；普通子代理的 continuable provider 也支持继续消息和冷恢复。具体能力取决于 provider。 | 区分“同一个人继续接任务”和“回收身份创建另一个人”。只有前者是现成能力；普通子代理也并非只能执行一次。 |
| 普通子代理不受 8 限制？ | `dsh-subagent` 的 `maxActiveSubagents` 默认 8。Team 也通过 `subagents.startActivation` 创建，共享根树的容量池。运行、驻留空闲、创建中和清理中不能简单等同于完成释放。 | 名册容量与运行容量必须分别反馈；不能承诺 8 个 Team 队员之外再无限开临时助手。 |
| Team 按什么生命周期存在？ | `TeamId` 取 lead 的根 Session ID，名册和任务事件保存在这个根的日志中。LCA 当前按日期、项目选择或恢复 DSH 根会话。 | 不能把每条新用户任务当作新 Team，也不能为了清席位偷偷换根会话、复制全部上下文或抹掉旧记录。 |
| 能否把两套工具直接叠加？ | 上游 Team profile 禁用普通委派及三个重名控制工具，还装配自己的 UI。Team 工具会在成员作用域注册 `send_message/list_agents/interrupt_agent`。 | 不套整个上游 profile。P0 已验证服务可共存；完整身份路由仍需 P5 探针证明。 |
| 普通助手能直接认领 Team 任务？ | `tryMembership` 排除名册外的 provider 子代理。共享任务操作依据真实 Team membership。普通消息权限以父子邻接关系为边界。 | UI 统一不等于权限统一；普通助手不能伪装为队员、直接领取 Team 任务或任意给兄弟发消息。 |

本地依据位于 `dsh/runtime/node_modules/@deepseek-ai/` 下的：

- `dsh-experimental-agent-team/lib/index.js`：Config、默认值、Team 服务出口；`lib/types/roster.js`：membership、spawn、interrupt、failed 名册记录。
- `dsh-experimental-tool-agent-team/lib/index.js`：teamPolicy、成员作用域、工具说明；当前说明主要解释工具用法，没有普通委派与 Team 的共同选择规则。
- `dsh-subagent/lib/index.js`：容量池、`drainChildren` 与服务配置；包内 README 说明驻留与续跑边界。
- `dsh-tool-subagent/lib/index.js`、`dsh-tool-subagent-control/lib/index.js`：独立委派、fork、邻接消息和中断。
- `dsh-tools/lib/index.js`：公开工具注册和按 Agent 作用域的机制。
- LCA 的 [execution](../../src/main/dsh/execution.ts)、[family](../../dsh/lca-bridge/family.js)、[运行时准备脚本](../../scripts/prepare-dsh-runtime.mjs)。上游固定源码参考沿用 [主计划](v1.2-development-plan-20261023.md#固定版本源码参考)。

## 建议的产品语义

书里统一显示正在帮忙的小桃子、任务、活动、等待原因和产物；详情保留“临时委派 / 团队成员”及实际可用控制。主角色负责向用户交付和协调，不把 DSH 的两种运行方式做成必须由用户先选的产品开关。

模型仍保留两种明确的创建入口，不新增一个隐含猜测后端的万能 `auto` 路由。选择依据是**协作方式**，不是任务看起来大不大、预计要多久或是否包含代码：

| 情况 | 优先方式 | 例子 |
| --- | --- | --- |
| 输入、交付和责任边界清楚，收回结果即可；不需要同伴认领任务或互相发消息 | 普通 `subagent`；确实需要已经完成的对话上下文时才考虑 fork | 查一份文档、审一个模块、独立比较两种方案 |
| 多个人需要共同任务板、稳定责任、依赖排序或反复相互协作 | Team；先检查已有成员，续用合适身份，再按需创建 | 接口、实现、验证互相交接，需要共享领取和版本控制 |
| 有 Team，同时出现一块独立的查询或审查 | root 创建普通助手；结果交给 lead 或负责队员，由真实队员维护共享任务 | 团队开发中临时查 API 行为；助手不是共享任务的 owner |
| 工作不可独立拆分，或容量、预算不足 | 主角色继续处理或等待必要成员 | 不为每个小步骤新建成员，不默认越多越快 |

初版不预设永久的“前端 / 后端 / 测试”角色，不强行凑人数，不自动把普通成员升级为 Team 身份。普通助手默认由 root 创建，暂不顺带扩大现有委派深度。需要组队时使用少量明确责任的成员，完成一个任务后可继续分配合适的新任务；新任务不自动继承旧批准或已退役的原文授权。

## 引导要进入实际模型请求

采用短而稳定的选择规则，并在创建说明与运行反馈中重复必要约束：

1. 先判断是否需要共享任务协作；仅需独立产物时选普通委派，已有合适成员时先续用。
2. 创建前读取真实成员与容量。返回 Team 名册已用 / 上限、运行容量及无法确定的部分，不能从 running 数量推算剩余容量。
3. Team 任务遵循读取、按当前 revision 领取、执行、核对产物、更新状态；依赖 ready 不自动唤醒队员，写入范围提示不等于文件锁。
4. `inactive` 不代表成功。消息已接收不代表处理完；中断已接受不代表已经停止。等待前必须有能继续产生进展的成员，完成交付前核对必要产物。
5. 名册满时明确返回原因和可行动选项：续用已有适合队员，或把可独立工作显式委派给普通助手。需要 Team 身份的任务不能悄悄降级成普通委派。

规则通过 LCA 的 system-prompt 接口和工具说明接入，不只写进人读的 README。不靠每回合隐藏 / 删除能力节省提示成本，也不依赖模型自己记住席位数字。提示只能改善选择，身份、容量、预算、审批和 revision 冲突仍由代码执行。

合成模型可证明规则和反馈进入请求、路由正确，不能证明真实模型已学会选型。实际模型选型质量需另行获授权，用有 / 无共享协作需求的代表任务观察。

## 包外适配的实现边界

首选只修改 LCA 自有 `dsh/lca-bridge`、主进程和共享接口：

- 保持随附 DSH npm 版本、锁文件和包内代码不变，使用已有 Team service、subagents service、任务板和持久事件。
- 装配 Team service，保留普通 spawn / fork；不直接装配整个 Team profile。首选由 LCA 提供薄的模型工具适配：复用服务方法实现 Team 创建、任务操作和等待；三个冲突的控制名只保留一个 LCA 路由实现，保留两类成员原有能力。
- 控制目标用 LCA 生成的明确地址，列表返回 mode、真实关系与可用操作；名字仅用于显示，不以名字猜系统。发送 / 停止先核对 root、project、runtime、调用者关系和当前 activation，再调用对应服务。
- root 的总览不等于每个普通助手都拥有全部消息或操作权限。Team 同伴通信走 Team service；普通父子通信走 subagents service；renderer 继续通过现有受限命令，不直接拿 Cordis 服务或任意 RPC。
- 装配顺序、工具输出结构和提示上下文是适配层要承担的维护面。需要验证同名工具只出现一次、冷恢复重新装配正确、provider 能力没有被谎报；不能称“无需 fork”等于“无需回归”。

目前包里已有 Team 服务。首选路线预计无需增加一套上游构建、补丁应用或本地发布步骤；这是基于当前依赖和服务出口的判断，仍要用打包后的产物验证。若必须依赖私有字段、修改 node_modules 或重写执行循环才能成立，应报告具体阻塞并重新比较方案，不悄悄引入 fork。

## 席位、连续性与来源

初版承认 Team 名册不可回收：停止和收起不增加名册容量，不提供无效的“踢人换新”按钮。提高 maxMembers、清空记录、轮换根会话都不是本次默认解法。运行实例的卸载与冷恢复属于另一个问题，只有证明 pending inbox、迟到回执、审批取消和预算归属正确后，才考虑用公开服务释放运行容量。

P2 当前在新的 root followup 时使旧成员工作授权失效，并取消旧等待 / 重试；root 单纯结束则不取消仍工作的成员。P5 不把成员身份持久化解释成权限永远有效。初版保留这条保守边界，明确显示需要续派的状态，经新的明确指令继续；真正跨 root 新回合无缝持续工作，必须独立定义工作授权，不能为了复用队员直接放宽 P2。

共享任务板是新增的持久内容路径：任务标题、描述、成员职责及后续编辑可能来自第三方材料。仅把 `team_task_get/list` 的返回值标为 member 来源不够——旧内容可能下一轮被重新读出。适配层需记录字段 / revision 的来源与授权，或采用更保守的整条记录退役；读出时投影，不能改个状态或 revision 就洗成新来源。原日志保留，过期原文不重新进入模型。UI 的安全标签也不展示私有原文。

## P5 的具体推进顺序

1. **P5a 包外共存探针。** 隔离 profile 装入服务和薄适配；证明普通委派、Team、单一控制路由、现有成员续用、两个容量限制及满额反馈。注入创建失败，证明失败名额没有被 UI 当作释放；停止、空闲与实际释放分别核对。
2. **P5b 契约与来源。** 按现有“接口：”独立提交规则补齐容量、状态和控制结果；补任务板持久来源、恢复、迟到消息、跨项目拒绝和 root 新回合的明确续派边界。先通过 P2 回归。
3. **P5c 模型引导与功能页面。** 让模型收到选择规则、当前可用控制和容量反馈；接成员 / 任务安全视图、单成员停止、整组停止、消息、任务 revision 冲突反馈。基础交互先使用既有书本样式；全房间资产仍等用户在场调整。
4. **P5d 隔离验收与打包核对。** 覆盖普通助手与 Team 同时工作、名册满但旧队员可继续、共享容量耗尽、失败占位、消息权限、写范围冲突提示、主角色闲置时的预算 / 审批、断连和冷恢复。复跑相关 P2 / P3 / P4 场景；核对随附运行时、裁剪和许可。真实模型选型、实际安装与升级分别记录，不用合成通过代替。

备选方案不作为本次默认范围：完全用普通子代理另写 LCA 的任务板，会让 LCA 接管更多协作语义；修改上游名册回收机制，则必须设计身份世代、旧任务 owner、迟到消息和恢复迁移，还会增加依赖发布与打包成本。先验证现成服务加薄适配，只有证据说明不足时再比较这些代价。
