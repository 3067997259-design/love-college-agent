## 2. 核对官方来源后的两个边界

**token 节省发生在哪一层。** 当前设计是文字 → 图片 → DeepSeek-OCR → 还原文字 → 主模型。64–400 是 OCR 端的名义视觉 token 预算，不能直接用来宣称主模型上下文压缩了同样倍数。还原文字进入主模型后仍按它的 tokenizer 计数；完整链路要额外计算 OCR 生成、传输、主模型输入与延迟。如果只送摘要或查到的片段，节省也要与普通文字摘要／片段回读比较。此判断来自数据流，不是已测出的性能结果。

**中文识别与中文光学记忆是不同验收。** 论文含中文 OCR 的评估，但 10×／20× 压缩曲线主要来自 Fox 的英文页，原文约 600–1300 个 OCR tokenizer token；不能直接作为中文聊天记录的指标。总体 CER 很低，也可能把“不允许”变成“允许”、把日期或旧新版本关系写错，必须另看关键事实与更正顺序。

来源：[原论文 §4.1、表2与表3](https://arxiv.org/html/2510.18234v1)、[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-OCR)。

## 4. 第一轮怎么测

| 档位 | base_size／image_size | crop_mode | 名义视觉 token |
| --- | --- | --- | --- |
| Tiny | 512／512 | false | 64 |
| Small | 640／640 | false | 100 |
| Base | 1024／1024 | false | 256 |
| Large | 1280／1280 | false | 400 |

同一张源图分别过四档；不先手工缩四张不同图，不开 Gundam 的动态裁块。脚本另记录实际 image placeholder positions，避免把行分隔等位置与名义编码预算混为一谈。

样本包括虚构对话、事实更正、中英标识符、密集观察记录、否定／未完成语句、低冗余字符串。两种版式帮助观察拉伸与 padding 的差异；这是 12 页的初筛，不能证明覆盖所有中文材料。

执行顺序：

1. 查 GPU、驱动、CUDA、Python、空闲显存、CPU 内存、磁盘和下载连通性。
2. 固定模型 revision，先跑 dialogue-square 的 Base 单页，保留加载时间与输出。
3. 单页成功后跑 12 页 × 4 档，共 48 次；每条结果立即落盘，错误不改成成功。
4. 对候选档位的对话、密集页和低冗余页各重复 3 次；冷启动、首推与稳态计时分开。
5. 检查原文、解码、错误字符、日期／编号／否定／更正关系；literal anchor 命中只算字面保留，不算语义正确。

记录字段：原文与解码 token（OCR tokenizer）、名义预算、实际图片位置数、原始与空白规范化 CER、关键片段保留、输出是否触及生成上限、每页时间、CUDA allocated／reserved 峰值。触及上限的诊断须同时检查模型上下文总长，不能把截断归因于光学压缩。本轮 8192-token 复测超出默认总长，单列为失败诊断，不进入常规质量与速度指标。

判定先看是否有值得继续的档位：高分辨率能稳定还原，低分辨率的损失可辨、不会稳定改写关键事实；再谈产品接入。阈值等第一轮错误分布出来再定，不用论文的英文数字替中文测试预先写 PASS。
