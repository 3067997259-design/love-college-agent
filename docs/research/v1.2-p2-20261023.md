# 1.2 P2：成员审批与持久来源追踪

2026-10-23。接续 [开发计划](v1.2-development-plan-20261023.md)及 [P0 / P1 反例](v1.2-p0-p1-20261023.md)。本切片修复 S1 / S2，尚未推进 P3 扩展管理、P5 成员控制或全房间 UI。

## 实现与授权边界

- **S1：每个成员的审批。** 创建、恢复、模型步骤和工具执行前，都按主进程授予的项目信任重新应用 `workspace-write + ask` 或 `lca-trusted + ask`；覆盖 DSH 委派时设置的 `never`，并替换不再适用的自动拒绝提示。ACL 错误由实际执行成员的来源状态决定安全反馈，不向模型返回修复 ACL 的原始错误。
- 审批携带 `approvalId / activationId / policyRevision`，主进程再加入 `AbortSignal`。成员审批不借用主角色的回合寿命；普通成员提问仍走主角色。书里的审批卡只算可见时间，超时、拒绝、取消和断连都不执行。相同项目并发信任请求串行重读规则，已有一份明确授权时不重复提问；不同项目不会共享规则。
- 撤销信任同时删除该项目的常驻批准，取消家族运行等待与待审批，恢复项目沙箱。主进程及 bridge 双方都核对策略代次；撤销前的“同意”即使迟到，也不能用于新活动。主角色正常结束不取消成员；新的根回合授权、停止、项目切换、熄灯和退出会使旧活动失效。对已经发出的外部动作，不声称取消已经撤回其效果。
- **S2：可重放的来源。** `lca-sources-v2` 按会话日志计数，记录每项内容的授权、来源、轮次和表面位置。来源工具、LCA 工具和委派结果都会传播来源；同轮派生的助手输出、工具参数及结果一并追踪。摘要继承被替换输入的来源与最早轮次，fork 重放已完成前缀，不能把子成员的轮次数字与主角色比较。
- `plugin:lca/tool-source` 保存调用时的来源类别，无原文；停用插件不会使历史结果变干净。旧记录缺少声明时，LCA 工具结果按插件来源处理。这里使用固定 DSH 已提供的插件记录接口，没有修改上游仓库或 `node_modules`。
- `dsh-home/lca-source-mailbox.json` 仅保存发送者、正文 SHA-256、根会话、项目、授权和来源类别。转述、完结消息必须匹配投递证据；旧授权、跨项目、缺失记录、相同正文对应多个授权均退役。冷恢复产生新授权，旧投递不自动获得新权限。损坏的索引令打开会话失败，并返回固定错误，不能挂起等待启动或继续发模型请求。
- 退役采用 DSH 表面替换。保留用户自己的开场文字；来源派生的助手消息及其配对结果转为退役通知，避免保留工具参数中的原文。DSH 不允许直接替换带来源流的助手消息，也不允许在工具结果替换中改动其非内容字段；实现遵守这两个约束。原始事件和执行证据没有删除。
- 主进程也封住回填：跨项目 `earlierToday` 仅自动接续经过新来源策略核实且未降级的助手回复。旧策略无法核实或来源受限的回复不进入新的自动记忆抽取；用户原话和书里的原始记录保留。`work/turn.sourcePolicy = 2` 是这条边界的日志版本标记。
- `plugin_manager` 的模型写操作暂时拒绝，等 P3 接入主进程的扩展操作授权；项目 full-access 不等于安装或关闭安全组件的授权。工具没有被移除。代码插件仍是获准的宿主代码，不声称能隔离恶意插件。

## 未外推的结论与后续

本次关闭的是固定运行时、生产 bridge 和主进程边界上的两个已复现缺口。没有真实模型、邮箱、校园或付费生成调用；没有 Electron 窗口、安装包、实际升级、存档 UI 恢复、跨日长期体验或真实超长上下文验收。真实 Windows ACL 失败分支本次使用确定性错误注入覆盖；临时目录里的真实 OS 沙箱运行成功不能算该失败分支的系统验收。

消息证据缺失或相同正文跨授权复用时采用保守退役，可能需要主角色重新发出内容明确的新任务；无法证明干净时不会自动放宽。当前任何新的根回合（含自动事件）都会结束旧成员活动，再由新指令激活；这保证不会以新回合续用旧授权，但持续团队的跨根回合调度仍需 P5 细化，不能把它描述为已完成的长期自治体验。此前已经保存的用户记录与记忆没有被追溯删除或改写。P3 仍需解决扩展声明持久化、受保护组件和操作审批；P5 再接成员生命周期、控制项及团队工具分派。子智能体 UI 继续遵循左页、较远镜头呈现全房间的已确认方向。
