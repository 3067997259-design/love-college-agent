## 1. 审计

### 1.1 让人困惑的入口

从新上手的人看，下面这些入口要么找不到，要么看不出做了什么。它们指向同一组结构问题（§1.2）。

| 入口 | 实际行为 | 指向的问题 |
| --- | --- | --- |
| 设置 → 专注与作息 → 她的生活与书桌 →「进入心流」 | 普通模式下唯一的工作入口（[设置分组](../../src/renderer/src/tools/UserSettings.tsx#L71)）。 | 工作是一个要"进入"的房间，不是从对话里开始的事。 |
| 门牌「工作中」 | 不开心流，不动番茄；和"安静"的区别只是她的主动消息不压到休息（[门牌](../../src/renderer/src/book/LeftPage.tsx#L185)、[安静判定](../../src/main/harness/loop.ts#L61)、[生活判定](../../src/main/life/service.ts#L17)）。 | "我们在干嘛"有四个开关：门牌、番茄阶段、心流、日程页的"你今天要工作"。 |
| 「批准计划并允许书桌写入」 | 把当前心流从只读切成可写，没有被批准的具体计划对象（[按钮](../../src/renderer/src/book/flow/FlowPanel.tsx#L36)）。 | 权限是全局模式，不是对一件具体事情的授权。 |
| 「收起工作过程」和 `/compact` | 只改模型看到的上下文，界面不变；`/compact` 在心流内外是两个命令（[分派](../../src/main/bridge/controller.ts#L422)）。 | 两套上下文要用户手动整理。 |
| 聊天里的 `/goal` | 新建跨天工作目标；普通聊天的上下文不含目标，界面只在心流面板里显示（[目标注入](../../src/main/heart-flow/service.ts#L41)）。 | "要做什么"散在四处：工作目标、番茄计划条目、每回合步骤、确认过的截止日期。 |
| 「状态 / 权限 / 差异」 | 打开原生窗口，显示一段 JSON（[查阅](../../src/main/index.ts#L442)）。 | 工作状态在主界面里读不出来。 |
| 「退出心流」 | 普通上下文和对话流都排除心流区间（[上下文](../../src/main/heart-flow/context.ts#L11)、[界面](../../src/main/bridge/controller.ts#L296)），只回传约 2,000 字证据 JSON（[摘要](../../src/main/heart-flow/summary.ts#L7)）。 | 回到聊天，她像不记得刚才一起做了什么。 |

### 1.2 结构：缺一个跨回合的"任务"

- 回合是执行单位，每次开始都清空步骤（[投影](../../src/main/journal/projection.ts#L89)）。目标只是用户标签，番茄计划只排时间，确认过的截止日期只在日程页。
- 唯一能跨回合存在的是心流这个全局模式。主进程里 `heartFlow.active()` / `occupied()` 出现 20 次，其中 18 次在 `src/main/index.ts`；回忆、日记、语音、备份、模型设置、她的生活和工具列表都用它做开关。renderer 至少还有 9 处按 `activeId` 分支。
- 数据层已经是同一份当日日志，分裂只在投影层：普通上下文过滤（[装配](../../src/main/index.ts#L391)）、界面消息过滤（[快照](../../src/main/bridge/controller.ts#L296)）、工作上下文另行组装（[工作准备](../../src/main/heart-flow/service.ts#L113)）。合并主要是去掉一层投影分裂，不需要迁移日志。
- "书桌"同时是用户工作的文件根（[书桌根](../../src/main/index.ts#L429)）和她自己读写作品的材料区（[同一书桌](../../src/main/index.ts#L469)）。
- 单回合默认最多 12 次模型步骤（[步骤上限](../../src/main/harness/loop.ts#L109)），对持续工作偏短。

### 1.3 心流与聊天的分隔也是一道安全墙

- 新安装默认"跟随主模型"。此时邮件提取本身已经是一次不带工具的独立请求（[读取端口](../../src/main/model/task-ports.ts#L56)，返回工具调用即判失败）；之后原文另被附进聊天那一轮，最近 4 封、每封最多 24,000 字（[附加](../../src/main/campus/service.ts#L230)）。心流期间不附（[判定](../../src/main/index.ts#L546)）。
- 守住的部分：邮件和附件原文与书桌写入、命令执行不在同一次请求里。
- 不归它管或已有缝隙的部分：
  - 心流里网页读取的结果和书桌文件本身就是不可信内容，现在靠逐个网址、逐条命令的批准约束；
  - 进入心流会带上最近 12 条聊天、每条前 500 字（[引用](../../src/main/heart-flow/service.ts#L179)），她对邮件的转述可以随之越墙；
  - 聊天里外部 MCP 能做什么，取决于用户接入了什么。
- 结论：现在兜底的是逐条批准，分隔是给邮件和附件额外加的一层。合并时必须用不依赖"两套上下文"的方式保留它（§2.4）。

### 1.4 邮件入口

- 两条入口汇入同一条提取流程：核心直连 IMAP（[IMAP 来源](../../src/main/mail/imap.ts#L56)、[凭据读取](../../src/main/index.ts#L377)），以及校园助手插件交来的 Student Hub 材料（[接收](../../src/main/campus/service.ts#L227)）。插件的"导入已有事项"交来的是 Student Hub 已提取好的结构化事项。
- 旧包 `plugin-packages/student-hub` 与 `student-hub-candidates` 已由一体插件取代，仅为兼容保留（[插件说明](../plugins.md)）。
- 规模：约 24 个源文件和 9 个 Electron 场景脚本引用邮箱、假邮箱或 IMAP 路径。
- 未核对：Student Hub 能否提供邮件附件。现在附件经 IMAP 进入资料整理。

### 1.5 成本观测缺口

- 流式解析已解析并记录缓存命中字段（M1，2026-10-19）：DeepSeek 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 与 OpenAI 兼容的 `prompt_tokens_details.cached_tokens` 归一为 `cachedInputTokens` / `uncachedInputTokens` 写入 `model/attempt`（[解析](../../src/main/model/stream.ts#L11)、[类型](../../src/main/model/types.ts#L11)、[日志 schema](../../src/main/journal/schema.ts#L146)）。
- 真实验收（2026-10-19，授权 `LCA_REAL_MODEL=1`）：DeepSeek 官方真实 SSE 同时回报命中 / 未命中与 `cached_tokens`，记录值、`model/attempt` 与重启后的 journal 逐字段一致；相同合成前缀第二次调用命中 1,280、未命中 244，第一次显式 0 也被记录。换过分区的文本 GPT 端点单独回报 `prompt_tokens_details.cached_tokens`（命中 4,224 / 未命中 1,445），OpenAI 兼容分支也已完成真实验证；中转 Gemini / Claude 的 usage 不带缓存字段时记录保持缺失而不是 0。
- 计量注意：中转号池反代会注入并复用隐藏前缀（本次 GPT 端点对短请求即出现约 4 千 token）；D0 / R1 记录成本时把供应商侧前缀与 LCA 自身上下文分开即可。这是已知中转行为，不作为本项目开销判断。
- 切换心流会换掉工具列表（[工具选择](../../src/main/index.ts#L543)），进入或恢复心流会新建一段前缀；世界事实和召回插在最后一条用户消息之前。
- 因此现在既不能证明新设计更省，也不能证明现设计更费。M1 已补记录并完成真实验收；成本测量（D0、R1）仍需真实模型授权与预算。

### 1.6 她自己的生活与工作

- 她读书、照着材料写东西（生活作品）只在空闲时开始：主循环不忙、心流未开、不在休息、人在房间等十余项条件全部满足（[可用判定](../../src/main/index.ts#L470)）。被挡住时暂停并标为"先让给你的事"，条件恢复后接着做（[让位原因](../../src/main/life/work/service.ts#L27)、[续做](../../src/main/life/work/service.ts#L94)）。
- 礼物在专注开始时动工，不看她是否在忙；做好后等休息再交给用户（[动工](../../src/main/gifts/service.ts#L47)、[交付](../../src/main/gifts/service.ts#L46)）。
- 她此刻在做什么没有统一的决定者：各模块互相检查对方是否在忙，生活作品的可用判定就要问十个模块。左页姿势也是由各处状态拼出来的，例如开着心流就坐到书桌电脑前（[姿势](../../src/main/bridge/controller.ts#L296)）。
- 心流平时藏在设置里，所以"工作挤掉生活"现在很少发生；工作一旦成为日常，这个冲突就会每天出现。

## 2. 设计（建议，待 demo 验证）

### 2.1 名词

- **时间线**：沿用一天一页。聊天、任务推进、番茄与校园事件、她的生活都按发生顺序追加在同一份日志和同一个投影里。
- **任务**：跨回合、可跨天的对象，持有关联目标、工作区、带版本的计划、授权、执行证据、交班记录和状态。任务有两种主人：用户交给她的事，需要用户授权，作用于用户的工作区；她自己的事，即读书、写作和做礼物，只作用于她自己的区域，不需要授权。两种用同一个模型，在同一条时间线上。用户的任务从对话里提出。
- **注意力**：她同一时刻只把一件事拿在手上，由一个地方按让位顺序决定拿哪件（§2.5）。左页画面显示的就是这件事。
- **节拍**：番茄钟仍是用户的节奏。专注时她在旁边安静地做手上的事：用户交给她的任务优先，任务在等待时做她自己的；休息时交班和聊天。不开番茄也能工作，检查点改为任务结束或用户喊停。
- **交班**：专注结束、任务结束或日切时形成的一份记录，说的是她这一段做的全部事情，不只是用户的任务。它同时用作：休息时她说给用户听的内容；模型上下文的检查点；用户决定的来源（引用用户原话）；第二天接着做的起点；日记素材。

### 2.2 一天的样子

1. 早上用户说今天要写完作业二。她把确认过的截止日期挂成目标，排三个番茄。
2. 第一个专注：她读项目、提出计划，用户批准一次。她改文件、跑测试；测试在跑、或者在等用户批准时，她翻开自己那本书，任务一要她，就夹上书签回来。用户中途吐槽一句，她简短回应、记下，然后继续。工作进展写进任务卡，闲聊留到休息。
3. 休息：她交班，说清改了什么、测试结果、一个待用户决定的问题，也说自己那本书读到哪了；答应过的礼物做好了就拿出来。随后聊午饭。
4. 下午说"接着上午那个"：任务从交班处继续，也知道午饭时说过的话。
5. 晚上的日记和日摘要从交班取材，不碰工具原始输出。

### 2.3 上下文四段

| 段 | 内容 | 何时变化 |
| --- | --- | --- |
| A | 系统规则、角色卡、用户档案、全天固定的工具列表 | 设置或角色变化 |
| B | 最近一次检查点：日内对话摘要、手上任务的交班、前几日摘要 | 交班或日切 |
| C | 检查点之后的时间线：用户与她的消息、工具调用与结果、追加的事件 | 只追加 |
| D | 每次请求现算的状态：番茄阶段、手上任务与授权、是否降级、世界状态、本轮召回、本轮获准附加的原文 | 每次请求 |

原则：发生过的事件追加进 C，当前状态只放进 D；D 放在请求末尾，内容保持粗粒度。压缩只在交班时做，旧的第三方工具结果在检查点后替换为回执。D 的具体位置以供应商接受的消息顺序和实测命中为准。

### 2.4 安全规则

1. **隔离的是请求，不是模型。** 邮件、附件、网页和插件交来的原始材料默认只进入一次不带工具的读取请求，产出经校验的结构化结果，主时间线只收结果。"跟随主模型"改为"读取请求也用主模型"，原文默认不再附进主对话。
2. **原文进了哪一轮，哪一轮降级。** 用户明确要求查看原文时，原文才作为本轮附加内容进入主对话。第三方工具结果（网页读取、MCP、来源类插件）留在 C 中期间同样视为降级，直到下一次检查点替换为回执。降级期间，写文件、执行命令、外发、付费生成一律逐次批准，卡片写明来源；不能新建或扩大授权。
3. **授权只来自用户批准的计划。** 授权绑定任务和计划版本，写明范围（目录、写入、命令），在任务结束或重启时失效，不重放。

用户自己项目中的文件不按第 2 条处理，否则无法编程；其风险由授权范围、默认无网络、逐次写入记录与撤回约束。项目里的恶意文件仍可能在授权范围内影响模型，这是已知的残余风险。

工作区工具的输出在记忆中按来源工具处理，不进入个人记忆。现在的[来源工具判定](../../src/main/campus/context.ts#L4)不含书桌工具，合并时需要补上。

### 2.5 她自己的生活：同一份日程，不按时段切分

她的生活不是和工作分时段轮流的另一个板块。如果规定"有任务的专注归工作、没任务的专注归她"，只是把模式切换换成了时段切换，她仍然在两种身份之间来回跳。这里的做法是：用户的任务和她自己的事放在同一份日程里，由注意力和让位顺序安排。

1. **让位顺序**：用户正在和她说话 > 用户任务里正在进行的一步 > 答应用户的礼物 > 她自己的读书、写作和外出。被让位的事夹上书签，之后从书签继续，沿用现有的"先让给你的事"暂停与续做。
2. **任务在等，就是她的时间**：等用户批准、等用户回答、等命令或测试跑完，或计划本来就排在下一个专注时，用户的任务不占用她。"忙"只算任务正在计算的时候，不算任务存在的时候。于是专注里她的生活和用户的任务交错进行，而不是被整段挤掉。
3. **一个决定者**：她此刻做什么由一个调度点决定，替代各模块互相检查是否在忙。左页姿势直接取自它，用户一眼能看出她在做你的事、做她自己的事，还是在等你。
4. **一次交班说完两边**：休息时的交班既说用户的任务，也说她这一段自己做了什么、礼物有没有做好。这仍是"专注时安静陪伴，休息时交付和交流"的节奏，只是交付的内容里多了用户的工作。
5. **忙就是忙，如实反映**：用户让她忙了一整天，她自己的事就少，日记和闲聊里可以照实说；不为了"公平"在用户需要时把她调走。答应过的礼物不受影响：动工本来就不看她是否在忙，交付仍等休息。没有任务的专注、用户休息和用户不在时，她照常过自己的生活；外出仍按现有作息规则。
6. **工作和生活互为经历**：一件任务完成本身就是一段共同经历，可以成为礼物和日记的来源。她的读写作品能否取材于用户的工作内容，涉及工作内容的使用范围，先不做（待决定 D-9）。

### 2.6 邮件只经 Student Hub

删除核心直连 IMAP 和两个旧包，邮件只经校园助手插件进入。候选卡、看原文、确认 / 忽略、本地导出和证据库保留在 LCA；老用户已有候选与决定不变。没装 Student Hub 的用户不再有邮件功能（待决定 D-1）。

### 2.7 不变的约束

主进程拥有事实与权限；业务时间走 Clock / Scheduler；日志只追加，压缩不删原始历史；停止、取消、重启和恢复不重放旧批准；她生活的地点、时间与完成状态由代码决定，离线只补算一次虚构事件；日记不是事实来源；番茄钟是相处节奏，不被删减，产品也不缩成计时器。

### 4.3 D0 基线结果（2026-10-19）

固定剧本 S0（`pnpm probe:baseline-flow`，脚本 [probe-baseline-flow-live.mjs](../../scripts/probe-baseline-flow-live.mjs)，需要 `pnpm build` 与 `LCA_REAL_MODEL=1`）：新建工作目标 → 进入心流 → 批准计划（唯一 1 次审批）→ 一条固定工作消息（要求 `desk_write` 创建 `answer.js`）→ 退出心流。使用授权 providers 的 DeepSeek 官方 chat 槽位（能回报缓存字段；不是日常默认的中转 Gemini 槽位），提示词为合成文本，临时 profile 用完删除；报告只含 token 数、哈希与枚举。

证据都在本机 `test-results/d0-baseline-20261019/`：`context-continuity.json`（合成连续性探针 33 项现状）、`live-flow-run.json`（真实模型基线）、`summary.json`（机器摘要）。

| 指标 | 基线值 |
| --- | --- |
| 回合状态 | completed；`desk_write` 写入 `answer.js`；总耗时约 6.4 s，2/2 请求成功 |
| 成功请求 token | 输入 9,996 = 缓存命中 4,992 + 未命中 5,004；输出 247 |
| 第 1 次请求 | 输入 4,857（缓存 0 / 未命中 4,857），输出 243 |
| 第 2 次请求 | 输入 5,139（缓存 4,992 / 未命中 147），输出 4 |

| 审批次数 | 1（计划批准）；无运行 / 命令审批 |

## 6. 风险

- **上下文变长**：工作输出拉长时间线，可能拖慢响应或降低质量；靠交班压缩缓解，需要实测。
- **续跑成本**：专注中自动续跑可能失控；每段专注设预算与回合上限，超限即停，并在休息时说明。
- **两边紧挨着调用模型**：她的读写走 background 路由，任务走 chat；等待期间两者可能交替调用，预算由资源账本统一核算。任务恢复时，生活作品按现有方式中止当前一步并留书签。
- **工具全集**：全天固定的工具列表可能让模型在不合适的时候调用工作工具；调用时判定并返回明确错误，误用次数计入 R2。
- **缓存依赖供应商**：前缀稳定不等于命中，各供应商规则不同；以 R1 实测为准。
- **测试改动面**：现有场景脚本依赖按钮名（如"进入心流"），分支内需要同步更新。
- **旧数据**：合并前要把旧心流区间投影为已结束的历史任务、旧工作目标转为目标，旧日志不改写。
