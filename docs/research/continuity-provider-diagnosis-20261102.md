# Provider 超时的控制变量复现

2026-11-02。用户要求详细探究原因并复现结论。本轮上限为 8 次真实请求、128,000 预留单位、自主 0。最终恰好使用 8 次，窗口已持久关闭，关闭后再次运行被入口拒绝，未产生第 9 次请求。

## 结论

**本地失败的直接原因已确定：探针在 45 秒时主动调用 abort，终止仍在等待响应头的请求。相同调用条件随后可以在几秒内成功；没有复现出确定性的 LCA 工作调度、上下文格式或 Node 专属故障。** 用户随后报告的 `client_gone` 与主动取消机制相符，但日志时间字段尚未确认，不能认定就是这两次探针；具体对应条件见下节。

证据最强的一对是第 1、6 次：同一端点／模型、同一 139 字节请求体、同一 Node fetch、同一 45 秒上限，前一次在请求写出后等不到响应头，后一次 5.338 秒成功。cURL 独立重现了同类超时，所以故障并不需要经过 LCA、DSH 或转发网关。完整产品输入也分别在 cURL 和 Node 下成功，原正常书页测试入口随后成功。

这界定了本地失败机制，**尚不能区分 provider 内部排队／首响应耗时、中间网络或透明代理为何使等待超过阈值**。不能把“客户端写出请求”当作“模型服务已接收”，也不能把无响应头称为空响应。45 秒是测试脚本的选择，不是 provider 可用性或模型完成能力的可靠界线。

## 用户补充的 client_gone 日志

用户随后说明早上还有其他 agent 使用同一 key，并在 provider 后台看到两条流式 `client_gone`，时间为 08:30:17 与 08:12:51，首字／耗时约 45 秒和 1 分钟。用户认为时间列“应该是开始时间”。以下服务端信息来自用户转述，尚未取得请求 ID，时间字段含义仍未直接验证。

| 本地请求 | 本地开始 | 本地 45 秒截止 | 用户提供的 provider 时间 | 相对本地截止 |
| --- | --- | --- | --- | --- |
| 首批工作 | 08:11:45.131，账本准入近似开始 | 08:12:30.144，近似 | 08:12:51 | 晚约 20.856 秒 |
| 单次补测 | 08:29:30.670，记录的请求开始 | 08:30:15.676 | 08:30:17 | 晚约 1.324 秒 |

只有当 provider 时间表示结束／记录时间时，第二条才高度吻合本地主动取消后的记录；第一条差约 21 秒，仍不能确认匹配。如果按用户的判断视为开始时间，两条都晚于本地请求取消，不能直接对应这两次探针，可能是同 key 的其他请求。

作为字段含义的实现参照，[New API 当前日志代码](https://github.com/QuantumNous/new-api/blob/main/model/log.go)在记录消费或错误日志时，把当时的时间写入 `CreatedAt`，不是直接读取请求开始时间。因此不能仅凭界面上的“时间”二字确定它是开始时间。该 provider 是否采用此实现／字段未确认，不能拿通用源码覆盖用户实际部署；需要字段说明或请求详情完成关联。

作为实现参照，[New API 的流扫描代码](https://github.com/QuantumNous/new-api/blob/main/relay/helper/stream_scanner.go)在客户端请求上下文取消时设置 `StreamEndReasonClientGone`。部署是否采用该项目及具体版本未确认；本地则已经确认 `clock.after(45000, ...)` 调用了 `abort.abort()`。因此应优先解释为“探针截止导致客户端取消”，不是仅凭该标记断言 provider、模型或网络失败。错误记录中的首字数字也应核实其统计含义，不能仅凭它断言模型在该时刻才生成第一字。

同 key 的并发调用可能共享 provider 的并发／速率额度；是否因此排队，需要服务端策略与时段日志证明。没有证据把责任归给用户的其他 agent。后续测试应把首响应等待、流中空闲和总时长分别记录并配置，按新窗口验证，不能直接删掉旧失败或无条件无限等待。

## 网络路径发现及其限度

只读检查显示 Windows 为该端点选中了系统代理，当前进程没有代理环境变量，并存在名称符合隧道特征的网络接口。默认 cURL 报告 `proxy_used: 0`；Node 没有接入 Electron session 的系统代理，连接地址哈希与 DNS 目标一致。

这说明默认探针与使用系统代理的客户端可能走不同路径。第 8 次只在该次请求中采用现有系统代理，保留 HTTPS/TLS 验证，不更改系统设置、不失败回退，能够正常返回。但默认路径也出现了快速成功，且这里只有一次顺序代理对照，**不能据此宣称“代理绕过就是根因”或“切换代理已经解决间歇故障”**。`proxy_used: 0` 也不能排除透明隧道。其他 agent 的实际路径未核实。

下一轮若需要继续定位到网络或 provider 内部，应把这些精确时间与入口／代理／模型日志对齐，并用固定请求体做交错路径对照。当前证据不足以替代这一步；本轮额度已结束，没有自动继续。
