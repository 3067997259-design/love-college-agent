# Provider 超时的控制变量复现

2026-11-02。用户要求详细探究原因并复现结论。本轮上限为 8 次真实请求、128,000 预留单位、自主 0。最终恰好使用 8 次，窗口已持久关闭，关闭后再次运行被入口拒绝，未产生第 9 次请求。

## 结论

**本地失败的直接原因已确定：探针在 45 秒时主动调用 abort，终止仍在等待响应头的请求。用户随后提供的 CSV 表明，相关请求高度匹配 provider 的消费记录，时间列是结束／记账时间。四次本地超时对应的服务端记录均有输出 token 和非零费用。** 相同调用条件随后可以在几秒内成功，没有复现出确定性的 LCA 工作调度、上下文格式或 Node 专属故障。

证据最强的一对是第 1、6 次：同一端点／模型、同一 139 字节请求体、同一 Node fetch、同一 45 秒上限，前一次在请求写出后等不到响应头，后一次 5.338 秒成功。cURL 独立重现了同类超时，所以故障并不需要经过 LCA、DSH 或转发网关。完整产品输入也分别在 cURL 和 Node 下成功，原正常书页测试入口随后成功。

CSV 把范围进一步收窄：相关请求已在 provider 侧处理并记账，“没有到达 provider”已不符合这些记录。**仍不能区分服务端排队、模型生成或上游转发各自占了多少时间**，也不能从没有首字字段的 CSV 推断首字延迟。45 秒是测试脚本的选择，不是 provider 可用性或模型完成能力的可靠界线。

## 用户 CSV 与本地记录对账

最初用户转述两条流式 `client_gone`，并认为时间列“应该是开始时间”。随后用户提供 `usage-logs-20261102-20261102.csv`，共 16 行数据。只读核对后，7 条已知成功请求的输入／输出 token、流式标记逐一吻合，CSV 时间与本地完成时间的最大绝对差为 **743 ms**，因此可以确定该导出时间列反映结束／记账时间。比如正常入口请求本地从 09:11:33.462 运行到 09:11:39.195，CSV 是 09:11:39，输入／输出为相同的 12,967／70 token。此前将其作为开始时间讨论的条件假设不再适用。

这也解释了首条为什么在本地取消约 21 秒后才出现记录：它的服务端耗时是 65 秒，不能直接把记账时间当作发起时间。两次最小请求本地都在 45 秒退出，provider 却分别记了 56／55 秒、44／109 token 和非零费用。因此“本地取消等待”不等于“provider 没有处理或没有消费”。CSV 不能证明取消何时传到上游，也不能把消费记录当作客户端成功收到结果。

CSV 的“详情”全空，没有首字时间、HTTP 状态或 `client_gone` 原始字段。`client_gone` 仍只来自用户后台观察，与本地截止触发取消的机制一致。[New API 的流扫描代码](https://github.com/QuantumNous/new-api/blob/main/relay/helper/stream_scanner.go)也采用这种标记，但 provider 部署身份与版本尚未确认，不能把参考实现当作部署证明。

本次仅分析已有记录，新增模型调用 **0**。CSV SHA-256 为 `24845cdaf1fc0f08b55ecab1dca2023740d00da0c2e6b328e387ea4bcb94b46b`。[对账证据](evidence/continuity-provider-csv-20261102.json)保留相关行号、时间推算和用量，原 CSV、令牌名称、IP、模型名、分组及完整请求 ID 不复制进仓库。

同 key 的并发是否导致排队仍无证据。后续应先把测试网关的首响应等待、流中空闲和总时长分开记录并配置，再在新授权窗口验证；本次没有改超时或重新运行请求。

## 网络路径发现及其限度

只读检查显示 Windows 为该端点选中了系统代理，当前进程没有代理环境变量，并存在名称符合隧道特征的网络接口。默认 cURL 报告 `proxy_used: 0`；Node 没有接入 Electron session 的系统代理，连接地址哈希与 DNS 目标一致。

这说明默认探针与使用系统代理的客户端可能走不同路径。第 8 次只在该次请求中采用现有系统代理，保留 HTTPS/TLS 验证，不更改系统设置、不失败回退，能够正常返回。但默认路径也出现了快速成功，且这里只有一次顺序代理对照，**不能据此宣称“代理绕过就是根因”或“切换代理已经解决间歇故障”**。`proxy_used: 0` 也不能排除透明隧道。其他 agent 的实际路径未核实。

CSV 已证明相关请求进入 provider 消费记录。若继续细分延迟，应进一步对齐 provider 入口、排队和上游响应阶段；网络路径对照只能辅助，不能再把“请求可能完全没到 provider”作为当前主结论。本轮额度已结束，没有自动继续。

## 安全范围、工具和验证

完整请求由 `probe-work-live.mjs --first-request-only --capture-request` 从新建空测试 profile 截取。它只包含新测试存档生成的上下文、静态产品指令、脚本 WORK_A 指令和工具定义；测试项目只有 `barrier.ps1`，没有导入日用聊天、邮件、文件或旧工具结果。主进程在保存前断言不存在 API key，捕获阶段上游调用为 0。完整外发最初被自动审批以“可能存在敏感用户上下文”为由拒绝；保留来源审计后，重新审批放行了同一份已审计输入。拒绝本身没有发出请求或消耗调用额度。

新增 `probe-provider-diagnosis.mjs` 支持固定序列化请求、传输、超时、允许的请求头和显式系统代理对照，分别冻结每一条件的源码与报告。密钥只在主进程读取；cURL 经 stdin 接收配置。响应只保留状态、用量、正文长度、工具调用数量与结束标记等摘要，不保存内部推理。Node 诊断仅记录允许的头字段与连接地址哈希。后续增加的头观察和关闭保护没有改变默认请求体；不同阶段的实际源码均可按各自清单核对。

通过 6 个文件的 **32 项相关单元测试**、Node 类型检查、修改路径 lint，以及关闭窗口的负向检查。测试覆盖原始 UTF-8 请求字节保持、流式结束、敏感值排除、禁用重定向／重试、代理安全约束和额度。没有修改生产运行时代码、重建候选或改变日用数据。

7 次直接诊断的账本为 112,000 单位，正常入口 1 次为 16,000，合计 **128,000**，自主和 embedding 均为 0。离线捕获的模拟账本单列，不算真实模型调用。本地成功响应合计报告 **39,317 token**；随后 CSV 对账补出两次超时的 **153 token**，这 8 次对应服务端记录合计 **39,470 token**。CSV 中这两条也有非零费用；这是消费记录，不是账户余额或退款核对，预留单位不等于账单金额。

本轮验证到首个模型响应。没有执行返回的工作工具，也没有完成前台并发、任务补充、停止或恢复等整条真实工作验收。
