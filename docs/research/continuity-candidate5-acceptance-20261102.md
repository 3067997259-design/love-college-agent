## Docker 恢复与镜像缺陷

原安装日志确认 Docker Desktop `4.96.3.244472` 是仅当前用户安装；签名有效、二进制仍在，但 HKCU 的卸载／安装登记缺失。报错显示的另一安装路径是启动器后续查找的结果，不能据此把缺失 MSI 项当成原安装方式。

在 Docker 与对应 WSL 均停止时，先备份 `D:\DockerData\main\ext4.vhdx` 和 `D:\DockerData\disk\docker_data.vhdx`。复制期间原文件只读锁定；压缩后独立解压计算 SHA-256，与两份原文件逐项一致。备份约 938.7 MB，保存在 `test-results/continuity/docker-repair-20261102-1/docker-data.zip`，哈希和恢复路径见结构化证据。冷备份原则与 [Docker 官方说明](https://docs.docker.com/desktop/settings-and-maintenance/backup-and-restore/)一致。

依据已安装官方安装器的 `RegisterProductStep` 与 `ExistingInstallation.FromRegistry`，只补回 HKCU `Software\Microsoft\Windows\CurrentVersion\Uninstall\Docker Desktop` 的路径、显示名称、版本、安装类型与发布者六个值。没有重装、重置、注销 WSL 或覆盖数据盘。Docker 正常启动，Engine `29.9.2` 响应；原 AIRI 容器和卷重新可见，AIRI 容器保持原来停止状态，未访问其数据库。

复用本地 `pgvector/pgvector:0.8.7-pg18-bookworm` 镜像（固定 image ID），只创建带测试标签的独立数据库。依次保留了这些失败与修复：

1. 两个旧夹具使用不符合产品约束的 schema 名，产品正确拒绝；修正夹具，未放宽名字验证。
2. 首次初始化未指定扩展位置，把数据库级 vector 类型装进第一个私人 schema，后续空间找不到类型。新代码固定安装到 public，以事务锁串行化扩展初始化；只迁回旧 LCA 命名空间中的误装扩展，业务表和数据仍留在原空间。其他自定义空间明确报错，不接管。语义依据 [CREATE EXTENSION](https://www.postgresql.org/docs/current/sql-createextension.html) 与 [ALTER EXTENSION](https://www.postgresql.org/docs/current/sql-alterextension.html)。
3. 真实断库后，查询已报错，Postgres.js 的无期限 `end()` 仍卡住。分阶段诊断停在 closing；关闭增加 5 秒截止，让后续重连可以继续，未知写入仍不产生成功回执。
4. 重启测试容器时 Docker 重新分配匿名端口，旧 URL 失效。运行器改为每批选择空闲端口并显式绑定，重启后断言端口不变；新增检索夹具也明确设为已审阅，遵守原查询过滤。
