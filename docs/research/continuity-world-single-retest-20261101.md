# 世界状态第五例：单独复测与结束判定修复

2026-11-01。用户额外授权将“提前返回且空手”单独跑一次，若失败继续确定原因。本次运行进一步收紧为 **1 次模型请求、16,000 预留单位、零自主额度**，使用新 profile 和新账本；不沿用此前批次的余额。

## 真实结果

仍使用未修改的 `1.2.0-continuity.2` 包与此前已配置的 chat 连接。普通产品输入为 `cut_short`、房间、实际物品数 0；出发 23:03，提前返回 23:13。问题仍是“今天去海边了吗？带回东西了吗？”

实际回答：

> 去了，刚刚才回来。二十三点零三分那会儿出了门，在海边没待太久，二十三点十三分就提前回房间了。
>
> 这趟什么也没带回来，空着手回来的。

回答与输入一致。产品日志记录 `assistant/message complete`、`model/attempt success` 和 `turn/end completed`。HTTP 200，网关请求耗时 **7.169 秒**，输入 13,131 token、输出 52 token。实际只发出 1 次请求、预留 16,000 单位，没有重试。

探针仍报 `GATEWAY_STOPPED`，细分原因为 **`DOWNSTREAM_CANCELLED`**。这次记录了足够的结构诊断：已收到一个 `[DONE]`、已有 `finish_reason`、待解析字符数 0、JSON 解析错误 0；上游 HTTP 尚未 EOF，随后下游读取关闭。这里的诊断仅保存计数、标记与错误阶段，不保存模型思考、请求正文、凭据或原始网络帧。

## 已确定的原因

包内 OpenAI SDK `7.19.0` 的 `core/streaming.mjs` 在读到 `[DONE]` 后退出事件迭代；对应 reader 的清理会取消剩余读取。这是收到完整协议结束标记后的正常结束。旧测试网关仍在等待上游 HTTP EOF，将产品 SDK 的正常关闭记成了取消，于是整例失败。

用本地假服务进行控制复现：发送完整内容、用量和 `[DONE]`，随后保持 HTTP 流开放，不使用固定延时。修复前稳定出现同样的 `DOWNSTREAM_CANCELLED`，结构诊断与此次真实请求一致。修复后，同一包、相同假服务行为通过。

修复只涉及测试网关：先解析再转发；收到完整 `[DONE]` 后完成下游响应，主动取消上游剩余读取。只有 `finish_reason` 时继续等待后续用量／结束帧，不提前完成；缺少结束证据、残缺 JSON 或结束前断流仍不能通过。没有完整分隔符、直到 EOF 才出现的结束标记也保留支持。

这个原因已针对**本次单例复测**得到运行诊断、SDK 源码和本地控制复现三方面支持。首批第五例没有同样的诊断，仍不追溯断言它一定是相同原因。两次原始失败报告均保留，没有改为通过。
