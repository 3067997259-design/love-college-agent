# 插件迁入评估规格

版本：0.1，2026-10-26。适用于从 DSH 市场继承、定向适配、抽取组件和 LCA 原生开发，也适用于其他生态的候选。

**评审单位是“一个固定版本中的一项能力，以及它进入 LCA 后的完整使用流程”。** 同一插件的不同能力可以得到不同结论。评审标准统一，转换方案逐项设计；共享 DSH / Cordis 不能替代产品适配判断。

本文建立可复用的评审流程，不新增运行时 API、不放宽插件权限，也不宣布已有样本兼容。核心约束沿用 [AGENTS.md](../AGENTS.md)、[技术方案](tech-design.md)、[体验设计](experience-design.md) 与 [隐私与数据](privacy-and-data.md)；候选接口明确列为“待设计”。评审从 [迁入评审模板](templates/plugin-migration-review.md) 开始，实例记录放入 `docs/research/`。

## 1. 一次评审必须交付什么

每次评审给出以下九项，不能只写“支持 / 不支持”：

| 项目 | 必填结果 |
| --- | --- |
| 对象 | 上游版本 / commit、实际制品 hash、依赖与配置；LCA revision / dirty 状态、DSH、OS / Electron 基线 |
| 范围 | 要保留的具体能力、明确舍弃的能力、用户从哪里开始与在哪里拿到结果 |
| 价值 | 解决什么已有需求、相对现有能力增加什么、收益证据与未知项 |
| 决策 | 进入实现 / 先验证 / 暂缓 / 不迁入，以及决定依据 |
| 迁入路线 | 原样继承 / 外围适配 / 定向 fork / 组件复用 / 原生实现 |
| 流程影响 | 第 3 节的最高影响等级，涉及的核心约束编号 |
| 改造清单 | 每一部分保留、配置关闭、替换或重写；宿主缺口及负责人 |
| 验证与许可 | 分维度证据、失败与未测；允许的使用 / 分发范围及待处理义务 |
| 维护与退出 | 更新责任、复核触发条件、停用 / 卸载 / 数据保留与回退方式 |

源码评审可暂缺制品 hash，但必须标记，不能据此签发某个下载包的兼容结论。只适配一部分时，结论名称必须带范围，例如“某插件的显式图片分析能力适配版”。

## 2. 价值与可行性：先过门槛，再选路线

### 2.1 价值证据

以下各项记为“成立 / 不成立 / 未知”，附来源或可观察场景；不用加权总分抵消职责、权限或许可问题。

| 编号 | 成立的条件 | 不足以成立的理由 |
| --- | --- | --- |
| V1 真实用途 | 能写出至少一个 LCA 用户任务、触发方式、可验收结果；需求来自明确请求或记录的问题 | 插件很火、目录排名高、演示好看 |
| V2 增量收益 | 相比当前 LCA、已有 MCP / skill 或手动方式，增加能力或可说明地改善质量、步骤、成本 | 重做已有工作台、记忆或调度，但没有具体增益 |
| V3 流程适合 | 能给出完整的迁入后流程，保留角色连续性与既有决定权；无需让用户另学一套主流程 | 能加载、能注册工具，或只展示孤立技术 demo |
| V4 可持续 | 有维护人、版本策略、依赖 / 资源估算、可停止和退出的设计；所需成本在本次约定范围内 | 安装很快，所以长期维护也简单 |

V1 或 V2 不成立：通常不迁入；未知：先做最小用途验证。V3 或 V4 不成立：先裁剪范围、换路线，再评一次；无法改善则暂缓或不迁入。收益尚未实测可以进入有界实验，但必须写“预期收益”及验证办法。

### 2.2 必须单独检查的门槛

| 编号 | 门槛 | 不满足时怎么处理 |
| --- | --- | --- |
| G1 职责与流程 | 能保持第 3 节核心约束，执行 / 事实 / 授权 / 数据各有明确所有者 | 删除冲突功能、改造其职责；若仍需改变核心流程，转独立产品 / 架构决策 |
| G2 可控执行 | 知道全部执行入口、嵌套模型 / 外发调用、安装脚本和后台活动；能解释停止与未知结果 | 先查源码或做隔离探针；不能用外层 tool 审批推定内部调用受控 |
| G3 宿主可用 | 每项依赖能对应当前接口，或有明确的新增接口方案和验收范围 | 标记宿主缺口；不能通过禁用守卫或恢复整套 DSH Desktop 来“修兼容” |
| G4 许可路径 | 对这次具体动作，有明确授权依据和可落实的义务清单 | 暂停相应复制 / 修改 / 分发动作；可继续不依赖该授权的分析，另选路线 |
| G5 可证明与维护 | 成功、失败、取消、升级和退出都可核实，有负责人承担后续维护 | 缩小实验范围；没有交付证据就不能进入已验证目录 |

决策使用固定词汇：

- **进入实现**：价值理由成立，目标路线可行；缺口已有明确设计与验收，不含未决定的核心变更。只是工程决策，不等于已可用、已发布或获得真实服务调用授权。
- **先验证**：有价值假设，但存在决定路线的未知项。写清一个有界实验、预算、成功 / 失败条件及截止点；不无限扩充宿主来追求加载成功。
- **暂缓**：等待具体接口、许可、维护资源或产品决定，列出重新评审条件。
- **不迁入**：缺少增益，或可接受成本内无法适配。可以保留设计参考，但不挂“兼容”标签。

## 3. 哪些改动会触碰核心 userflow

先画出迁入前后同一个用户场景：**触发 → 上下文 / 权限准备 → DSH 执行 → 等待与停止 → 核实结果 → 书页交付 → 后续回忆或恢复**。标明每一步由谁决定，哪些状态持久化，以及专注、熄灯、换项目时会怎样。只有“工具输入 → 工具输出”的图不足以说明适配完成。

### 3.1 影响等级

| 等级 | 判定 | 处理 |
| --- | --- | --- |
| F0 内部能力 | 只增加解析、转换、查询等能力；用户入口、授权和交付方式不变 | 常规实现与相关回归；“只读”仍需检查数据外发和来源 |
| F1 既有流程内扩展 | 增加明确的工具、技能、连接配置或候选类型，沿用既有入口和决定方式 | 写迁入后的具体场景、能力范围和错误反馈，按现有扩展机制接入 |
| F2 新交互或宿主接口 | 需要新卡片 / 书签子页、受限数据出口、任务触发接口等，但不改变核心决定权 | 单独写接口和体验设计，说明为何不能复用现有面；新接口完成前标为缺口 |
| F3 核心流程改变 | 改变谁能启动工作、何时打断、谁批准、谁记忆、谁决定事实，或替换会话 / 编排 / 角色主入口 | 超出普通插件迁入；需要用户明确的产品决定及独立设计，不能由插件默认值决定 |

按全部保留能力取最高等级。F2 不自动意味着必须反复询问用户；常规可逆实现按项目约定推进，实质改变方向、权限或采用新美术才需要对应决定。已有明确授权不重复索取。

### 3.2 核心约束与常见触碰方式

| 编号 | 保留的 LCA 语义 | 需要拦下或另行设计的改动 |
| --- | --- | --- |
| U1 工作与角色连续性 | 同一角色的聊天、工作、生活保持连续；当前项目的回合沿用 LCA 接入的 DSH 会话与来源规则 | 插件另开隐形主 agent、替换 persona / 系统约束、建立第二套任务板和完成状态 |
| U2 执行所有权 | 模型步骤、工具、重试、取消由 DSH 执行；LCA 绑定作用域、授权、路由和逐步额度；协作也沿用此边界 | 插件自建规划—模型—工具循环、自发根会话、改模型回退或绕开成员授权；Minecraft 例外不外推 |
| U3 用户决定与结果 | 既有问题 / 审批卡、停止、实际工具与产物核验；accepted 不等于完成 | 插件自己的“永远允许”、隐式外发、把任务板 done 当交付、丢回执后自动重试外部动作 |
| U4 节奏与状态 | 专注安静陪伴，按既有规则在休息交付；熄灯暂停后台与计时；睡眠另有状态；手动门牌优先 | 自带 cron 唤醒、结束番茄专注、普通后台逐次通知、因工具结束自动翻牌、抢焦点 |
| U5 原文与隐私 | 用户 / 角色 / 项目 / 数据根隔离；原文按回合授权和退役；独立隐私失败停止，不静默回退 | 全局扫描、任意读取私有根、把原文交给插件自选 provider、跨项目缓存召回、原文进入 renderer / 普通日志 |
| U6 记忆与事实 | 只从成功模型输入的允许片段抽取记忆；索引、摘要、日记、候选与现实事实分开 | 将文件索引、工具原文、自动事件直接写成经历；用日记或模型自述补实际完成状态 |
| U7 持久化与恢复 | append-only 事实保留；统一 Clock / Scheduler；恢复不补算工作、不重放批准；未知动作先核对 | 改写旧历史、复制外部 agent 状态后继续执行、恢复返还预算、升级自动续跑旧任务 |
| U8 产品表面 | 书本与小窗是主入口；renderer 消费安全投影；既有角色素材与身份契约保留 | 引入独立工作台取代书页、网页获得 Node / 任意 RPC、未确认采用新形象、把关系解锁变成基本工作门槛 |

更换解析库、增加受控工具、改结果排版不必然触碰核心流程；关键看**决定权、授权范围、状态转换和用户承诺是否变化**，不能只按改了多少文件判断。

## 4. 当前可以扩展哪里

以下为 2026-10-26 开发工作区的源码核对，基线 `711af30d0299141d5830d78b51090dd195f9cb31` 且存在未提交改动。它是选接入面的依据，不是稳定公共 SDK 承诺；实际迁入时重新固定目标版本。

| 接入面 | 当前已具备 | 边界 / 仍缺少的东西 |
| --- | --- | --- |
| LCA 本地工具包 | `manifest.json` apiVersion 1、`.cjs` 工具入口、schema 校验、指纹启用、隐私包装；实现收到 `nowMs / signal / turnId` | 不是 DSH bundle；不向外部工具传内部 store / 凭据。Node 代码按可信代码执行，permissions 不是 OS 沙箱 |
| MCP | LCA 管理 stdio / Streamable HTTP 连接与工具白名单，再提供给 DSH | 保持单一连接所有者；不能自动带入另一宿主登录状态、独立连接或全部工具权限 |
| Markdown skill | 选定项目和当前存档的受限搜索根、导入、来源追踪与退役 | 内容不是权限授予；资源 / 脚本仍受路径、执行与回合授权限制，不能靠 skill 指令改主流程 |
| DSH bundle | 本地目录选择、`dsh.bundle`、Cordis 服务、安装 / 启停 / 重启 / 核对操作 | patch 只允许自身 `包名:` 命名空间的 insert 行，不能替换受保护组件；可加载不等于宿主服务齐全或行为受控 |
| 校园证据与候选 | `sourceMails` 经主进程既有提取 / 校验链；候选进入已有确认与版本流程 | 这是有具体类型的窄出口，不是任意私有数据总线；新领域须审视类型、授权和交付，不能把数据伪装为邮件 |
| 交付与 UI | 已有工具活动、问题 / 审批、候选、文件交付、插件管理等 LCA 页面 | 新 UI 由仓库代码实现安全投影；没有任意 DSH Web client / React 插槽。manifest 的 `furniture / configSchema` 被 schema 接受，不足以证明已有通用渲染 / 配置表单能力 |
| 激活与后台任务 | 本地包有 `activate({ nowMs, signal, ingestCandidates })`；内置服务有启停挂接 | 外部包没有通用 Scheduler 注册口，也没有完整的统一 activation dispose 契约。不能从存在 activate 推定停用会终止所有后台工作 |
| 模型、上下文、记忆与存储 | LCA 内部已有对应服务及 DSH bridge 适配 | 内部函数不等于可供插件调用的公共 API；没有通用第三方 prompt 改写、记忆写入、私有库读取或凭据共享契约 |

源码入口：[manifest](../src/main/plugins/manifest.ts)、[工具 registry](../src/main/plugins/registry.ts)、[MCP](../src/main/mcp/service.ts)、[skills](../src/main/dsh/skills.ts)、[bundle 主进程](../src/main/dsh/extensions.ts)、[bundle 守卫](../dsh/lca-bridge/extensions.js)、[扩展安全投影](../src/shared/extensions.ts)、[插件页](../src/renderer/src/plugins/PluginCenter.tsx)。

**现有两类代码插件都不是不可信代码沙箱。** 限定调用参数、声明权限、校验 patch 只能保护对应入口，不能证明插件 JavaScript 无法自行使用宿主能力。当前评审需要覆盖实际代码与依赖；若未来市场要接收未经审查的任意代码，须先另行设计隔离与权限执行机制，不能通过增加 manifest 字段宣称已经解决。

## 5. 怎么选迁入方式

先选最小完整的用户能力，再比较下列路线。是否保留包名、Cordis 或工具名都不是决定条件。

| 路线 | 适用条件 | 必须交付的差异说明 |
| --- | --- | --- |
| M0 原样继承 | 固定上游制品无需代码 / patch / 行为适配，所需服务已存在，目标功能满足 LCA 约束 | 锁定版本、配置与被验证范围；按原支持配置关闭的功能也须披露，不能称整包功能全兼容 |
| M1 外围适配 | 原实现可作为受限输入输出能力使用，不需要接管其内部编排；新增适配层即可接入 LCA | 映射协议、来源、授权、结果与停止；上游包不改也属于适配，不计作原样兼容 |
| M2 定向 fork | 核心能力值得保留，但需裁去或替换部分 provider、UI、hook、调度或存储行为 | 改动文件 / 补丁、禁用功能、与上游同步办法、适配包自己的版本和制品 hash |
| M3 组件复用 | 只有解析器、算法、格式、控件等独立部分合适，整包职责不适合 | 复用组件范围、依赖和来源许可；宿主行为由 LCA 实现，不称整个上游插件兼容 |
| M4 原生实现 | 无合适组件，或保留上游需要重写大部分编排 / 数据 / UI，维护 fork 不划算 | 以 LCA 流程定义需求，记录参考来源与实际复用内容；重新实现不是自动免除许可核对 |

每个进入实现的方案，至少比较“推荐路线、一个可行替代、暂不做”。比较初次实现成本、每次 LCA / DSH / 上游升级的维护成本、依赖与资源、用户操作负担、权限范围和退出成本。估算标为估算，附依据；不设凭空的重写比例阈值。

典型选择顺序是：原样是否语义成立 → 能否用小适配保持职责 → fork 是否仍保留足够有用实现 → 能否只用独立组件 → 原生实现是否更清楚。某条路线不合适不等于这项需求不值得做；反之，原样可装也不等于值得收录。

## 6. 迁入时具体改哪些东西

逐项填写改造账本。结论只能是“保留 / 配置关闭 / 替换 / 重写 / 不适用 / 待核实”，每项都有源码依据、目标行为和验收。配置关闭也要核实该配置确实阻止注册、启动与副作用。

| 检查项 | 必须回答的问题及常见改造 | 需要的证据 |
| --- | --- | --- |
| D1 包与依赖 | 是插件还是另一款宿主？目标入口、Cordis 注入服务、版本、安装脚本、原生模块、平台工具是什么？替换 packaging 还是抽组件？ | 实际发布制品、依赖锁定、干净环境安装；仅改行 ID 不算运行验证 |
| D2 执行与授权 | 启动 / 回调 / hook / 子进程 / 子代理分别从哪里来？哪些读写、命令、外发需批准？是否有独立循环或 permission preset？ | 用户入口到真实副作用的调用链，拒绝 / 撤销 / 迟到回调反例 |
| D3 模型与资源 | 嵌套 OCR / vision / embedding / LLM 是否另拿凭据、另走 fallback？应接 LCA 哪条路由、额度、超时和取消？ | 每一笔外部调用的归属；额度不足或独立隐私失败时未发请求。新服务尚无额度入口时列为缺口 |
| D4 来源与上下文 | 每种输出是事实回执、第三方原文、用户内容还是派生摘要？何时进入模型、何时退役，委派 / 压缩后如何追踪？ | 当前轮、下一轮、重启和成员传递的模型投影。新工具名不自动获得正确来源分类 |
| D5 数据与作用域 | 读取哪些目录 / 会话 / HTTP 接口？存在哪里、保留多久、作用域是什么？索引与角色记忆是否分离？ | 跨项目 / 角色拒绝，删除或失效来源不再召回，日志与 renderer 不泄露私有原文 |
| D6 调度与节奏 | 谁触发自动工作？用什么业务时钟？专注、熄灯、睡眠、跨日、离线如何处理？ | 对应状态转换；没有自行唤醒或补算实际工作。主进程没有所需触发接口时先设计接口 |
| D7 结果与交互 | 沿用哪个入口、审批、等待和交付面？如何区分已接收、处理中、失败、未知、完成？ | 从书页操作到实际产物 / 远端回执；本地导出不算外部写入 |
| D8 生命周期 | disable、cancel、断连、退出、重启、换项目对运行任务和迟到结果分别有什么效果？ | 无新副作用、旧授权失效；已发动作未知时能核对。区分 LCA 工具停用和 DSH bundle 待重启 |
| D9 存储与恢复 | 新状态是否进私人存档、如何迁移 / 导出 / 清理？服务端状态是否需要重新查询？ | 恢复不携带凭据或重放动作，卸载不误删用户产物；回退保留历史与未知结果 |
| D10 许可与供应链 | 源码、依赖、模型、字体、素材分别来自哪里？安装脚本和更新是否引入新行为？ | 第 7 节的具体义务与随包文件；hash 只标识制品，不证明代码可信 |

原生 DSH 工具尤其要核对 [policy.js](../dsh/lca-bridge/policy.js) 与 [bridge](../dsh/lca-bridge/index.js) 的实际接入：不能通过改名假装来源已分类，也不能从“工具外层受审批”推定内部网络、文件或模型调用同样受控。发现未覆盖行为时，应明确补适配或拒绝该能力，不能宣称现有规则自动覆盖所有第三方工具。

## 7. 许可与分发独立判定

许可结论绑定**内容 + 版本 + 集成方式 + 拟执行动作**。目录许可不覆盖被收录项目，根 LICENSE 不自动覆盖全部依赖、模型或美术。分别记录：收录介绍、用户安装原包、复制组件、修改 fork、随 LCA 分发、远程服务；某一项可行不代表其他项已核对。

评审表至少包含：原作者 / 来源、许可证全文位置、文件或组件范围、修改记录、所需 LICENSE / NOTICE / 署名、适用时的源码提供方式、素材与商标条件、负责人和待核实问题。正式分发时把实际采用部分记入 [第三方说明](../THIRD_PARTY_NOTICES.md)，并核实许可证文件进入制品。

- MIT 复用须保留适用的版权与许可告知，不能只留下一个 SPDX 标签。[MIT 原文](https://opensource.org/license/mit)
- Apache-2.0 分发核对许可证副本、修改标记及适用的归属 / NOTICE 要求。[第 4 节原文](https://www.apache.org/licenses/LICENSE-2.0.txt)
- 强 copyleft、额外条款或许可冲突按具体组合评审；不能仅因单独进程、IPC 或“插件”名称认定已隔离，也不把某类许可证一概等同于不能用。缺少明确许可时，不从公开可读推导复制、修改、分发授权。具体样本与许可问题见 [研究记录](research/dsh-plugin-host-semantics-licenses-20261026.md)。

固定状态为：**目标动作的授权与义务已核对 / 义务待落实 / 授权待明确 / 当前方案不可采用**。前两者也须写范围；“已看过根 LICENSE”不能填成所有内容可再分发。需要专门判断而尚未解决的组合问题保留为阻塞项，不用兼容测试代替许可判断。

## 8. 验收：每个承诺都有对应证据

所有维度单独记为 **通过 / 失败 / 未测 / 不适用**，附制品与配置、运行环境、断言和结果。不适用要给理由；不采用单一“最高测试等级”掩盖未测项。

| 维度 | 证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| E0 源码与方案 | 依赖、职责、数据流、差异和许可范围有依据 | 已加载、已安全运行或已分发清关 |
| E1 包装与准入 | 对应入口接受 / 拒绝 manifest、patch、路径、版本 | 依赖可安装；预期拒绝的断言通过不算插件可用 |
| E2 安装与激活 | 真正安装指定制品、启动需要的服务并核对实际状态 | 工具语义正确、UI 可达或用户任务完成 |
| E3 LCA 合成场景 | 在真实 LCA 接线下用受控服务完成正反场景，核对权限、来源、产物 | 真实供应商、账号、学校或外部写入已成功 |
| E4 真实功能 | 在获明确授权的范围和预算内，完成目标服务任务并有实际结果 | 未测供应商 / 功能、长期质量、升级和安装态也通过 |
| E5 生命周期与隔离 | 相关的取消 / 停用、未知核对、重启、换项目、恢复、跨日和冲突场景成立 | 加速跨日等于真实长期体验；一个平台等于所有平台 |
| E6 发布环境 | 指定打包或安装环境下的依赖、入口、许可证和功能成立 | 包内 EXE 检查等于真实安装 / 升级，旧包结果等于新包结果 |

测试选择由能力决定：纯本地解析能力可将真实外部服务标为不适用；没有持久化或后台执行的 skill 不必硬套完整 cron 矩阵。选择要在运行前写明，不能测试失败后改称不适用。真实模型、扫描、外发和付费服务遵守项目已有授权规则，评审文档本身不授予调用权限。

### 必选反例的选择规则

凡能力触及某一项，就至少覆盖相应失败路径：

| 触及的行为 | 必须验证的反例 |
| --- | --- |
| 原文 / 外部内容 | 来源退役、提示注入不能升权、隐私失败、下一轮或重启后不能重新自动注入 |
| 写入 / 外发 / 付费 | 拒绝与额度耗尽发生在副作用前；取消 / 丢回执后核对，避免重复发送或生成 |
| 后台 / 长任务 | 熄灯、停用、换项目、取消和迟到回调；已发外部动作保留未知状态 |
| 缓存 / 记忆 / 持久化 | 跨作用域拒绝、来源失效、升级 / 恢复不返还预算或重放授权 |
| 自定义 UI / 本地代码 | renderer 无任意文件 / RPC / 密钥通道；宿主代码实际权限与评审相符；兼容性限制明确呈现 |

正向场景必须贯穿触发、必要的批准、执行、失败反馈和可打开 / 可核实结果。组件测试、工具列表、模型自述和页面截图各自只证明对应部分。

## 9. 可以补充的扩展契约

以下是从样本暴露的问题提出的**候选方向**，当前不是已存在的 SDK，也不要求为一个插件一次性全部建设。只有选中的真实能力需要且有复用价值时，再单独设计和实现。

| 候选契约 | 应解决的具体缺口 | 不应交给插件的决定权 |
| --- | --- | --- |
| 工具能力与来源描述 | 统一表达读写 / 外发 / 原文 / 作用域 / 取消 / 资源需求，接入实际策略而非只靠工具名 | 自行把第三方数据标成可信指令，或声明后即绕过检查 |
| 受控辅助模型调用 | 图像分析、embedding 等嵌套调用复用选定连接、隐私路由、预算与取消 | 自选隐藏 provider、读取主进程密钥、自行无限回退 |
| 后台任务生命周期 | 向 main 提交有界任务需求，由 Clock / Scheduler 判断可运行时机并记录状态；模型工作进入既有 DSH 路径 | 插件自建业务时钟、自主根会话、绕过熄灯或重放恢复任务 |
| 领域证据与产物出口 | 新领域有类型、来源、版本、保留期限和安全投影，不借用邮件类型表达所有数据 | 私有原文写普通日志、直接生成记忆或将候选当已确认事实 |
| 有限 UI 扩展 | 经过审查的状态与有限命令映射到书页组件，复用审批和交付 | 任意 Web 页面、Node、RPC，或替换主工作台 |

内部已有服务可被仓库实现复用，但对外开放必须重新限定输入、调用者、作用域、状态与失败语义。接口改动遵守共享类型和独立接口提交约定。确实需要改核心主流程时，另做产品设计，不把它藏在“插件兼容补丁”里。

## 10. 用已研究的样本校准标准

下列是**迁入方向示例**，源自固定快照，尚无这些适配制品或运行验收，也没有完整的再分发结论。它们验证评审能产生不同方案，不构成实施承诺。原始证据见 [五项样本研究](research/dsh-plugin-host-semantics-licenses-20261026.md) 与 [Coopanion 研究](research/dsh-plugin-compatibility-coopanion-20261026.md)。

| 候选及缩小后的需求 | 建议先比较的路线 | 主要变化与流程影响 |
| --- | --- | --- |
| ModLens：用户显式选择图片后分析 | M1 受控引擎适配 vs M3 / M4 图像工具 | 逐项处理原包 provider 包装及自动读取；图像授权、路由、预算与结果由 LCA 接入。若需辅助模型接口为 F2，不能默认当 F0 工具 |
| dsh-context：只看聚合上下文用量 | M3 / M4 只读面板 | 目标范围排除全局 prompt 前后缀编辑和原始 session HTTP 暴露；用安全聚合投影接书页。新面板 F2；原包其他功能不计兼容 |
| DSH-better-sidebar：查看本项目文件差异 | M3 控件或 M4 有限差异查看 | 不迁入整套 sidebar 工作台；沿用项目权限，核对所需控件是否可独立抽取。新视图 F2；无限路径浏览和替换主入口涉及 U5 / U8 |
| dsh-cron：按用户安排触发一项工作 | M3 时间表达组件 + M4 宿主任务接入 | 原自带调度 / agent runner 不原样接管 LCA；还缺通用触发契约。定时工作何时可启动先有产品决定；通常至少 F2，改变自动启动权则 F3 |
| dsh-project-memory：当前项目显式检索 | M3 索引 / 检索组件 vs M4 项目检索工具 | 与角色经历分开；重新设计文件授权、失效和召回范围，取消隐式长期回填。受限显式查询可为 F1，需要新数据出口则 F2 |
| Coopanion：某项陪伴交互 | 先判断需求，再考虑 M3 / M4 或仅参考 | 属于另一套宿主 / World 方案，不能列 M0 DSH 插件；先保持 LCA 角色、生活与视觉契约，并核对代码和资产各自许可 |

### 示例：dsh-cron 不能只写“改成用 LCA Scheduler”

一个完整的评审应先固定场景，例如“用户明确安排明天整理某个项目；到时在允许工作的状态下执行，遇到需批准的动作等待，结果回书页”。这只是评审用场景，尚不是已确定的产品需求。

1. **价值未知项**：与现有计划 / 提醒相比，是否确实需要自动开始实际工作？如果只需提醒，任务 runner 没有迁入必要。
2. **职责表**：时间表达解析可以复用；持久任务意图、可运行时机、作用域和运行记录归 main；模型工作归现有 DSH 路径；用户批准仍在书页。
3. **必须作出的决定**：到点处于专注 / 熄灯 / 睡眠时是跳过、等待还是提示？跨日 / 恢复是否仍有效？不能从上游 cron 默认行为推导答案。
4. **改造范围**：逐项确认解析组件可抽取；原 scheduler / runner 不保留；补主进程触发契约，声明 task / run 身份与结果核对，不迁移旧执行授权。
5. **验收**：受控时钟下按规定触发一次；重复事件不重复执行；熄灯、取消、换项目、断连和恢复有明确结果；实际交付可核实。真实调用另按授权和预算验证。
6. **当前结论**：先验证用途并形成产品决定，不能因为有 cron 包就认定应开放自动工作。组件复用与从头实现分别估成本；尚不填写“可安装 / 可用”。

## 11. 将评审结果用于自己的 market

市场条目应以用户能得到的 LCA 能力命名，同时保留上游来源。先有评审记录即可积累候选目录，不必先做远程安装、通用转换器或任意代码商店。

每项同时展示三种信息：

- **接入方式与范围**：原样制品 / LCA 适配版 / 组件来源 / 原生能力 / 仅研究；舍弃功能明确列出。
- **实测状态**：固定 LCA / DSH / OS 与制品版本、功能场景、失败或未测、配置要求、最后复核时间。
- **来源与许可**：作者与仓库、实际分发方、采用内容、许可状态；不要用上游品牌暗示官方背书。

“已验证可用”要求所宣称能力对应的 E1–E6 适用维度有证据，关键问题和目标分发义务已处理；只过源码、安装或合成场景就按实际范围标记。没有第三方代码隔离时，也不能把目录标记包装成安全沙箱保证。

版本、依赖、安装脚本、所需权限、provider、hook、数据结构或宿主契约变化时重新评审受影响项；扩大功能范围重新判定流程等级与许可。保留旧记录，受影响能力在复核前不能沿用旧版本的“已验证”结论。维护人退出则标为无人维护 / 暂停推荐，并保留用户产物与历史。

统计兼容数量时固定样本分母与版本：原样通过、适配通过、组件复用、拒绝、未测分开计数；一项检索组件成功不折算为原插件整包兼容。当前五项源码研究以及先前的入口 / 合成包测试，均不能转换为已兼容的第三方插件数。
