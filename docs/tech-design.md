## 2. 进程与模块

```
主进程（Node）
├─ harness        任务执行：循环、步数上限、取消、重试、去重
├─ model          OpenAI 兼容客户端，流式 + 工具调用
├─ tools          内置工具（IMAP、资料处理、番茄钟、记事本……）
├─ mcp            MCP 客户端，按用户配置连接外部 server
├─ scheduler      唯一的调度器：工作 / 自主生活 / 主动交流三类事件
├─ store          SQLite 读写与迁移
└─ backup         导出、校验、恢复
预加载（contextBridge，只暴露白名单 IPC）
渲染进程（React）  立绘与场景、对话、任务面板、日记、设置
```

渲染进程开启 contextIsolation，关闭 nodeIntegration。模型密钥、IMAP 密码和外部调用都只在主进程中出现。

调度只有一个入口。工作执行、自主生活推进和主动发言都作为事件交给 scheduler，由它决定谁在跑、是否打扰用户，避免多个循环重复推进同一件事（AGENT.md「主动交流」）。

## 3. Harness

### 3.1 执行循环

- 每个任务一条执行记录：`pending → running → waiting_user → done / failed / cancelled`。
- 单个任务最多 12 步模型调用（默认），超出就停下，报告做到哪一步。
- 用户随时可以取消：AbortController 同时中断模型流和正在进行的工具调用，任务标记为 `cancelled`。
- 用户在任务中插话：插话作为新消息进入当前任务上下文，而不是另开一个任务。
- 去重：同一工具、同样参数在一个任务里调用第 3 次时停止，标记为疑似循环。
- 完成判定以工具结果为准。每次工具调用的参数、结果、耗时都写入 `tool_calls`，作为“做了什么”的证据；模型自述“完成了”不算。

### 3.2 重试策略（按状态分别处理）

| 情况 | 处理 | 上限 | 用尽后 |
| --- | --- | --- | --- |
| 429 限流 | 按响应的 Retry-After 等待；每次新的 429 都重新读取它的值。没有该头时等 5 秒 | 最多重试 3 次 | 停止，任务转 `failed`，界面提示“模型限流”，由用户决定稍后重试 |
| 5xx、网络错误、超时 | 指数退避 1s → 2s → 4s，有 Retry-After 时以它为准 | 最多 3 次，且总等待不超过 30 秒 | 停止，任务转 `failed`，提示服务不可用 |
| 400 / 401 / 403 / 404 | 不重试 | 0 | 直接报错；401/403 提示检查密钥 |
| 流式输出中途断开 | 本轮若已执行过工具，不自动重试，避免重复执行；未执行过工具时按 5xx 规则处理 | 同上 | 同上 |

每一次尝试（时间、状态码、等待时长）都记入日志。IMAP 和 MCP 调用沿用同一张表的 5xx 与 4xx 规则；IMAP 登录失败归入“不重试”，并提示登录失效，而不是当作“没有新邮件”。

### 3.3 运行时预算

- 每天 token 上限（默认 50 万，可在设置中改），工作任务和自主生活分开计数。
- 自主生活的预算单独设上限（默认占总量 20%），用完当天就只做不调用模型的叙事活动。
- 达到上限时停止后台调用并在界面显示，不静默失败。

### 3.4 礼物生成（经 MCP 调用 Rodin）

礼物是 Agent 调用 MCP 工具生成的 3D 物件，绑定一段经历记忆（README“她送的礼物”）。方向由用户于 2026-10-11 确定；以下细节为建议，实现时校正。

- **工具接入**：优先用影眸官方的 Rodin MCP server。官方若没有适合运行时调用的 server，就在赛中自写一个最小的 stdio MCP server 包装 Rodin REST API（提交生成、轮询状态、下载模型）。两种都走本项目的 MCP 客户端。
- **触发**：由 scheduler 根据真实事件提议，例如一项任务以工具证据完成，或用户参与她的小事后有了结果。默认每天最多 1 件，并受 Rodin 额度限制。首版安静陪伴时的自主活动就是“做礼物”。
- **流程**：
  1. 她从经历记忆中选一个物件，写一句给 Rodin 的物件描述和一句赠言。
  2. 调用生成工具，礼物状态记为 `making`。
  3. 后台轮询，拿到模型文件后记为 `ready`。
  4. 在合适的休息时刻送出，记为 `given`。
- **完成判定**：以工具返回的模型文件为准。生成失败或超时就记为 `failed`，她不能说“已经做好了”。
- **隐私**：发给 Rodin 的只有物件描述（如“一只画着樱花的小茶杯，手绘质感”），不含课程、邮件、姓名等个人信息。
- **赠言**：用角色口吻，带 subjective 标记，和日记一样不作为事实来源。
- **展示**：渲染进程用 `<model-viewer>` 显示 GLB。礼物架上每件礼物都能点开查看来源经历。
- **羽毛笔**：第一件礼物。赛中由助手用视频关键图经 Rodin 生成，属于预生成素材，演示中注明。它同时是私人存档在界面上的实体。
- **待实验**：Rodin 的生成耗时与额度，这决定现场演示是实时生成，还是用演示存档里预先生成的礼物；贴图能否保住手绘感。

## 4. 数据模型

所有业务数据都带 `character_id` 和 `user_id`，切换角色或用户不会串用经历。

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| messages | 原始聊天，**永不因压缩而删除** | role、content、created_at、session_id |
| summaries | 上下文压缩产物 | 覆盖的 message 区间、生成时间 |
| memories | 事实与经历 | kind（fact / experience）、source（消息或工具调用 id）、valid_from、superseded_by |
| tasks / task_steps | 任务与步骤状态 | status、等待条件、当前步骤 |
| tool_calls | 执行证据 | 工具名、参数、结果摘要、状态、耗时 |
| campus_items | 校园事项 | 来源、原始截止时间、计划完成时间（分开保存）、状态（candidate / confirmed / changed） |
| world_state | 世界泡 | 当前活动、目标、进展、kind（real_action / narrative / proposal / plan） |
| artifacts | 她产出的真实文件 | 路径、类型、来源任务 |
| diary_entries | 日记 | 引用的消息与事件 id，subjective 标记 |
| notebook | 记事本与灵感 | 内容、关联活动 |
| gifts | 她送的礼物 | 来源记忆 id、物件描述、赠言（subjective）、模型文件路径、状态（making / ready / given / failed）、Rodin 任务 id |

日记带 subjective 标记，不作为事实来源；检索事实时只查 memories 和 tool_calls。

### 上下文压缩

上下文接近模型窗口时，把较早的消息压缩成 summary 放进 prompt，但原始 messages 留在库里。需要细节时按 summary 记录的区间回查原文。这样备份恢复后能取回被压缩掉的内容（见 README「可以带走和恢复共同经历」）。

## 5. 备份与恢复（路演“最后一击”的硬性要求）

- **私人存档** `.lca-save`：zip 包，内含 SQLite 文件快照、artifacts 目录（含礼物模型文件）、manifest.json（格式版本、导出时间、角色与用户 id、每个文件的 SHA-256）。不含任何凭据：密钥和 IMAP 密码不进存档。
- **角色包** `.lca-character`：角色卡、立绘、场景素材和清单。不含聊天、记忆、校园数据。与私人存档分开设计。
- 导出：先用 SQLite 的 backup API 生成一致的快照，再打包。
- 恢复：先校验 manifest 版本和哈希，任一不符就拒绝恢复并说明原因；校验通过后，在恢复前先把当前数据自动备份一份，再替换。
- 存档里只有真实保存过的内容。恢复后的连续性用一条自动化检查验证：恢复前记录的最后一个任务、最后一篇日记、最后一件礼物，在恢复后都能查到。

演示脚本（路演 §11.1 最后一击）：演示中完成真实工作 → 导出存档 → 清空本地数据 → 收尾视频播放 → 视频结束后导入存档 → 让她说出演示中发生过的事。

## 6. 校园能力与 Student Hub

| 场合 | 做法 | 状态 |
| --- | --- | --- |
| 赛中开发与测试 | 把用户已有的 Student Hub 当作一个标准 MCP server 连接，验证本项目的 MCP 客户端和工具调用链路能正确工作 | 已确定 |
| 提交作品与现场演示 | 视情况赛中手写一个最小采集，作为本项目自己的内置工具 | 已确定（视需要） |
| 现场数据来源 | IMAP 只读读取用户的 163 邮箱（赛前准备好演示邮件） | 已确定 |

依据：Student Hub 对本项目而言是一个通用的 MCP 工具集，本项目实现的是通用 MCP 客户端，不内嵌、不复制 Student Hub 代码。

需要注意的边界：

1. 提交版中若仍默认连接 Student Hub，演示时它的能力会被评委看作作品的一部分。建议提交版的演示链路只依赖内置的 IMAP 工具；Student Hub 只作为“用户可以接入任意 MCP 工具”的示例出现，并在路演中如实说明它是作者另一个已有项目。
2. 用 Student Hub 做赛中测试，阅读、修改其代码或接管其运行实例都不在授权范围内（AGENT.md「工作目录与参考项目」）。只把它当外部进程启动和调用。
3. 用户判断（2026-10-11）：Agent 调用 MCP server 属于本项目能力，不再向主办方确认。主办方答复允许使用“赛前已独立存在的原创素材并注明”，Student Hub 据此在说明文档和技术说明中注明为作者赛前已有的项目。

### 6.1 内置最小采集（IMAP）

- 只读：只用 `FETCH`，不移动、不删除、不标记已读（使用 `BODY.PEEK`）。
- 范围：默认只读最近 14 天、指定文件夹，可在设置中调整。
- 演示邮箱：用户的 163 邮箱。开赛后由队友从其他邮箱向它发几封典型的待办事件邮件作为演示数据（演示邮件也算为本作品专门准备的内容）。163 开启 IMAP 需要在设置里申请授权码，赛前完成。
- 流程沿用”证据 → 候选 → 确认 → 安排”：邮件原文是证据；模型提取出候选事项写入 campus_items（状态 candidate）；用户确认后才变成 confirmed 并进入日程。扫描本身不等于用户接受了建议。
- 失败语义：登录失败、网络失败、解析失败分别报告，都不能显示成”没有新邮件”。
- 凭据：需要用户授权，使用邮箱的客户端专用授权码。
