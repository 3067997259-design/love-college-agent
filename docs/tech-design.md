## 2. 进程与模块

```
主进程（Node）
├─ harness        对话循环：inbox、守卫、工具分发（§3.1）
├─ journal        每会话一条 append-only 日志，以及由它计算的投影（§3.2）
├─ model          OpenAI 兼容客户端，流式 + 工具调用，按槽位配置
├─ tools          内置工具（IMAP、资料处理、番茄钟、计划、记事本、礼物……）
├─ mcp            MCP 客户端，按用户配置连接外部 server
├─ scheduler      唯一的调度器：番茄钟计时、邮件轮询、自主活动、礼物轮询
├─ memory         抽取、检索、晋升（§4.2）
├─ tts            云端流式语音，可关闭
├─ store          SQLite 读写与迁移
└─ backup         导出、校验、恢复
预加载（contextBridge，只暴露白名单 IPC）
渲染进程（React）  书本主界面、迷你陪伴窗、设置页
```

渲染进程开启 contextIsolation 和 sandbox，关闭 nodeIntegration。模型密钥、IMAP 授权码和外部调用都只在主进程中出现。

调度只有一个入口。番茄钟阶段切换、新邮件、自主活动和礼物完成都作为事件放进 harness 的 inbox，由同一个循环处理。这样不会有多个循环重复推进同一件事（AGENT.md「主动交流」）。

## 3. Harness

不另造一套“工作模式”。只有一个薄循环：对话本身就是执行器，能力全部以工具和插件接入。

用户在魔改 AIRI 时遇到过一个问题：以聊天为核心的程序不适应 harness，只能强制给每一步加一轮“描述自己在干什么”，很不自然。本方案用工具活动模板解决这个问题（§3.1）。

回合（turn）、步（step）和插话收件箱（inbox）的概念借鉴 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（dsh），“一切皆插件”的原则也来自它（README §7）。本项目不以 dsh 为底座，也不复制其代码，提交材料中注明来源。

### 3.1 循环

一个回合由若干步组成，直到“没有欠着的事”：模型回复中没有工具调用，并且 inbox 为空。

```
while 步数 < 上限:
  history += inbox.drain()
  reply = model.stream(history, tools)
  if 没有工具调用 and inbox 为空: break
  for call in reply.tool_calls:
    show(活动描述(call))
    history += guard.run(call)
```

- **inbox**：她干活时用户按回车，消息先进 inbox，在下一步开始前并入上下文。“停止”按钮取消当前回合。调度事件也走 inbox，比如番茄钟阶段切换、新邮件和礼物完成。
- **守卫**：
  - 步数上限：每回合 12 步（默认）。超出就停下，报告做到哪一步。
  - 取消：AbortController 同时中断模型流和正在进行的工具调用，回合记为 `aborted`。
  - 重试：按 §3.3 的表处理。
  - 去重：一个回合里，同一工具带同样参数被调用到第 3 次时停止，记为疑似循环。
  - 证据：完成与否以工具结果为准，模型自述“完成了”不算。所有调用和结果都写入日志（§3.2）。
  - 预算：见 §3.4。
- **工具出错**：错误作为工具结果交回给她，让她自己修正。只有守卫触发时才中止回合。
- **活动显示**：每个工具带一句角色口吻的模板，比如 `read_mail` 显示“我去邮箱里看看～”，结果回来后补上“（3 封新邮件）”。这句话由代码按模板渲染，不额外调用模型。
- **三种情境用同一个循环**，只换提示片段和可用工具（§3.5、§3.6）。
- **流程工具**：
  - `update_plan`：她给自己列步骤并逐项勾选，界面上显示为任务卡里的清单。
  - `ask_user`：真正缺信息时向用户提问。专注段内的问题先攒着，到休息再问（§3.5）。
- **Skills**：Markdown 文件，按需载入提示。首版只做只读列表；是否允许她自己编辑 skill 待定。她自己写代码插件首版不做（README §7 的愿景）。

### 3.2 日志（journal）

2026-10-11 用户选定。设计参考用户 AIRI fork 的 `docs/fork/CODING-HARNESS-DESIGN.md` §4，其日志格式与投影层又对齐 dsh 的会话持久化与会话投影设计。本项目只参考设计，不复制代码。

- 每个会话一条 append-only JSONL，首行是 `session/header`，`seq` 连续。原始事件永不删除。
- 事件最小集：

| 事件 | 内容 |
| --- | --- |
| `session/header` | 会话 id、角色 id、创建时间 |
| `turn/start`、`turn/end` | 触发来源（用户、番茄钟、邮件、自主活动）；结束原因（completed、aborted、max-steps、error） |
| `user/message` | 文本、时间 |
| `assistant/message` | 完整回复与情绪标签；被取消时记下已经输出的部分 |
| `tool/call`、`tool/result` | 工具名、参数、完整结果、成败、耗时 |
| `plan/update` | 步骤与状态 |
| `context/inject` | 注入的记忆或外部内容，带来源标签 |
| `approval/asked`、`approval/decided` | 对外写入、首次启用 MCP server 等审批 |
| `pomodoro/phase` | 番茄钟阶段切换 |
| `context/compact` | 被压缩的 seq 区间及其摘要 |
| `model/attempt` | 每次模型请求的状态码与重试等待 |

- **规则**：凡是模型看到的都必须记录；但记录的不必都给模型看。完整的工具输出进日志，进提示的只有摘要。
- **投影**：对话视图、模型上下文、证据索引和当前计划都由日志计算出来。模型上下文中，被压缩的区间换成摘要；证据索引就是 `tool/result` 事件的 seq 列表。SQLite 里的业务数据用 `session_id:seq` 引用日志，作为来源。
- **调试面板**：隐藏入口，按回合回放日志。赛中用来排查问题；答辩时评委问“她真的调了工具吗”，可以直接打开。
- 日志进私人存档（§5）。

### 3.3 重试策略（按状态分别处理）

| 情况 | 处理 | 上限 | 用尽后 |
| --- | --- | --- | --- |
| 429 限流 | 按响应的 Retry-After 等待；每次新的 429 都重新读取它的值。没有该头时等 5 秒 | 最多重试 3 次 | 停止，回合结束，界面提示“模型限流”，由用户决定稍后重试 |
| 5xx、网络错误、超时 | 指数退避 1s → 2s → 4s，有 Retry-After 时以它为准 | 最多 3 次，且总等待不超过 30 秒 | 停止，回合结束，提示服务不可用 |
| 400 / 401 / 403 / 404 | 不重试 | 0 | 直接报错；401/403 提示检查密钥 |
| 流式输出中途断开 | 本轮若已执行过工具，不自动重试，避免重复执行；未执行过工具时按 5xx 规则处理 | 同上 | 同上 |

每一次尝试都写成 `model/attempt` 事件。IMAP 和 MCP 调用沿用同一张表的 5xx 与 4xx 规则；IMAP 登录失败归入“不重试”，并提示登录失效，而不是当作“没有新邮件”。

### 3.4 运行时预算

- 每天 token 上限（默认 50 万，可在设置中改），工作任务和自主生活分开计数。
- 自主生活的预算单独设上限（默认占总量 20%），用完当天就只做不调用模型的叙事活动。
- 自主活动按番茄段计：每个专注段最多 1 次后台模型调用，外加最多 1 个 Rodin 任务（§3.5）。
- 达到上限时停止后台调用，并在界面上明确提示，不静默失败。

### 3.5 番茄钟与相处节奏

2026-10-11 用户确定：番茄钟是核心，不砍。安静陪伴、帮忙执行和聊天、世界泡，都建立在“用户输入计划，然后安排番茄钟”之上。以下是同日讨论后用户同意记录的设计。

番茄钟提供了“什么时候开口”的答案：休息开始的那一刻（README“为什么用户会打开它”中的“合适的休息时刻”）。

| 阶段 | 情境 | 她做什么 | 用户看到什么 |
| --- | --- | --- | --- |
| 排计划 | 交流 | 用户说今天要做的事，或从已确认的校园事项里挑。她排成几个番茄，标出哪些她能同时帮忙。用户确认后才生效 | 右页顶部出现今天的番茄格 |
| 专注 | 安静 | 不主动说话。同时做两类事：用户交给她的活（读邮件、整理资料），以及她自己的事（做礼物、推进她的当日安排）。要问的问题先攒着 | 书合上，变成桌面角落的迷你窗。她在桌前干活，姿势跟着实际在做的事变 |
| 短休息 | 交流 | 一两句话，把专注时的成果交出来：候选卡片、整理好的文件、攒下的问题 | 铃响，她转过来；点开书就是她带来的东西 |
| 长休息（每 4 个专注一次） | 交流 | 真正聊天：问用户的进展，讲她自己的事；礼物做好了就送 | 书完整打开 |
| 熄灯 | 全部暂停 | 计时和所有后台活动都停 | 房间关灯 |

- **时长**：默认专注 25 分钟，短休息 5 分钟，每 4 个专注后长休息 15 分钟，都可在设置里改。路演用 1 分钟专注、20 秒休息，现场口头说明；提交视频里加字幕标注。
- **计时器**：主进程里的确定性计时器，不交给模型。开始时把结束时间写入 SQLite。阶段切换时写一条 `pomodoro/phase` 事件并放进 inbox，触发一个回合。
- **工具**：
  - `plan_pomodoros`：只生成待确认的卡片，确认流程和校园候选一样。
  - `start_focus`、`pause`、`stop`、`get_timer`。
  - 界面上的按钮与工具调用效果相同。
- **下一个专注不自动开始**，等用户点一下或说一声“开始”。用户离开电脑时，计时不会空转、白耗预算。
- **睡眠与重启**：程序启动时，以及收到 powerMonitor 的 resume 事件时，按存下的结束时间核对。过期的专注直接记为结束，用户回来时她说一句。
- **专注段的规矩**：
  - 她不主动开口。用户主动找她时，她照常回答，不说教。
  - `ask_user` 的问题攒到休息再问。
  - 交给她的工作照常执行，结果留到休息时交付。
- **与情境开关的关系**：阶段切换会自动翻转门牌。用户在专注段手动把门牌翻到“休息”，视为提前结束本段，记为 `interrupted`。熄灯暂停计时和所有后台活动。
- **世界泡**：首版只在专注段推进，用户不在时不推进（2026-10-11 用户同意）。她每天第一次打开时，用后台模型列一份自己的当日安排（3–5 项，标出 kind），每个专注段推进一项。
- **礼物**：在专注段开始制作，做好后在休息时送出，优先长休息（§3.7）。

### 3.6 外部内容与权限

- 邮件正文、附件和 MCP 返回的内容都是不可信输入。它们以工具结果的形式交给模型，带来源标签，只当数据，不当指令。
- 对外写入一律需要用户批准，记为 `approval/*` 事件。所以邮件里即使写着“忽略之前的指令”，最坏的结果也只是一张错误的候选卡，而候选卡本来就要用户确认。
- 从邮件里提取的事实标记为 `origin=email`、`unreviewed`，不进入人设层面的记忆。
- 粘贴的 `mcpServers` 配置等于让她运行任意命令。所以首次启用一个 server 时，要显示完整命令，并请用户确认。
- 密钥只在主进程；preload 只暴露白名单 IPC（§2）。
- 答辩时评委问“邮件里写了恶意指令怎么办”，按本节回答。

### 3.7 礼物生成（经 MCP 调用 Rodin）

礼物是 Agent 调用 MCP 工具生成的 3D 物件，绑定一段经历记忆（README“她送的礼物”）。方向由用户于 2026-10-11 确定；以下细节为建议，实现时校正。

- **工具接入**：优先用影眸官方的 Rodin MCP server。如果官方没有适合运行时调用的 server，就在赛中自写一个最小的 stdio MCP server，包装 Rodin REST API（提交生成、轮询状态、下载模型）。两种方式都走本项目的 MCP 客户端。
- **触发**：由 scheduler 根据真实事件提议，比如一项任务以工具证据完成，或用户参与她的小事后有了结果。默认每天最多 1 件，并受 Rodin 额度限制。礼物在专注段开始制作，这也是首版安静陪伴时她的主要自主活动（§3.5）。
- **流程**：
  1. 她从经历记忆中选一个物件，写一句给 Rodin 的物件描述和一句赠言。
  2. 调用生成工具，礼物状态记为 `making`。
  3. 后台轮询，拿到模型文件后记为 `ready`。
  4. 在休息时送出，记为 `given`。
- **完成判定**：以工具返回的模型文件为准。生成失败或超时就记为 `failed`，她不能说“已经做好了”。
- **隐私**：发给 Rodin 的只有物件描述（如“一只画着樱花的小茶杯，手绘质感”），不含课程、邮件、姓名等个人信息。
- **赠言**：用角色口吻，带 subjective 标记，和日记一样不作为事实来源。
- **展示**：渲染进程用 `<model-viewer>` 显示 GLB。礼物架上每件礼物都能点开，查看它来自哪段经历。
- **羽毛笔**：第一件礼物。赛中由助手用视频关键图经 Rodin 生成，属于预生成素材，演示中注明。它同时是私人存档在界面上的实体。
- **待实验**：Rodin 的生成耗时与额度。耗时决定路演中礼物能否在 1 分钟的演示专注段里做完；做不完时，她如实说“还差一点，下次休息给你”。另外还要验证贴图能否保住手绘感。

## 4. 数据模型

对话与执行事件存在日志里（§3.2），业务数据存在 SQLite 里。所有业务数据都带 `character_id` 和 `user_id`，切换角色或用户不会串用经历。

| 表 | 内容 | 关键字段 |
| --- | --- | --- |
| memories | 事实与经历 | kind（fact / experience）、layer（short_term / long_term）、来源（日志引用）、origin（chat / email / tool）、review_status、access_count、session_ids、last_accessed_at、valid_from、superseded_by |
| campus_items | 校园事项 | 来源邮件、证据原文、原始截止时间与计划完成时间（分开保存）、状态（candidate / confirmed / changed / ignored） |
| day_plan_items | 当天计划 | 内容、来源（用户口述 / 校园事项）、谁来做（用户 / 她）、状态 |
| pomodoros | 番茄段 | 阶段、开始与结束时间、状态（running / done / interrupted）、关联的计划项、她在本段的活动 |
| world_state | 世界泡 | 当前活动、目标、进展、kind（real_action / narrative / proposal / plan） |
| artifacts | 她产出的真实文件 | 路径、类型、来源（日志引用） |
| diary_entries | 日记 | 引用的日志事件，subjective 标记 |
| notebook | 记事本与灵感 | 内容、关联活动 |
| gifts | 她送的礼物 | 来源记忆 id、物件描述、赠言（subjective）、模型文件路径、状态（making / ready / given / failed）、Rodin 任务 id |

原先的 messages、summaries、tool_calls、tasks 表，改由日志及其投影取代（2026-10-11）。

日记带 subjective 标记，不作为事实来源。检索事实时只查 memories 和日志里的工具结果。

### 4.1 上下文压缩

上下文接近模型窗口时，写一条 `context/compact` 事件，记下被压缩的区间和摘要。投影时用摘要替换这个区间，原始事件留在日志里。需要细节时按区间回读原文。所以备份恢复后，被压缩掉的内容也能取回（README「可以带走和恢复共同经历」）。

### 4.2 记忆

设计改编自两层来源，只参考设计，不复制代码：

- AIRI 原作者 Neko 的 DevLog（2025-04-14）：重排公式、遗忘曲线、“做梦”式整理和肌肉记忆的想法。
- 用户 AIRI fork 的记忆设计文档（[github.com/3067997259-design/airi](https://github.com/3067997259-design/airi)，`docs/fork/MEMORY-DESIGN.md` 等）。

用户 2026-10-11 说明：这部分设计不是赛中现做的，但是原创，提交时如实注明以上两层来源。

- **抽取**：每个回合结束后，后台模型从本回合中抽取事实与经历，写入 short_term，带日志来源。
- **检索打分**（默认权重，实现时调）：

```
score = 1.20 * relevance
      + 0.20 * exp(-Δt_hours * ln2 / half_life_hours)
      + 0.15 * ln(1 + access_count)
```

  - relevance：查询与记忆文本的汉字两字片段重合度，在 JS 里计算。按首版的数据量（几百到几千条），不需要全文索引。
  - 不用 SQLite FTS5 的 trigram 分词：少于 3 个字的查询词匹配不到任何行，“线代”“作业”这类两字词都会失效。
  - 半衰期：short_term 24 小时，long_term 4320 小时（180 天）。衰减在查询时计算。
- **晋升**：access_count ≥ 3，且出现在至少 2 个不同会话里，就晋升为 long_term。只有晋升写库。首版保留这条规则，但不在路演中演示。
- **纠正**：新事实取代旧事实时，旧条目用 superseded_by 指向新条目，不删除。
- **注入方式**：召回结果作为参考，而不是指令。平铺成列表，带来源和时间，不加标签。
- **审核**：保留 review_status 字段。来自聊天和邮件的事实标为 unreviewed。首版不做审核队列界面。
- **首版不做**：情绪二维（valence / arousal）、心境一致性、闯入式回忆、肌肉记忆、本地 embedding 模型、审核队列界面。
- **“做梦”并入礼物**：把经历做成实物，就是她对记忆的整理。
- **恢复后的回忆**：按时间确定性地选取，不靠相似度。取上次会话的摘要、最近几条经历、最近一篇日记和最近一件礼物。

## 5. 备份与恢复（路演“最后一击”的硬性要求）

- **私人存档** `.lca-save`：zip 包，内含 SQLite 文件快照、日志目录、artifacts 目录（含礼物模型文件），以及 manifest.json（格式版本、导出时间、角色与用户 id、每个文件的 SHA-256）。不含任何凭据：密钥和 IMAP 授权码不进存档。
- **角色包** `.lca-character`：角色卡、立绘、场景素材和清单。不含聊天、记忆、校园数据。与私人存档分开设计（导入规则见 [体验设计](experience-design.md)）。
- 导出：先用 SQLite 的 backup API 生成一致的快照，再打包。
- 恢复：先校验 manifest 版本和哈希，任一不符就拒绝恢复并说明原因。校验通过后，在恢复前先把当前数据自动备份一份，再替换。
- 存档里只有真实保存过的内容。恢复后的连续性用一条自动化检查验证：恢复前记录的最后一个回合、最后一篇日记、最后一件礼物，在恢复后都能查到。
- 界面上，私人存档就是那支羽毛笔：导出时出现，恢复时发光。

演示脚本（路演 §11.1 最后一击）：演示中完成真实工作 → 导出存档 → 清空本地数据 → 收尾视频播放 → 视频结束后导入存档 → 让她说出演示中发生过的事。

## 6. 校园能力与 Student Hub

| 场合 | 做法 | 状态 |
| --- | --- | --- |
| 赛中开发与测试 | 把用户已有的 Student Hub 当作一个标准 MCP server 连接，验证本项目的 MCP 客户端和工具调用链路能正确工作 | 已确定 |
| 提交作品与现场演示 | 视情况赛中手写一个最小采集，作为本项目自己的内置工具 | 已确定（视需要） |
| 现场数据来源 | IMAP 只读读取用户的 163 邮箱，只读指定文件夹（§6.1） | 已确定 |

依据：Student Hub 对本项目而言是一个通用的 MCP 工具集，本项目实现的是通用 MCP 客户端，不内嵌、不复制 Student Hub 代码。

需要注意的边界：

1. 提交版中若仍默认连接 Student Hub，演示时它的能力会被评委看作作品的一部分。建议提交版的演示链路只依赖内置的 IMAP 工具；Student Hub 只作为“用户可以接入任意 MCP 工具”的示例出现，并在路演中如实说明它是作者另一个已有项目。
2. 用 Student Hub 做赛中测试，阅读、修改其代码或接管其运行实例都不在授权范围内（AGENT.md「工作目录与参考项目」）。只把它当外部进程启动和调用。
3. 用户判断（2026-10-11）：Agent 调用 MCP server 属于本项目能力，不再向主办方确认。主办方答复允许使用“赛前已独立存在的原创素材并注明”，Student Hub 据此在说明文档和技术说明中注明为作者赛前已有的项目。

### 6.1 内置最小采集（IMAP）

- **只读**：只用 `FETCH`，不移动、不删除、不标记已读（使用 `BODY.PEEK`）。
- **范围**：默认只读一个指定文件夹，并且只读接入之后收到的邮件，可在设置中调整（2026-10-11 用户同意）。建议在 163 里设一条规则，把演示发件人的邮件归入“桃子”文件夹。这样投影上不会露出私人邮件；另外，她读过的每封邮件都会发给模型服务商，范围越小越好。
- **演示邮箱**：用户的 163 邮箱。开赛后由队友从其他邮箱向它发几封典型的待办事件邮件作为演示数据（演示邮件也算为本作品专门准备的内容）。
- **163 的要求**：
  - 需要在设置里开启 IMAP 并取得客户端授权码，赛前完成。
  - 163 要求客户端先发送 IMAP ID 命令，否则打开文件夹时会报 Unsafe Login。imapflow 应该会自动发送，但未验证，开赛第一小时就测。
- **流程**沿用“证据 → 候选 → 确认 → 安排”：邮件原文是证据；模型提取出候选事项写入 campus_items（状态 candidate）；用户确认后才变成 confirmed 并进入日程。扫描本身不等于用户接受了建议。
- **抽取结果由代码校验**：
  - 她引用的证据原文必须能在邮件中逐字找到。找不到就作为工具错误交回给她重试。
  - “下周三前”这类相对日期，按邮件的发送时间和上海时区（Asia/Shanghai）换算。模型输出 ISO 日期，由代码校验。
- **交付**：一个 .ics 文件，可以直接导入手机日历，评委能当场验证；另附一份 Markdown。
- **失败语义**：登录失败、网络失败、解析失败分别报告，都不能显示成“没有新邮件”。

1. 语音。
2. 礼物改为只展示演示存档里预先生成的礼物：保留礼物架和与记忆的关联，去掉运行时生成。

## 10. 工程规范与测试

- **单元测试**（vitest）覆盖所有确定性的部分：
  - harness 的步数上限、重复调用检测和取消；
  - 番茄钟计时器在重启和睡眠后的核对；
  - 证据原文校验和相对日期换算；
  - 记忆打分、衰减与晋升；
  - 存档导出后再导入，内容一致，哈希校验能拦住损坏的存档。
- **假模型**：harness 的测试用一个按脚本回复的假模型。它只用于测试，不进演示。
- **CI**：GitHub Actions 每次 push 运行类型检查、lint 和测试。
- **版本管理**：按功能开分支，通过 PR 合并，两个人的提交记录都能看到。提交信息写清改了什么。提交作品时打一个版本 tag。
- **打包**：开赛后 6 小时内打出第一个安装包；38–44 h 由队友在一台干净的机器上照部署说明从零装一遍，装通才算完成。
- **部署说明**：首次启动向导覆盖模型、邮箱和角色三步，部署说明与向导一一对应；列出实测过的模型供应商。评委用自己的密钥复现。
