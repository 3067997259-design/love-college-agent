## 2. 进程与模块

```
主进程（Node）
├─ harness        对话循环：inbox、守卫、工具分发（§3.1）
├─ journal        每会话一条 append-only 日志，以及由它计算的投影（§3.2）
├─ model          OpenAI 兼容客户端，流式 + 工具调用，按用途配置（§3.15）
├─ tools          内置工具（IMAP、资料处理、番茄钟、计划、记事本、礼物……）
├─ mcp            MCP 客户端，按用户配置连接外部 server
├─ scheduler      唯一的调度器：番茄钟计时、邮件轮询、自主活动、礼物轮询
├─ clock          统一时钟：所有时间和定时器都从这里拿，调试时可冻结、拨动、加速（§3.17）
├─ debug          开发者模式：调试用的 MCP、假依赖、场景存档，只在打开时加载（§3.17）
├─ memory         抽取、检索、晋升（§4.2）
├─ tts            云端流式语音，可关闭
├─ store          SQLite 读写与迁移
└─ backup         导出、校验、恢复
预加载（contextBridge，只暴露白名单 IPC）
渲染进程（React）  书本主界面、迷你陪伴窗、设置页
```

渲染进程开启 contextIsolation 和 sandbox，关闭 nodeIntegration。模型密钥、IMAP 授权码和外部调用都只在主进程中出现。

调度只有一个入口。番茄钟阶段切换、新邮件、自主活动和礼物完成都作为事件放进 harness 的 inbox，由同一个循环处理。这样不会有多个循环重复推进同一件事（AGENTS.md「主动交流」）。

## 3. Harness

循环只有一套：对话本身就是执行器，能力全部以插件接入（§3.13）。2026-10-13 用户修订：在同一套循环之上另设“心流模式”（§3.11），承载多步的工作和编码。两种模式的区别在上下文策略、插件组合和界面，不在循环代码。原先“不另造一套工作模式”的说法改为这个意思。

用户在魔改 AIRI 时遇到过一个问题：以聊天为核心的程序不适应 harness，只能强制给每一步加一轮“描述自己在干什么”，很不自然。本方案用工具活动模板解决这个问题（§3.1）；多步的工作交给心流模式（§3.11）。

回合（turn）、步（step）和插话收件箱（inbox）的概念借鉴 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)（dsh），“一切皆插件”的原则也来自它（README §7）。本项目不以 dsh 为底座，也不复制其代码，提交材料中注明来源。

### 3.1 循环

一个回合由若干步组成，直到“没有欠着的事”：模型回复中没有工具调用，并且 inbox 为空。

```
while 步数 < 上限:
  history += inbox.drain()
  reply = model.stream(history, tools)
  if 没有工具调用 and inbox 为空: break
  for call in reply.tool_calls:
    show(活动描述(call))
    history += guard.run(call)
```

- **inbox**：她干活时用户按回车，消息先进 inbox，在下一步开始前并入上下文。“停止”按钮取消当前回合。调度事件也走 inbox，比如番茄钟阶段切换、新邮件和礼物完成。
- **守卫**：
  - 步数上限：每回合 12 步（默认）。超出就停下，报告做到哪一步。
  - 取消：AbortController 同时中断模型流和正在进行的工具调用，回合记为 `aborted`。
  - 重试：按 §3.3 的表处理。
  - 去重：一个回合里，同一工具带同样参数被调用到第 3 次时停止，记为疑似循环。
  - 证据：完成与否以工具结果为准，模型自述“完成了”不算。所有调用和结果都写入日志（§3.2）。
  - 预算：见 §3.4。
  - 参数校验：工具参数必须能解析成一个 JSON 对象，否则作为工具错误交回给她，并提醒她一次只调用一个工具。中转站在流式模式下会把多个并行调用的参数拼进同一个调用（§8 实测），这一条负责兜底。
- **工具出错**：错误作为工具结果交回给她，让她自己修正。只有守卫触发时才中止回合。
- **活动显示**：每个工具带一句角色口吻的模板，比如 `read_mail` 显示“我去邮箱里看看～”，结果回来后补上“（3 封新邮件）”。这句话由代码按模板渲染，不额外调用模型。
- **三种情境用同一个循环**，只换提示片段和可用工具（§3.5、§3.6）。
- **流程工具**：
  - `update_plan`：她给自己列步骤并逐项勾选，界面上显示为任务卡里的清单。
  - `ask_user`：真正缺信息时向用户提问。专注段内的问题先攒着，到休息再问（§3.5）。
- **Skills**：Markdown 文件，按需载入提示。首版只做只读列表，预设插件附带官方 skill（比如编码，见 §1）；是否允许她自己编辑 skill 待定。她自己写代码插件首版不做（README §7 的愿景）。

### 3.2 日志（journal）

2026-10-11 用户选定。设计参考用户 AIRI fork 的 `docs/fork/CODING-HARNESS-DESIGN.md` §4，其日志格式与投影层又对齐 dsh 的会话持久化与会话投影设计。本项目只参考设计，不复制代码。

- 每个会话一条 append-only JSONL，首行是 `session/header`，`seq` 连续。原始事件永不删除。一天就是一个会话（2026-10-13，§4.1）。
- 事件最小集：

| 事件 | 内容 |
| --- | --- |
| `session/header` | 会话 id、角色 id、创建时间 |
| `turn/start`、`turn/end` | 触发来源（用户、番茄钟、邮件、自主活动）；结束原因（completed、aborted、max-steps、error） |
| `user/message` | 文本、时间 |
| `assistant/message` | 完整回复与情绪标签；被取消时记下已经输出的部分 |
| `tool/call`、`tool/result` | 工具名、参数、完整结果、成败、耗时 |
| `plan/update` | 步骤与状态 |
| `context/inject` | 注入的记忆或外部内容，带来源标签 |
| `approval/asked`、`approval/decided` | 对外写入、首次启用 MCP server 等审批 |
| `pomodoro/phase` | 番茄钟阶段切换 |
| `context/compact` | 被压缩的 seq 区间及其摘要 |
| `model/attempt` | 每次模型请求的状态码与重试等待 |

- **规则**：凡是模型看到的都必须记录；但记录的不必都给模型看。完整的工具输出进日志，进提示的只有摘要。
- **投影**：对话视图、模型上下文、证据索引和当前计划都由日志计算出来。模型上下文中，被压缩的区间换成摘要；证据索引就是 `tool/result` 事件的 seq 列表。SQLite 里的业务数据用 `session_id:seq` 引用日志，作为来源。
- **调试面板**：隐藏入口，按回合回放日志。赛中用来排查问题；答辩时评委问“她真的调了工具吗”，可以直接打开。
- 日志进私人存档（§5）。

### 3.3 重试策略（按状态分别处理）

| 情况 | 处理 | 上限 | 用尽后 |
| --- | --- | --- | --- |
| 429 限流 | 按响应的 Retry-After 等待；每次新的 429 都重新读取它的值。没有该头时等 5 秒 | 最多重试 3 次 | 切到备用通道；都失败就按“上游繁忙”提示（§3.9） |
| 5xx、网络错误、超时 | 指数退避 1s → 2s → 4s，有 Retry-After 时以它为准。同一个模型连续两次 503，直接切备用通道，不等满 | 最多 3 次，且总等待不超过 30 秒 | 同上；本机断网按“网络”提示 |
| 400 / 401 / 403 / 404 | 不重试；主通道记为配置有问题，切到备用通道 | 0 | 按“配置错误”提示 |
| 流式输出中途断开 | 本轮若已执行过工具，不自动重试，避免重复执行；未执行过工具时按 5xx 规则处理 | 同上 | 按“说到一半断了”提示 |

流式请求发出后 30 秒内一个字节都没收到，按网络超时处理（§8 实测出现过一次挂起）。每一次尝试都写成 `model/attempt` 事件，记下用的是哪个通道、哪个模型。IMAP 和 MCP 调用沿用同一张表的 5xx 与 4xx 规则；IMAP 登录失败归入“不重试”，并提示登录失效，而不是当作“没有新邮件”。

**状态码不可靠**（§8，2026-10-12 实测）：这个中转站对不存在的模型返回 503，看起来和上游宕机一样；密钥错误返回 401，正文也不是 OpenAI 的标准格式。所以不能只按状态码分类，判断方法见 §3.9。用户最终看到什么，也统一由 §3.9 决定，本表只管重试和切换。

### 3.4 运行时预算

- 每天 token 上限（默认 50 万，可在设置中改），工作任务和自主生活分开计数。
- 自主生活的预算单独设上限（默认占总量 20%），用完当天就只做不调用模型的叙事活动。
- 自主活动按她的安排项计：每一项最多 1 次后台模型调用；Rodin 任务按礼物的上限，每天最多 1 个（§3.7）。外出本身不调用模型（§3.14）。2026-10-13 起不再按专注段计，因为她的生活不再只在专注段里推进。
- 达到上限时停止后台调用，并在界面上明确提示，不静默失败。

### 3.5 番茄钟与相处节奏

2026-10-11 用户确定：番茄钟是核心，不砍。安静陪伴、帮忙执行和聊天、世界泡，都建立在“用户输入计划，然后安排番茄钟”之上。以下是同日讨论后用户同意记录的设计。

2026-10-13 用户补充了它为什么是核心：她的作息要配合她的用户。用户工作而不需要她配合时，她忙自己的事；用户休息时，她也休息，陪用户聊天；心流模式另算。番茄钟是把用户的作息精确到分钟的那一层；整天的作息、外出和离线期间怎么算，见 §3.14。

番茄钟提供了“什么时候开口”的答案：休息开始的那一刻（README“为什么用户会打开它”中的“合适的休息时刻”）。

| 阶段 | 情境 | 她做什么 | 用户看到什么 |
| --- | --- | --- | --- |
| 排计划 | 交流 | 每天第一次打开时，她先拿出一份草案：昨天没做完的，加上今天到期的已确认事项。用户也可以自己说今天要做的事，或从已确认的校园事项里挑。她排成几个番茄，标出哪些她能同时帮忙。用户确认后才生效 | 右页顶部出现今天的番茄格 |
| 专注 | 安静 | 不主动说话。同时做两类事：用户交给她的活（读邮件、整理资料），以及她自己的事（做礼物、推进她的当日安排）。要问的问题先攒着 | 书合上，变成桌面角落的迷你窗。她在桌前干活，姿势跟着实际在做的事变 |
| 短休息 | 交流 | 一两句话，把专注时的成果交出来：候选卡片、整理好的文件、攒下的问题 | 铃响，她转过来；点开书就是她带来的东西 |
| 长休息（每 4 个专注一次） | 交流 | 真正聊天：问用户的进展，讲她自己的事；礼物做好了就送 | 书完整打开 |
| 熄灯 | 全部暂停 | 计时和所有后台活动都停 | 房间关灯 |

- **时长**：默认专注 25 分钟，短休息 5 分钟，每 4 个专注后长休息 15 分钟，都可在设置里改。路演用 1 分钟专注、20 秒休息，现场口头说明；提交视频里加字幕标注。
- **计时器**：主进程里的确定性计时器，不交给模型。开始时把结束时间写入 SQLite。阶段切换时写一条 `pomodoro/phase` 事件并放进 inbox，触发一个回合。
- **工具**：
  - `plan_pomodoros`：只生成待确认的卡片，确认流程和校园候选一样。
  - `start_focus`、`pause`、`stop`、`get_timer`。
  - 界面上的按钮与工具调用效果相同。
- **每天第一次打开**（2026-10-13 用户同意）：有事才开口，比如夜里到的急件和候选卡、今天到期的事项、她刚外出回来，以及上面那份排计划的草案；没事就只抬头看一眼。
- **下一个专注不自动开始**，等用户点一下或说一声“开始”。用户离开电脑时，计时不会空转、白耗预算。
- **睡眠与重启**：程序启动时，以及收到 powerMonitor 的 resume 事件时，按存下的结束时间核对。过期的专注直接记为结束，用户回来时她说一句。恢复存档不走这条核对，见 §3.14 第 6 条。
- **专注段的规矩**：
  - 她不主动开口。用户主动找她时，她照常回答，不说教。
  - `ask_user` 的问题攒到休息再问。
  - 交给她的工作照常执行，结果留到休息时交付。
- **与情境开关的关系**：阶段切换会自动翻转门牌。用户在专注段手动把门牌翻到“休息”，视为提前结束本段，记为 `interrupted`。熄灯暂停计时和所有后台活动。
- **世界泡**：2026-10-11 曾定为只在专注段推进、用户不在时不推进。2026-10-13 用户改为按真实时间推进：专注段里她照样做自己的事、推进当日安排，用户离开时她也有自己的生活（§3.14）。
- **礼物**：在专注段开始制作，做好后在休息时送出。当天后面还有长休息（按 §3.14 的作息看）就等长休息，没有就在下一次休息送（§3.7）。

### 3.6 外部内容与权限

- 邮件正文、附件和 MCP 返回的内容都是不可信输入。它们以工具结果的形式交给模型，带来源标签，只当数据，不当指令。
- 对外写入一律需要用户批准，记为 `approval/*` 事件。所以邮件里即使写着“忽略之前的指令”，最坏的结果也只是一张错误的候选卡，而候选卡本来就要用户确认。
- 从邮件里提取的事实标记为 `origin=email`、`unreviewed`，不进入人设层面的记忆。
- 粘贴的 `mcpServers` 配置等于让她运行任意命令。所以首次启用一个 server 时，要显示完整命令，并请用户确认。
- 密钥只在主进程；preload 只暴露白名单 IPC（§2）。
- 答辩时评委问“邮件里写了恶意指令怎么办”，按本节回答。
- **隐私模型**（2026-10-13）：标了“可能处理隐私数据”的插件，原文先交给一个没有工具的隐私模型，她只拿到校验过的字段，见 §3.15。
- **待定（2026-10-12）**：她一旦能运行代码（§1），“最坏只是一张错误的候选卡”这个说法就要重写。用户计划用成熟的沙箱和自动审核机制，把风险控制在不高于市面上主流 harness 的水平，并对传统 Agent 做针对性的调整，具体方案由用户在赛中给出，§3.15 的隐私模型可以作为其中一块。届时同步改写本节和答辩卡里的对应题目，并定好展位模式下是否开放运行代码。

### 3.7 礼物生成（经 MCP 调用 Rodin）

礼物是 Agent 调用 MCP 工具生成的 3D 物件，绑定一段经历记忆（README“她送的礼物”）。方向由用户于 2026-10-11 确定；以下细节为建议，实现时校正。

- **工具接入**（2026-10-11 更新）：影眸有官方的 MCP server（服务名 hyper3d，Streamable HTTP，地址 `https://api.hyper3d.com/api/mcp`），但用 OAuth 授权。本项目的 MCP 客户端原计划只做 stdio；要接官方 server，就得加上 Streamable HTTP 传输和一套 OAuth 流程（打开浏览器授权、保存和刷新令牌），工作量和现场风险都更大。
  - 建议的主路径：赛中自写一个最小的 stdio MCP server，用 API key 包装 REST 接口（提交、轮询、下载），约 1–2 小时。
  - 有余力再接官方 server。
  - 两种方式都走本项目的 MCP 客户端。
- **触发**：由 scheduler 根据真实事件提议，比如一项任务以工具证据完成，或用户参与她的小事后有了结果。默认每天最多 1 件，并受 Rodin 额度限制。礼物在专注段开始制作，这也是首版安静陪伴时她的主要自主活动（§3.5）。
- **流程**：
  1. 她从经历记忆中选一个物件，写一句给 Rodin 的物件描述和一句赠言。
  2. 调用生成工具，礼物状态记为 `making`。
  3. 后台轮询，拿到模型文件后记为 `ready`。
  4. 在休息时送出，记为 `given`。当天后面还有长休息就等它，没有就在下一次休息送，免得新用户做不满 4 个番茄，礼物一直等着（2026-10-13）。
- **完成判定**：以工具返回的模型文件为准。生成失败或超时就记为 `failed`，她不能说“已经做好了”。失败怎么说、之后怎么排，见 §3.9 第 2 条。
- **隐私**：发给 Rodin 的只有物件描述（如“一只画着樱花的小茶杯，手绘质感”），不含课程、邮件、姓名等个人信息。
- **赠言**：用角色口吻，带 subjective 标记，和日记一样不作为事实来源。
- **展示**：渲染进程用 `<model-viewer>` 显示 GLB。礼物架上每件礼物都能点开，查看它来自哪段经历。
- **羽毛笔**：第一件礼物。赛中由助手用视频关键图经 Rodin 生成，属于预生成素材，演示中注明。它同时是私人存档在界面上的实体。
  - **每个用户的第一件礼物都是它**（2026-10-13 用户同意）：第一件真事（一项任务以工具证据完成）之后的那次休息，她把笔送给用户，意思是以后想带她走，就用这支笔。台词赛中写。
  - 导出存档的入口就在这支笔上；设置页里的导出一直都在，没拿到笔也能导出。
  - 它不依赖 Rodin，所有用户都有，也不用等生成。备份功能借一件礼物让用户发现，对应片子第 13 镜赠笔、第 18 镜颜色从笔尖晕开。
  - 在礼物表里记为一件预制礼物，来源记忆就是那件真事。
- **没配 Rodin**（2026-10-13，用户原本就倾向这样，助手同意）：除了羽毛笔，没有别的礼物；工作台保持线稿，配好了她才上色（体验设计 §7.1）。
  - 助手提过手写卡片，不做，因为和日记冲突：两者都是她写同一段经历，内容重复，两次写的主观感受还可能对不上；片子也把“她写的东西交到你手里”留到第 19 镜递日记，平时就送卡片，会提前用掉这一下。
  - 没配 Rodin 的用户，关系反馈靠书桌上越摆越多的东西（§3.14）。
- **实测**（2026-10-11，用文字生成一个无关物件，`Gen-2.5-Low`、`Raw`、`glb`）：提交后约 83 秒完成，扣 0.5 额度。一次提交分成 6 个子任务依次完成，第一个约 17 秒完成。返回一个约 23.6 MB 的 GLB 和一张 `preview.webp` 预览图。由此：
  - 演示用的 1 分钟专注加 20 秒休息，刚好卡在边上。礼物要在专注一开始就提交；赶不上时她如实说“还差一点，下次休息给你”。是否把演示专注延长到 1 分 30 秒，用掉一部分路演余量，待用户定。
  - 一件 23.6 MB 太大，礼物架加载慢，存档也会越积越大。赛中试低一档的质量或贴图设置，把单件压到几 MB；预览图可以直接当礼物架的缩略图。
  - 贴图能不能保住手绘感，仍待实验。

### 3.8 展位：经 MCP 和她一起玩 Minecraft

2026-10-11 用户提出：展位上让同学拿键盘和她一起玩一会儿 MC。节目效果接近 Neuro-sama，也让 Agent 类项目在展位上有了一个能反复玩的短互动。以下除注明的以外都是建议。

- **摆法**（用户确定）：同学和她各开一个客户端，进同一个本地世界，都在展位那台电脑上跑。另一台电脑放宣传片。
- **账号**：用户已于 2026-10-11 购买正版账号，同学用的客户端用它登录。她的客户端相当于机器人，在本地世界里用离线名。
- **来源**：mcpfabric 是 MIT 许可的开源 Fabric mod（上游版权 dabinayo），用户赛前做了魔改（`github.com/3067997259-design/mcpfabric`）。它本身是标准的 MCP server，本项目只通过 MCP 配置接入，不复制代码。
  - 开赛前在 mcpfabric 仓库打一个标签，固定展位用的版本。
  - 赛中如果为展位改它，那部分属于赛中为作品做的工作，要另行说明。
- **安全**：
  - 展位上关掉 `enableCommands` 和 `enableWorldWrite`。这座桥有管理员级权限，同学可能会哄她执行命令或拆地图。
  - 桥只监听 127.0.0.1；token 放进加密的设置里，不进仓库。
  - 首次启用时照常显示完整命令，请人确认（§3.6）。
- **工具与守卫**：
  - 50 多个工具不全给模型，“玩”的情境只开一组：移动、看、寻路、挖、背包、聊天、截图。
  - 这个情境单独设步数上限。
  - 展位当天调高每日预算，并盯着用量。
- **节奏**：只在休息和交流时玩，展位停在长休息；专注段的安静陪伴不变。她的克制和冷面吐槽式的幽默照常保留，话少也正好盖住每个动作等模型回复的延迟。
- **数据**：展位用一套单独的数据，每轮同学玩完就恢复展位存档，和路演用的存档分开。
- **工作量与排期**：赛中要做的是：
  - 一份“陪你玩”的 Markdown skill；
  - 工具子集；
  - 主要工具的活动台词；
  - 展位的数据设置。

  大约 2–3 小时，32–38 h 进度有余才做，不进核心需求。
- **赛前准备**（只是环境）：在展位电脑上装好 Java 21、Fabric、mod 和两个客户端，把本地世界跑通。

### 3.9 出戏防线：出错、拒绝和思维链

2026-10-12 用户与助手讨论后确定。对话中最煞风景的三件事：思维链混进正文、跳出角色的拒绝、把报错原样摆在书页上。模型和屏幕之间设一层，专门决定什么能上屏、以什么样子上屏。

**原则**：她能开口时，失败由她自己说，怎么说由角色卡决定。她开不了口时（模型调用失败），由书本旁白提示，不替她编台词。两种情况下，真实原因都只要点一下就能看到。

**1. 工具失败：交回给她，按角色卡的“工具调用指引”说**

- 工具出错时，错误原样作为工具结果交回给她（§3.1）。交回前遮掉错误信息里可能带出的密钥和授权码。
- **角色卡加一个框：“工具调用指引”**。做法参考 AIRI 的分段注入提示（用户魔改版里，仿照 coding harness 写了简单的工具调用指引）。用户用自然语言写清：哪些工具的失败要如实说，哪些可以按情景改编。比如礼物做失败了，可以说成“手里没有合适的胶水了，抱歉今天没有惊喜啦”。
- **默认值**：
  - 干活的工具（邮件、日程、资料处理、文件）：失败必须如实说。它们的结果关系到用户的现实生活，“邮箱没登上”绝不能说成“邮件都看过了，没什么事”。
  - 故事里的工具（礼物、她自己的活动）：失败可以改编进情节。失败的礼物和活动排进她之后的当日安排，和世界泡接上（§3.5）。
- **“！”按钮由 harness 挂，不靠模型**：一个回合里只要有工具失败，这条消息后面就出现“！”。点开是 harness 记下的原始报错（`tool/result`，遮掉密钥），像 Cherry Studio 那样浮出一个窗口。不要求模型把报错写成 JSON 转述：模型可能抄错或自己编，多花 token，报错经过模型也多一次泄漏密钥的机会。所以不管角色卡怎么写、她说得多委婉，真实情况都能点开看到。诚实的底线由程序保证。
- 同一个工具在一个回合里连续失败 2 次，就不再让她重试（与 §3.1 的去重守卫一致）。需要用户动手的（比如授权码过期），“！”的窗口里附一个“去设置”按钮。

**2. Rodin 是长任务，先区分“还在做”和“失败”**

一件礼物要做 1–2 分钟（§3.7 实测约 83 秒）。任务进行中，她的状态就是“在书桌前做礼物”，scheduler 在后台轮询。轮询超时先悄悄重查几次，不急着判失败；真失败了才交回给她，按指引改编。失败的礼物不自动反复重做（每次都扣 Rodin 额度），而是排进她之后的安排。

**3. 模型调用失败：书本旁白提示，点开看原文**

她开不了口时，消息位置显示一行旁白。旁白是书本在说话，不是桃子在说话，样式也和她的台词分开，并且要和“她在做自己的事”这个正常状态明显区分。点开浮出详情窗口：哪个通道、哪个模型、状态码、返回的原文（遮掉密钥）、发生时间、建议怎么处理。用户发的那句话保留，标成未送达，可以一键重发。

| 类别 | 包括 | 显示旁白之前先做什么 |
| --- | --- | --- |
| 上游繁忙 | 短时 429、5xx、过载、空回复或解析不了的回复 | 悄悄重试，再切备用通道（§3.3）。多数时候用户根本看不到 |
| 配置错误 | 401、密钥没有该模型的权限、模型不存在、地址错误（返回网页而不是 JSON）、参数不被支持、从没成功过的配置 | 不重试。详情窗口给“去设置”按钮 |
| 内容被拦截 | 上游的安全过滤；Claude 接口的 `refusal` 停止原因 | 不重试同一句。旁白不能写成指责用户：过滤有误判 |
| 网络 | 本机断网、代理连不上、超时、连接被重置 | 网络恢复后自动重发 |
| 墨水用完 | 余额不足；周期额度用完（详情里写明何时恢复） | 不重试 |
| 说到一半断了 | 已经上屏半句，流断了 | 未执行过工具时悄悄重试一次；仍失败就保留半句，给一个“让她接着写”的按钮 |

旁白的文案属于产品文案，赛中由用户定稿。讨论中的方向（构思，未定稿）：所有旁白共用书、笔、墨水的意象，和书本界面、片子同一套语言。

**4. 怎么判断是配置错误还是上游的问题**

- **保存设置时体检**：查一遍模型列表，确认密钥有效、模型存在，再发一个极小的请求。启动时和展位布展时也各跑一次。绝大多数配置错误在这一步拦住，不留到聊天的时候。
- **看这套配置成功过没有**：同一套配置之前能用、现在出错，按上游的问题处理；从没成功过，按配置错误处理。这条不依赖中转站返回什么状态码。
- **辅助看报错正文里的关键词**：`invalid key`、`balance`、`quota`、`余额`、`额度`、`not supported` 等。

**5. 预防**

- **备用通道**：主对话槽位可以配多个通道，按顺序切换（比如主模型 → Gemini → 组委会的免费额度）。日志记下每句话是哪个模型回的。隐私模型的调用不走备用通道（§3.15 第 8 条）。
- **余额**：中转站没有标准的余额查询接口（§8）。本地按每次的用量累计扣费，快用完时在设置页提前提醒，不等到聊到一半才断。
- **后台让路**：用户在聊天时，后台任务（记忆抽取、她的当日安排）暂停。后台出错只写日志，永远不出现在对话里。

**6. 思维链不上屏，拒绝不出戏**

- **只显示指定通道的内容**：接口单独返回的思考内容一律不显示；如果主对话用会把思考写进正文的模型，就要求回复放进固定格式（JSON 字段或一对标签），格式以外的内容丢弃，流式时缓冲到标签打开再上屏。上屏前再按常见的泄漏特征检查一次。用 Claude 时可以不开扩展思考，从根上避开这个问题（§8 待测）。
- **长上下文**：长对话用摘要代替原文（§4.1），也降低模型在正文里写出思考内容的概率。
- **拒绝不出戏**：人设里写明，遇到不合适的请求，她用自己的口吻转开或拒绝，不跳出角色讲政策。

### 3.10 内容边界

2026-10-12 讨论，助手建议。本项目不另设道德或法律审查，主要靠模型自身的约束；以下几处模型管不到，或者出了问题代价很大，单独处理。

- **运行时生成图片**：只用自带过滤的托管模型（如 GPT Image、Gemini 的生图模型）。没有审查、能本地部署的模型（如 Qwen 的生图、Minimax 的视频）只用来赛中做素材，由人挑选后才用，不接进产品。开源后用户换成别的模型，由 README 写明默认配置和风险。
- **展位模式**：展位上路过的同学什么都可能输入，屏幕对着评委和人群，用的又是我们自己的密钥（有人发违规内容，被封的是我们的中转站账户）。
  - 系统提示更收敛，提供一键清空对话，必要时只开放几个预设话题入口。
  - 输入先用便宜的小模型分类一次，明显违规的不发给主模型。
  - 用一把单独的演示密钥，余额充足（§3.9 第 4 条的体检在布展时跑）。
- **人设的两条底线**：
  - 官方卡设定为 19 岁（2026-10-12 用户定）。设成未成年，大多数带安全约束的模型会格外在意，反而更不会往不合适的方向推进；设成成年也要写明，不留空。用户换成本地无审查模型、再硬改设定的，和他们自己画图一样，本项目管不了。
  - 拒绝时不出戏（§3.9 第 6 条）。
- **情绪危机**：用户流露出自伤等危机信号时，她可以暂时放下角色，认真回应，并给出心理援助热线。号码赛中核实后再写进人设。

### 3.11 心流模式（heart-flow）

2026-10-13 用户设计。撤销、自动压缩和指令执行，天然和气泡式的对话不兼容。把干活外包给 Codex 一类的 MCP（比如 `codex mcp-server`），harness 就只剩转发，既没法扩展，也接不住人设。所以在同一套循环之上，单独设一个干活的模式。

- **对话只有一条**：不做 AIRI 那样的并行对话窗口。几个窗口同时抽取记忆，会写进互相矛盾的事实；她也不该同时出现在几个地方。心流可以有很多次，但同一时间只有一个（她只有一台电脑）。历次心流留成列表，可以回看、可以接着做；多个任务用 todo 排队。
- **进入**：点电脑，或她提议、用户同意。进入时把对话压缩成摘要，和人设一起冻结成前缀，顺序是：harness 规则与工具定义 → 人设 → 对话摘要。之后不再按轮注入记忆、时间、情绪等会变的内容。前缀稳定，缓存一直命中；工作时也不会忘了人设。
- **期间**：工作过程接在前缀后面。用户在输入框说的话进插话收件箱（§3.1），她在心流里回应。自动压缩只压前缀以下的工作过程，前缀不动。
- **退出**：`/exit`。
  - 对话按自己的日志重新加载原文。进入时的压缩只是临时的投影，不是永久的。
  - 整段心流压缩成一份工作摘要，作为一条事件并入对话，她不会干完活就失忆。
  - 记忆只从工作摘要里抽取，带工具证据，不从几百行命令输出里抽。
- **实现**：对话、心流、摘要，都是同一份日志的不同投影（§3.2、§4.1），不删任何事件。

| 类 | 内容 | 首版 |
| --- | --- | --- |
| 进出 | 进入心流；`/exit` 退出并生成工作摘要 | 做 |
| 计划 | `/plan`：只读探索，先提方案，用户批准了才动手 | 做 |
| 压缩 | `/compact`（可附一句“重点保留什么”）；接近上限时自动压缩 | 做 |
| 撤销 | `/undo`：回到某一步之前（见下） | 做 |
| 状态 | `/status`：模型、上下文用量、审批模式、花了多少钱 | 做 |
| 审批 | `/permissions`：切换审批模式（配置项见体验设计 §7.1） | 做 |
| 查看 | `/diff`：这次心流改了什么 | 做 |
| 初始化 | `/init`：读项目，写一份项目说明 | 有余力 |
| 审查 | `/review`：她审一遍自己的改动 | 有余力 |
| 目标 | `/goal`：跨多次心流追踪的长期目标，可以和世界泡的长期目标合并 | 有余力 |
| 隐私 | `/privacy`：附件和拖进来的文件走隐私模型（§3.15）。普通对话里也能用 | 做 |
| 工具 | `read`、`write`、`edit`（精确替换）、`bash`（带超时）、`glob`、`grep`、`update_todo`、`ask_user` | 做 |
| 工具 | `web_fetch`、看图（截图）、分身（§3.12） | 有余力 |

- **撤销**：`edit`、`write` 改的文件先做快照，可以撤回；工作目录是 git 仓库时，每一步打一个影子提交（仿照 Codex）。`bash` 的副作用（装了包、删了文件、发了请求）撤不回，撤销时要明确告诉用户。对话的撤销追加一条“撤销”事件，不删日志。
- **前台与后台**：
  - 前台：用户看着她做，随时批准。
  - 后台（专注段里）：需要审批的操作先交给自动审查，由另一个模型按规则判断能否放行（仿照 Codex 和 Claude Code 的自动审查）。过不了，就弹 Windows 系统通知，提醒用户去审批。为用户负责优先于不打扰（2026-10-13 用户定）。
- **演示**：演示主线（邮件 → 日程）不走心流，它在对话里几次工具调用就能做完。心流用来展示构建能力（2026-10-13 用户定）。
- **缓存**：冻结前缀能省钱，前提是中转站透传了缓存（§8 待测）。不透传时，冻结前缀仍然能保住人设，只是省不了钱。
- **界面**：右页换成工作视图：计划、命令与输出、diff、审批（体验设计 §2）。左页的她坐在电脑前。

### 3.12 分身（子代理）

2026-10-13 用户提出。意象来自漫画：人忙到分身乏术时，画成同时出现在好几个地方；也像影分身，解除时经历回到本体。漫画的读者都明白这仍是同一个人在忙，所以不破坏“她只有一个”。

- 分身带一个小任务出去，上下文是全新的；做完就消失，只把结论交回本体。
- **记忆只归本体**：分身不写记忆。结论由本体整合，进心流的工作摘要。
- **默认只读**：读、搜、查。改文件和有副作用的命令留给本体，避免两个分身同时改一个文件。
- 用便宜的模型和精简的提示词，不带完整人设。分身的输出显示为进度小卡，只有本体用她自己的口吻说话。
- 同时最多 3 个（默认），防 429，也控制花费。每个分身是独立的请求，不受中转站流式并行调用问题的影响（§8）。
- **画面**：Q 版的桃子，用什么工具就跑到对应的家具旁：书架前翻书是搜索，挤在电脑前是跑命令，蹲在信箱边是读邮件，趴在窗台上是上网。做完冒一团烟消失，手里的纸飞回本体桌上。需要一套 Q 版素材，属于赛中美术。
- **首版**：有余力才做。机制在心流之上约 2–3 小时，动画约 2 小时。

### 3.13 插件标准与 mod 加载器

2026-10-13 用户提出。一般 harness 的插件只能改“怎么干活”；本项目的插件还能改“她怎么在这个世界里干活”。这是 README §7“一切皆插件”的落地，也是片子里“书写者画出零件，桃子接住并自行组装新电脑”的真实对应：装一个插件，铅笔在她屋里画出一件新家具，她来上色。

一个插件可以在四个层面上加东西：

| 层 | 内容 |
| --- | --- |
| 行为 | 工具、指令、skill、MCP server、循环钩子（工具调用前后、番茄钟阶段切换时） |
| 表现 | 家具、表情、短动画、活动台词模板、音效，都绑定在事件上（比如“这个指令执行期间换成这个表情”） |
| 配置 | 一份配置结构的描述，程序自动生成设置面板。点家具弹出的就是它，插件作者不用写界面 |
| 叙事 | 写进系统提示的世界设定（让她知道屋里有这件东西、它是干什么的）；工具调用指引的默认条目（§3.9） |

- **具名槽位**：插件不直接带桃子的图，只声明要用哪个槽位，比如 `expression: proud`、`anim: celebrate`。角色包按命名约定提供；没有的，按体验设计 §8“缺什么回退什么”回退。写功能的人和画角色的人不用互相认识，插件生态和角色生态由此接上。
- **家具的接口**：
  - 三层素材（线稿、简单上色、完整上色），新装的家具也能走“铅笔画出来、她来上色”的流程（体验设计 §7.1）。
  - 可点击的多边形区域，同时是上色的遮罩。
  - 她和分身用这件家具时站在哪里。
  - 房间里的摆放位置。位置有限，要有一套槽位分配，处理两个插件抢同一个角落。
  - 点击后打开哪个配置面板，哪些工具“住在”这里（分身调用这些工具时跑到这里）。
- **地点和带回来的东西**（2026-10-13）：地点和家具一样有三层素材，外加她在这里时用的姿势槽位；带回来的东西是目录条目，每条一张透明底小图加一句事实描述。素材由插件作者自己画、自己花钱（§3.14）。
- **隐私标记**（2026-10-13）：清单里可以声明“可能处理隐私数据”，标了的插件，工具结果先交给隐私模型（§3.15）。建议分两档：“总是”，比如邮件正文，配好隐私模型就过滤；“按需”，比如附件和文件，开了 `/privacy` 才过滤。插件自己声明的标记不能全信，用户可以在设置里按插件、按 MCP server 改；MCP server 没有清单，默认不标。
- **指令的可用范围**（2026-10-13）：指令在清单里声明能在哪里用：只在心流里，或对话和心流都能用。`/privacy` 属于后者（§3.15）。
- **安全底线**：
  - 表现层只收声明：家具、表情、动画只能是 JSON 加图片，插件的代码不进渲染进程，否则一个装饰插件就可能读到密钥。
  - 带代码的插件和 MCP 一样，首次启用时显示它要做什么，请用户确认（§3.6）。只带素材的插件可以直接装。
  - 清单里写 API 版本，加载器检查兼容性（思路同 Fabric 的 `fabric.mod.json`）。
- **首版**：不做插件市场，不开放循环内部的钩子。我们自己的功能全部经加载器装入：信箱是 IMAP 插件（工具、家具、配置面板、失败指引），工作台是 Rodin 插件，电脑是编码插件加官方 skill，心流的指令也是插件。这样接口是真的在用，路演时可以当场打开一个插件的清单。外部插件只支持从一个文件夹加载。清单格式赛中定。

### 3.14 世界泡：作息、外出与带回来的东西

2026-10-13 用户提出。起因：片子里她有四成多的时间在外面（第 10–14 镜，以及第 18 镜后半到第 19 镜），原设计里她却从没出过房间。参照旅行青蛙：她自己决定出门，回来带点东西，摆上自己的书桌。

原先世界泡只在专注段推进，是因为她做自己的事时用户如果不在，那些动画没人看。有了带回来的东西，用户不在时发生的事，回来也看得见。用户的判断：“你专心工作或者离开，而她依然有自己的生活”，本身就是很好的正面反馈。

#### 她的作息跟着用户的作息走

这也是番茄钟成为核心的原因：用户通过计划表或别的方式说明哪些时间工作、哪些时间休息，她的一天跟着排。

| 用户在做什么 | 怎么知道 | 她在做什么 | 她在哪 |
| --- | --- | --- | --- |
| 工作，交给了她活 | 她的任务在跑，或在心流中 | 和用户一起干 | 房间，电脑前 |
| 工作，不需要她 | 专注段；计划或课表上的工作时间 | 自己的事：学习、写东西、做礼物、推进她的当日安排 | 房间，书桌前 |
| 休息 | 短休息、长休息，计划里的空档 | 也休息，陪用户聊天 | 在哪都行 |
| 休息日或大块空闲 | 周末和节假日、当天没有计划、用户说“今天休息” | 可能出门 | 外景 |
| 熄灯 | 用户关的 | 全部暂停 | 房间，关灯 |

- 心流模式另算（§3.11）。心流期间她手上有活，不做自己的事，也不出门。
- **她的当日安排**：每天程序第一次运行时，后台模型按用户当天的作息列 3–5 项，标出 kind。工作日的安排排进用户的工作时间；只有看起来是休息日，才可能排外出。原 §3.5 的“每个专注段推进一项”改为按安排项推进。

#### 防止时间和因果错乱的规则

第 1、4 条用户已同意（2026-10-13），第 2 条来自用户的作息模型；标“建议”的是助手补的。

1. **一个真实时钟。** 她的世界和用户用同一个时钟、同一本日历。光线本来就跟真实时间走；她说“昨天”，就是真实的昨天。
2. **用户的作息是输入，她的作息由此推出。** 用户的计划变了，她还没发生的安排跟着重排；已经发生的不改（建议）。
3. **判断用户在干什么，越直接的证据越优先（建议）。** 眼前的事实（正在打字、番茄钟在跑、心流中）优先于用户明说的（“今天休息”、确认过的计划），再优先于推断的（课表、周末、节假日）。日历只是兜底：国内有调休，周末不一定休息。比赛那个周末日历上是周末，用户说要干活，就按干活算。
4. **一个身体。** 任何时刻她只在一个地方、只做一件事。干活必须回到桌前，聊天在哪儿都行；手上有活就不出门。她在外面时：
   - 用户交代的活：她马上回房间，这次外出记为提前结束。
   - 邮件这类后台的活：等她回来再处理，急件除外。否则来一封信就打断一次，外出永远走不完。
5. **事实由代码定，措辞交给模型（建议）。** 去哪、几点走、几点回、带回什么，都由确定性代码按种子定下并写库，和番茄钟的计时器不交给模型是同一个道理。模型只写她怎么说、日记怎么写，而且只能引用记录。“周四”“三天前”这类说法，由代码从记录算好再交给她，不让模型自己推算日期。
6. **每段时间只结算一次（建议）。**
   - 程序在运行：出门那一刻就把这次外出定好。
   - 程序没开的那段（关机、整个周末不在）：下次启动时，由代码按同样的规则一次结算并写死，以后不再重算。电脑睡眠后唤醒，和番茄钟一样按存下的时间核对。
   - 离线只结算虚构事件，不结算工作；不能说停机期间干过活。
   - 离开太久，只结算最近几天（建议 3 天），桌子不会一下摆满。
   - **恢复存档不算离线。** 导出到导入之间的空白不补算。库里记一个“已结算到哪一刻”，恢复时直接设成恢复那一刻，再写一条恢复事件，记下存档的导出时间和恢复时间。存档里还在进行的计时，一律在导出那一刻收尾：专注段记为 interrupted，外出记为提前结束（cut_short）。恢复后她在房间里，从恢复那一刻重新开始。她知道中间隔了多久（由代码算好），但不说自己在这段时间做过什么。礼物这类真实的外部任务，照实查它的状态。不这样做，路演“最后一击”时她可能人在海边，或者把一次补算出来的外出当成“刚才发生的事”；展位反复恢复同一份演示存档，每次也会补算出不同的经历。
   - 讨论中原先的说法是“程序关着时不产生新决定，只兑现已经定下的事”。这里改掉它，因为休息日恰恰是用户最可能关机的时候：照原说法，周五关机、周一再开，她整个周末什么都没做。
7. **出门前打招呼（建议）。** 不在用户说话说到一半时走。用户在的时候，她在排计划时提一句想出去走走，这是一条提议（proposal）；用户可以帮她挑衣服，对应第 09 镜，也就是旅行青蛙里的“准备行囊”。用户不在，她就自己走。去哪、什么时候去由她定，用户能提议、能帮她准备。这算是对 README 中“用户对她计划的影响程度”的一个回答。

#### 外出与带回来的东西

- **地点**：每个地点是书里的一页。一开始只有铅笔线稿，她第一次去过才上色（创意脚本 §2.2：她亲身经历过的才有颜色），和新手流程里她给家具上色是同一套逻辑。首版两处：海岸和秋千，背景直接用片子的。
- **左页显示她在的地方**（体验设计 §2）。空房间只有用户主动翻回去才看得到；伞架空着、桌上压着一张纸条，读得出是出门了，不会和第 15 镜的“失去”混在一起。门牌是用户的情境开关，不用来表示她的去向。
- **时长**：真实时间，几十分钟到几个小时，赛中调。
- **带回来的东西**：
  - 每个地点一份目录，每条是一张透明底小图加一句事实描述（比如“秋千那棵树下捡的叶子”）。赛中先画好，运行时按种子抽，不在运行时生图：风格稳、不花钱，也不涉及 §3.10。
  - 出门时就定好带回什么、在第几分钟拿到。提前回来时还没到那一刻，就空手回来。
  - 回来后摆上书桌的固定位置，先是线稿再上色。点开能看到哪天、哪里、哪次外出，并能跳到那天的日记。桌上位置有限，摆满后旧的收进抽屉，点抽屉能翻看全部。
  - 和礼物分开：礼物是给用户的 3D 物件，由用户的真实成果触发（§3.7）；带回来的东西是她自己的 2D 小物，来自她的外出。她在外面见过的东西，可以成为以后礼物的素材。
  - 这是 README 关系候选里“世界泡中的场景、物品或活动出现持续变化”的落地：桌子越摆越满，是一种不用好感度数值的关系反馈。
- **扩展**：更多地点和可带回来的东西由插件提供（§3.13），素材由插件作者自己画、自己花钱。首版官方只带两处地点和一份小目录。
- **预算**：外出本身不调用模型。回来以后她怎么讲，放进下一次正常对话里。离线补算的日子，日记措辞每天最多一次调用，计入自主生活预算（§3.4）。
- **降级（建议）**：不画她在外面，只保留“出门了”的房间和带回来的东西，也就是纯旅行青蛙式，省掉外景页和她在外景里的画面。
- **演示**（2026-10-13 用户定）：不安排她现场出门。演示存档的书桌上有一件她赛中测试外出带回来的东西就够，讲到她自己的生活时点开一次，说出哪天、在哪里带回来。这件东西和礼物一样，列进“预先准备的内容”。外景页做出来，本身就有说服力。
- **用户的作息从哪来**（默认）：首版用对话里说的和确认过的计划，加日历兜底；导入课表（.ics）有余力再做；Student Hub 的教学周课表只作为 MCP 示例（§6）。

### 3.15 隐私模型（滤芯）

2026-10-13 用户提出。设置页除了配置供应商，还按用途选模型（体验设计 §7.2），其中一项是隐私模型。插件在清单里声明“可能处理隐私数据”（§3.13），这类插件拿到的原文先交给隐私模型处理，桃子只看到脱敏、校验过的结果。隐私模型没有任何工具，只跑在用户信得过的地方：本机的小模型，或者学校私有部署的模型。用户的比喻是“一个无情的滤芯”。

它同时做两件事：

- **隐私**：原文不交给云上的主模型服务商，只交给本机或学校的模型。
- **防注入**：读原文的那一层没有工具，邮件里写了什么指令都执行不了。

做法和业界的“双 LLM 模式”（Simon Willison，2023）同源，DeepMind 的 CaMeL（2025）在它上面加了数据流约束。我们的不同在于把它做进插件标准：插件声明一下，加载器就自动接上。提交材料的来源声明里注明。

规则（助手建议，2026-10-13）：

1. **出口要窄。** 隐私模型不写成段的文字，只按固定结构填字段：类别用固定选项，截止时间用 ISO 日期，“要做的事”限 20 字。字段由代码校验，不合格就当工具错误处理（§3.9）。理由：
   - 忠实地摘要一封恶意邮件，摘要里本身就带着那个请求。
   - 专门穿透多层的攻击也有人做过，比如 2024 年的 Morris II，让恶意提示在邮件助手之间自我复制。
   - 小模型更容易听原文里的话。

   出口窄了，输出里很难再夹带指令，“哪一层干活哪一层中招”才真正成立。双 LLM 的原版更严：有工具的那一层连滤芯的输出都不看，只拿变量名。我们让她看窄字段，是在好用和安全之间取中间。
2. **证据原文只给用户看。** 证据句由隐私模型摘出，代码逐字核对它能在原文里找到（§6.1），然后只显示在候选卡上，不进她的上下文。
3. **“可信”说的是数据交给它放心，不是它的输出可信。** 它的输出仍按不可信数据、带来源标签交给她（§3.6）。界面上叫“隐私模型（滤芯）”。
4. **脱敏先用代码。** 手机号、邮箱地址、学号，以及密钥一类的长串（比如 `sk-` 开头的），这些有固定格式的先由代码按规则替换，模型只补剩下的，比如人名。学校邮箱里就有校内模型的 API key（用户 2026-10-13 提到）。
5. **她问细节时再问滤芯。** 她想知道原文的细节，就调用一个工具去问隐私模型，答案同样走窄出口。原文留在本机日志里，“!”按钮照样能看，不经过任何模型。
6. **只适用于“读完再汇报”的插件。** 邮件、附件、校园通知可以。编码和 computer use 必须看到原文才能干活，对它们来说，这个标记只起提醒和授权的作用。
7. **模型大小赛中实测。** 零点几 B 的模型做脱敏、抽简单字段大概够用；摘要长邮件、换算“下周三前”这类相对日期，容易漏，也容易编。编错的会在候选确认时被拦住，漏掉的拦不住。
8. **连不上就停，不退回主模型。** 隐私模型出错或连不上时，这份内容先不处理，她如实说滤芯连不上（工作类工具如实报告，§3.9）。隐私模型的调用不走 §3.9 的备用通道，也不悄悄改交给主模型，否则用户以为过滤了，其实没有。用户可以关掉 `/privacy`，或把下拉框改回跟随主模型，再交给主模型处理。

- **默认**（2026-10-13 用户定）：选“跟随主模型”，就是信任主模型，不隔离、也不过滤，`/privacy` 也打不开。助手曾建议邮件即使跟随主模型也单独隔离抽取一次，用户没有采纳：都跟随主模型了，说明信任它。
- **首版**（2026-10-13 用户定）：只接邮箱插件。邮件正文在配好隐私模型时自动过滤；附件和拖进窗口的文件由 `/privacy` 控制（下一条）。
  - 附件和文件的整理结果不进她的上下文：隐私模型把它整理成文件，代码直接写盘，做成交付卡片交给用户；她只拿到文件名和几个字段（类型、页数、里面的截止时间）。这份成品是成段的文字，但只给人看，不进有工具的那一层，所以不违反第 1 条。
  - 用户之后主动让她读这份文件，内容才会交给主模型。
  - 隐私模型太小时，资料整理的质量会明显下降，设置页上提示一句。
- **`/privacy` 指令**（2026-10-13 用户定）：开着 `/privacy`、且配好了能用的隐私模型时，附件和拖进窗口的文件才走滤芯。不是所有文件都涉及隐私，比如公开的作业要求，这时交给主模型整理得更好。它和心流的指令不同，不只在心流里能用，普通对话里也能用。以下细节是建议：
  - **做成开关**：输一次打开，一直有效，再输一次关掉；重启后保持。附件是专注时在后台读的，只管“下一条消息”的写法管不到它们；开关要是重启后悄悄复位，用户会以为还开着。
  - **看得见**：开着时，输入框旁有一个滤芯标记；她用模板回一句确认，不调用模型。
  - **“能用的隐私模型”**：下拉框里选了具体模型（不是跟随主模型），而且连接测试通过过（§3.9“这套配置成功过没有”）。没有就不打开，告诉用户去设置页配。
  - **只管以后**：只对打开之后读到的文件生效；已经交给主模型的内容收不回来。
  - **不管编码工具**：心流里 `read`、`grep`、`bash` 这些必须看原文（第 6 条），`/privacy` 只管资料处理工具。
  - **存在设置里，不进存档**：恢复一份旧存档，不会把开关悄悄改掉。
- **路演**（2026-10-13 用户定）：展示隐私那一半，隐私模型接学校私有部署的模型。现场能连上，用户平时也用它写代码。地址和密钥由用户提供，存进 `secrets/`；赛前测连通和延迟（§8）。演示前打开 `/privacy`：演示邮件里有附件，附件要是没过滤，调试面板上会看到它发往云端，“原文只交给学校的模型”就站不住了（侧边代理指出）。

### 3.16 她的文件夹：日记、带回来的东西和运行记录

2026-10-13 用户提出，借的是 ARG（替代现实游戏）的做法：故事不只在应用里，也落在用户电脑上真实的文件里。用户的参照是 Neuro-sama 那个至今没完全解开的 ARG。

用户定的部分：

- **她有自己的文件夹。** 她的日记、她做过的礼物、外出带回来的东西、她的运行记录，都放在这里，用户在资源管理器里就能翻。
- **日记每天写，加密。** 真想看也能看：不用复杂的加密，任何一个公开的、凭密钥解开的算法都行。
- **钥匙藏起来，随进度解锁。** 不同篇日记的钥匙藏在重要的地方。片子第 19 镜她递出日记，在产品里就是她把钥匙交给你。

以下是助手的建议：

1. **文件夹照着房间排。** 比如 `桃子的房间/` 下面有 `书桌/`、`日记/`、`带回来的东西/`、`礼物/`、`运行记录/`，默认放在“文档”下，可以改。编码配置里说的“她的书桌”（体验设计 §7.1）就是其中的 `书桌/`，也是她的工具唯一能写的地方；房间里其余的东西只由程序写，不然她跑一条命令，就可能改掉自己的日记和记录。具体怎么拦，并进用户的沙箱方案（§3.6）。
2. **运行记录只写她做了什么，不写原文。** 真正的日志（§3.2）里有邮件原文和工具结果，学校邮件里甚至有 API key。日志留在应用的数据目录里，那里她的工具永远碰不到（体验设计 §7.1）。这个文件夹里只放一份按天的可读记录：几点做了什么、结果怎样，不含正文，脱敏规则同 §3.15 第 4 条。理由有两个：
   - 编码范围选“整台电脑”时，她的工具读得到这个文件夹；原文放在这里，隐私模型就白隔离了。
   - 这个文件夹在“文档”下面，可能被 OneDrive、WPS 这类网盘同步上云。
3. **文件夹是投影，不是本体。** 数据库和日志才是本体。用户删了、改了文件夹里的东西，不影响她的记忆，程序可以重新生成。存档也不用另带这个文件夹，恢复后重新生成。
4. **加密用带密码的 zip。** 每篇日记一个带密码的 zip。Windows 资源管理器双击、输密码就能打开，不用装任何工具。Windows 自带的只支持老式的 ZipCrypto，强度很弱，正合“真想看也能看”；要更正式就用 AES，但得装 7-Zip 才能打开。
5. **钥匙由代码在写日记那一刻定下，存进库里**（同 §3.14 第 5 条）。钥匙是什么、藏在哪、什么时候露出来，都写死。她可以挑一个有意义的词当钥匙，但事后不能改口。
6. **藏在共同经历里，并且比日记晚一步露出来**，免得用户实时读到她当天的心思。候选的地方，每处都能在应用里找到：
   - 她带回来的东西，点开后的描述里藏一个词；
   - 礼物的详情，或预览图的角落；
   - 一起做成的事，比如某张确认过的日程里一个事项的名字；
   - 她在某次休息时随口提起的一句话（由代码提醒她说，钥匙本身仍是事先定好的）。
7. **不会永远锁死。** 钥匙藏的地方没了，比如那件东西收进了抽屉，也要能找回。第 19 镜那一下，她把剩下的钥匙一次交给你。
8. **日记的内容规则不变**：主观、带标记、不作为事实来源，不写模型内部的推理（AGENTS.md）。

**待定**：

- 书签里的日记怎么办。建议显示日期和锁，应用里也能输钥匙解开，给不想翻文件夹的人。
- 每天什么时候写：和“新的一天翻一页”一起定。
- 一篇一把钥匙，还是按阶段几篇一把。
- 第 19 镜那一下什么时候发生：和关系反馈一起定（README“关系与正向激励”）。

### 3.17 调试模式与开发者模式

2026-10-13 用户提出。用户调 AIRI 时没有这样的模式，大模型即使能通过 agent-browser 远程自动调试，也很费劲。赛中主要是助手写代码，助手能不能自己把应用跑起来、看到内部状态、点按钮、快进时间，决定了每个功能调试要花多久。所以它是底座，和日志、harness 一起排在最前面（§9）。

1. **统一的时钟。** 所有代码只从一个时钟模块拿时间和定时器，调试时可以冻结、拨到任意时刻、加速。渲染进程的光线和时段也从主进程的时钟拿。业务代码直接调用 `Date.now`、`new Date()`、`setTimeout`、`setInterval` 的，由 ESLint 拦下（§10）。这也是 §3.14 第 1 条“一个真实时钟”的实现落点。
2. **能被智能体直接驱动。**
   - Electron 带远程调试端口启动，助手用 Playwright 启动应用、点击、输入、截图，在主进程里执行代码。
   - 应用里起一个只在开发者模式下才有的 MCP server（本机 HTTP，带随机令牌）。工具包括：读状态（世界状态、调度队列、当前上下文的投影）、拨时钟、往 inbox 塞事件（新邮件、番茄钟到点、外出回来、翻页）、切换假依赖、载入和导出场景。助手在 Claude Code 里直接调用。
   - 它本身也是一个插件，经插件加载器装入（§3.13），只在开发者模式下加载。
3. **外部依赖都能换成假的。** 模型、邮箱、Rodin、隐私模型、光学记忆都可以替换：模型按脚本回复，包括工具调用；假邮箱里放固定的测试邮件；假 Rodin 隔几秒返回一个样例模型。日志还能当录像带，把一次真实运行里模型的回复原样重放。这样测试结果可重复，离线也能测，不花额度。假依赖只用于开发和测试，不进演示（§10）。
4. **场景存档。** 每个场景就是一份私人存档（§5），用现成的格式，一条命令就能载入，比如“刚装好”“新手流程走完”“第三天：桌上两件东西、一件礼物、两篇日记”“演示开始”。演示用的存档本身就是一个场景。
5. **看得见内部。** 调试面板在按回合回放日志之外，再加：
   - 这一轮模型实际看到的上下文，按 §4.2 的顺序分层显示，缓存的顺序对不对一眼就能看出来；
   - 每轮的 token、花费、首字延迟，以及缓存命中了多少；
   - 调度器里排着的事件和定时器；
   - 记忆检索的打分；
   - 隐私模型的进和出，原文和过滤后的字段并排对照，只在本机显示。

   界面元素带机器能读的状态，比如 `data-pose`、`data-location`、`data-phase`，助手不看截图也能检查画面状态对不对。
6. **安全。**
   - 开发者模式默认关闭，在设置里手动打开（用户定：正式版保留）；展位模式下禁止打开。
   - 远程调试端口和调试用的 MCP 只对本机开放，MCP 带随机令牌。远程调试端口本身没有鉴权，本机任何程序都能借它操纵应用，所以只在开发者模式下开。
   - 任何调试接口都拿不到密钥：密钥只在主进程（§2），调试接口输出时一律打码。
7. **演示时钟**（用户定）：路演可以用加速时钟，或直接调整时间，当场演一次外出回来、凌晨 4 点翻页和做梦。和缩短的番茄钟一样当场说明，列进 README 的标注清单。按 AGENTS.md，它不能当作长期运行或跨天记忆的验证。
8. **工作量**：时钟、假依赖、调试用的 MCP 和远程调试开关约 3–4 小时，排在开赛后 0–6 h；调试面板的扩展约 2–3 小时，和原来的“调试面板最小版”合并。之后每个功能的调试时间都会因此缩短。

### 4.1 上下文压缩

上下文接近模型窗口时，写一条 `context/compact` 事件，记下被压缩的区间和摘要。投影时用摘要替换这个区间，原始事件留在日志里。需要细节时按区间回读原文。所以备份恢复后，被压缩掉的内容也能取回（README「可以带走和恢复共同经历」）。

2026-10-13 记忆系统审计的结论（§4.2 另有几条）：

- **压缩时机由我们定，不看模型窗口**（建议）。一天聊不到 1M token，但跨天会累积。更要紧的是，窗口远没满时，每轮的费用、首字延迟和长上下文下的质量（用户在 AIRI 里见过思维链混进正文）就先出问题了；而且换一个模型，窗口就变。上限的具体数字，等 Opus 4.6 和缓存透传测完再定。一天之内超过上限，先压一次；新的一天翻页时再压，见下一条。
- **新的一天翻一页**（2026-10-13 用户定）：
  - 右页一天一张纸，往回翻能看到前几天的对话。她的墨色褪成铅笔灰，字始终能读：聊天记录是用户的，褪色的只是她那边的视角（建议）。
  - **一天在凌晨 4 点、她睡着时结束**（用户定）。4 点时用户还在，她就陪着，等用户停下一段时间再睡；永远不在聊天或心流的中途翻页（建议）。熄灯时夜里的整理也停，开灯后补做。
  - **一天就是一个会话**（用户同意）：日志按天分文件；升为长期记忆要出现在 2 个会话里，就是 2 天；恢复时取的上次会话的摘要，就是前一天的。
  - **翻页时做的事就是做梦**（用户同意）：把前一天压成日摘要（后台模型）；写前一天的日记（主模型，她的口吻，按 §3.16 加密，钥匙在写时定下）；补抽前一天的记忆；把超过 7 天的日摘要合并成周摘要。光学记忆做出来的话，也在这时处理。一天大约多 3–4 次模型调用，计入自主生活预算。
  - **往回翻时，左页是那天的照片**（用户提出）：在当天某个要紧的时刻给左页拍一张，往回翻时用它代替实时的房间。这正是片子第 16–17 镜“页隧道”的产品对应：一页页往回翻，越早越淡。以下是建议：
    - 拍哪一刻：当天送出了礼物，就拍那一刻；没有就看外出回来，再没有就看第一件真事做完；都没有，就拍她睡前的最后一刻。
    - 存真截图，只截场景层，不截对话框、钟和门牌。不按现在的样子重新渲染：她换了衣服，旧照片也不该跟着变。
    - 越旧越淡：颜色先褪成铅笔灰，再只剩线条，显示时用滤镜做。
    - 照片进私人存档。
- **分层遗忘，文字版是默认**（建议）。今天是原文；最近 7 天各一份日摘要；更早的按周压成一段；再往前，一个月只剩几行。越久越模糊，但原文始终在日志里，按区间能取回：她眼前看到的会褪色，原文一字不丢。书往前翻，越早的页颜色越淡，最后只剩铅笔线稿，对应片子第 15 镜的“静风”（创意脚本 §5）。
- **光学记忆，做成可选插件**（用户提出；首版范围待定，建议有余力；答辩时可作为技术亮点）。参考 DeepSeek-OCR（论文 *DeepSeek-OCR: Contexts Optical Compression*，2025-10）讨论部分的设想：旧的页存成图片，越旧分辨率越低，比如 Large（400 个视觉 token）→ Base（256）→ Small（100）→ Tiny（64）。回忆时由 DeepSeek-OCR 自带的解码器（DeepSeek3B-MoE-A570M）还原成文字，再交给主模型；主模型读到的仍是文字。提交时在来源声明里注明。
  - **价值与评价目标**（2026-10-14 用户明确）：以接近人类的遗忘体验为目标，节省 token 不作为目标。分别观察主线、细节、不确定性、无答案线索帮助回忆和原文回查恢复；光学分辨率档位暂不当作已经校准的记忆年龄。OCR 退化与误读安全筛查是前提，不能代替遗忘体验验证。
  - **解码出来的只算“模糊印象”，不当事实**（建议）。压到 20 倍时，论文里的准确率只剩六成左右，错字会变成编造的记忆。她可以说“记不太清了”；要说具体细节，必须回日志查原文。
  - 给它识别的页用印刷体单独渲染，不用界面上的手写体。
  - 论文的 10×／20× 压缩曲线主要来自 Fox 英文页；论文另有中文 OCR 评估，中文聊天记忆另测。2026-10-14 已完成 [75 次独立 GPU 推理](research/optical-memory-results-20261014.md)：较密页 Large 较好，Base 仍会改错编号，Tiny 出现编造和生成触顶。按年龄自动降档的设想仍需验证；具体事实只回读她当时可见的原文。
  - **遗忘体验试验**（2026-10-14）：[两段共同经历的先导对照](research/optical-memory-forgetting-pilot-20261014.md) 另做 12 次解码与 46 次主模型请求。Small 有主线保留与部分细节未知，也有确定的错误替换；裁去空白改为方页后退化显著减轻。用户略偏好日摘要＋校验残片，措辞后续再调；这份候选未比纯摘要增加可答细节。先校准版式、预处理与退化档位，再决定扩样；稳定主线＋模糊细节仍是待验证建议，不将档位映射成天数。
  - **方页复查**（2026-10-14）：获用户同意另做 [12 次主模型请求](research/optical-memory-square-recall-20261014.md)，不增加 GPU 解码。四档保住纸桥经历与纪念意义，较清晰三档比短摘要多保留日期／时间／颜色，但署名仍确定误读；Tiny 还替换编号和加入付款误读。建议赛前扩样在此收口，默认文字分层保持原设计；人类式遗忘与生产印象守卫仍未验收。
  - **部署**：用户的笔记本是 6 GB 显存的移动版 3060，官方全量 BF16 权重本身已超过其显存，首轮不在本机跑。原计划为 Google Cloud 24 GB 显卡（L4）；2026-10-14 用户找到 CompShare 的 24 GB 3090 候选，实际开通并测试了 24 GB 4090。独立 BF16 解码已跑通，后续再在 Linux 上验证 vLLM 的 OpenAI 兼容接口，设置页里它仍是“记忆解码”槽位，插件只认接口。若先解码成文字再交主模型，64–400 个视觉 token 只属于 OCR 端预算，不能据此宣称主模型同倍数省 token；端到端成本另测。准备与未完成阶段见 [测试清单](research/optical-memory-preflight.md)。
  - 多数用户没有 N 卡，所以只做可选插件，默认走文字分层。

### 4.2 记忆

设计改编自两层来源，只参考设计，不复制代码：

- AIRI 原作者 Neko 的 DevLog（2025-04-14）：重排公式、遗忘曲线、“做梦”式整理和肌肉记忆的想法。
- 用户 AIRI fork 的记忆设计文档（[github.com/3067997259-design/airi](https://github.com/3067997259-design/airi)，`docs/fork/MEMORY-DESIGN.md` 等）。

用户 2026-10-11 说明：这部分设计不是赛中现做的，但是原创，提交时如实注明以上两层来源。

- **抽取**：后台模型从对话中抽取事实与经历，写入 short_term，带日志来源。时机（2026-10-13 改）：用户聊天时后台任务要让路（§3.9），所以不按回合抽，而是闲下来时成批抽，翻页时再补一次（§4.1）。
- **检索打分**（默认权重，实现时调）：

```
score = 1.20 * relevance
      + 0.20 * exp(-Δt_hours * ln2 / half_life_hours)
      + 0.15 * ln(1 + access_count)
```

  - 查询（2026-10-13）：自动检索把最近几句（比如最近 3 轮）一起当查询，不只用最后一句，免得“那个呢？”这类话什么都搜不到。另给她一个搜索记忆的工具，需要时自己写检索词。
  - relevance：查询与记忆文本的汉字两字片段重合度，在 JS 里计算。按首版的数据量（几百到几千条），不需要全文索引。
  - 不用 SQLite FTS5 的 trigram 分词：少于 3 个字的查询词匹配不到任何行，“线代”“作业”这类两字词都会失效。
  - 半衰期：short_term 24 小时，long_term 4320 小时（180 天）。衰减在查询时计算。
- **晋升**：access_count ≥ 3，且出现在至少 2 个不同会话里，就晋升为 long_term。只有晋升写库。首版保留这条规则，但不在路演中演示。
- **纠正**：新事实取代旧事实时，旧条目用 superseded_by 指向新条目，不删除。
- **注入方式**：召回结果作为参考，而不是指令。平铺成列表，带来源和时间，不加标签。
- **上下文的顺序**（2026-10-13）：按变化频率排，不变的在前，每轮都变的在后，缓存才能命中。依次是：规则与工具 → 人设 → “关于你”和提醒规则 → 周摘要与日摘要（一天只变一次）→ 今天的对话 → 每轮都变的部分（召回的记忆、她此刻的状态、用户今天的作息）→ 用户的新消息。心流的冻结前缀（§3.11）是同一个思路。
- **审核**：保留 review_status 字段。来自聊天和邮件的事实标为 unreviewed。首版不做审核队列界面。
- **首版不做**：情绪二维（valence / arousal）、心境一致性、闯入式回忆、肌肉记忆、本地 embedding 模型、审核队列界面。
- **“做梦”**（2026-10-13 改）：翻页那一刻、她睡着时做的整理就是做梦（§4.1）。把经历做成礼物，仍是她整理记忆的另一种方式。
- **常驻内容**（2026-10-13 用户定）：必须每轮都在的个人信息，比如名字、称呼、明说过的偏好，由用户自己写进分层提示词里对应的一块，不另做自动抓取。以下是建议：
  - 这一块叫“关于你”，存在用户档案里，不放进角色卡。角色卡会做成角色包分享出去，写在卡里就会跟着泄露；SillyTavern 把用户人设和角色卡分开，也是这个道理。私人存档里带着它，角色包里没有。
  - 会变的状态不用写：今天的作息、她在哪、在做什么、提醒规则，由代码每轮确定地放进上下文的最后，也不靠检索。
  - 聊天里说的（“以后叫我……”）首版仍只进记忆检索。她可以提一句“要不要写进‘关于你’”，由用户自己去改。
- **引用与回忆**（2026-10-13 用户提出；建议首版做最小版）：用户在旧的一页上选中一句话（谁说的都行），点“引用”。这说明它已经不在今天的上下文里，需要她回忆。豆包那种引用只把那一句装进去，前后都没有；这里交给她自己判断要装多少。以下是建议：
  - 被引用的那句在日志里有确切的位置，所以第一步直接落到那里，一次装进三样：那一句和前后几条原文、那天的日摘要、那一周的周摘要。
  - 不够时，她用一个工具往前或往后多取几条，总量有上限。
  - 从周摘要一层层往下找，留给没有锚点的回忆，比如“上个月那次……”。
  - 回忆时显示“桃子正在回忆……”，用的是工具模板，不额外调用模型；左页短暂换成那天的照片。
  - 回忆只取她当时看到的内容（上下文的投影），不取原始工具结果。不然隐私模型挡住的邮件原文，会从这里漏进她的上下文（§3.15）。
  - 取回的是原文，可以当事实说，这正是“细节回日志查原文”那条路（§4.1）。她自己想，只记得轮廓；用户一提醒，她就能翻回那一页想起来。心理学上这叫提示回忆。
- **恢复后的回忆**：按时间确定性地选取，不靠相似度。取上次会话（也就是前一天）的摘要、最近几条经历、最近一篇日记和最近一件礼物。

## 5. 备份与恢复（路演“最后一击”的硬性要求）

- **私人存档** `.lca-save`：zip 包，内含 SQLite 文件快照、日志目录、artifacts 目录（含礼物模型文件），以及 manifest.json（格式版本、导出时间、角色与用户 id、每个文件的 SHA-256）。不含任何凭据：密钥和 IMAP 授权码不进存档。
- **角色包** `.lca-character`：角色卡、立绘、场景素材和清单。不含聊天、记忆、校园数据，也不含“关于你”（§4.2）。与私人存档分开设计（导入规则见 [体验设计](experience-design.md)）。
- 导出：先用 SQLite 的 backup API 生成一致的快照，再打包。
- 恢复：先校验 manifest 版本和哈希，任一不符就拒绝恢复并说明原因。校验通过后，在恢复前先把当前数据自动备份一份，再替换。
- 存档里只有真实保存过的内容。恢复后的连续性用一条自动化检查验证：恢复前记录的最后一个回合、最后一篇日记、最后一件礼物和书桌上的东西，在恢复后都能查到；导出到恢复之间，没有多出任何补算的外出（§3.14 第 6 条）。
- 界面上，私人存档就是那支羽毛笔：导出时出现，恢复时颜色从笔尖晕开。

演示脚本（路演 §11.1 最后一击）：演示中完成真实工作 → 导出存档 → 清空本地数据 → 收尾视频播放 → 视频结束后导入存档 → 让她说出演示中发生过的事。

### 6.1 内置最小采集（IMAP）

- **只读**：只用 `FETCH`，不移动、不删除、不标记已读（使用 `BODY.PEEK`）。
- **范围**：默认只读一个指定文件夹，可在设置中调整（2026-10-11 用户同意）。每次扫描读最近的未读邮件，最多 30 封（2026-10-13 用户定，取代原来的“只读接入之后收到的邮件”），所以刚接上时也有信可读。
  - “未读”看的是邮箱服务器上的标记。她自己从不标已读（见上一条），所以本地另记处理过哪些，就是下面那条随存档走的读取进度，同一封不会处理两次。
  - 用户在手机或网页上先点开过的信，她不会再看。
  - 演示风险：彩排或测试时，谁在 163 里点开过演示邮件，它就成了已读，演示时她读不到。演示前把演示邮件全部标回未读（路演 §5）。
  - 建议在 163 里设一条规则，把演示发件人的邮件归入“桃子”文件夹。这样投影上不会露出私人邮件；另外，没配隐私模型时，她读过的每封邮件都会发给模型服务商，范围越小越好；配了就只交给隐私模型（§3.15）。
- **读取进度随存档走**（建议，2026-10-11）：读到了哪封邮件，记在 SQLite 里，随私人存档一起导出。恢复演示存档后，同一批演示邮件对她来说又是新的，展位可以反复演示，不用重发邮件。前提是这些邮件在服务器上仍是未读。
- **演示邮箱**：用户的 163 邮箱。开赛后由队友从其他邮箱向它发几封典型的待办事件邮件作为演示数据（演示邮件也算为本作品专门准备的内容）。
- **163 的要求**：
  - 需要在设置里开启 IMAP 并取得客户端授权码，赛前完成。
  - 163 要求客户端先发送 IMAP ID 命令，否则打开文件夹时会报 Unsafe Login。imapflow 应该会自动发送，但未验证，开赛第一小时就测。
- **流程**沿用“证据 → 候选 → 确认 → 安排”：邮件原文是证据；模型提取出候选事项写入 campus_items（状态 candidate），配了隐私模型时由它提取，她只拿到校验过的字段（§3.15）；用户确认后才变成 confirmed 并进入日程。扫描本身不等于用户接受了建议。
- **抽取结果由代码校验**：
  - 她引用的证据原文必须能在邮件中逐字找到。找不到就作为工具错误交回给她重试。
  - “下周三前”这类相对日期，按邮件的发送时间和上海时区（Asia/Shanghai）换算。模型输出 ISO 日期，由代码校验。
- **交付**：一个 .ics 文件，可以直接导入手机日历，评委能当场验证；另附一份 Markdown。天天用时（2026-10-13 用户同意）：
  - 每次只导出新确认的那几项，导过的不再导；每个事项一个固定的 UID，存在 campus_items 里。
  - **改期**：新邮件改了已确认事项的时间，事项记为 changed，出一张变更卡：旧时间、新时间，附两封邮件里的证据原文。用户确认后，导出的那一项沿用同一个 UID，版本号（SEQUENCE）加一，手机日历里是更新，而不是多出一项。各家日历对同一个 UID 重新导入的处理不一样，赛中实测；不行就在变更卡上提醒用户手动删掉旧的那项。
- **急件提醒**（2026-10-13 用户定）：只有邮件内容表明它很急时才弹系统通知，比如截止时间很近。用户也可以提前告诉她哪些邮件要提醒，由她自己维护这份标准。以下细节是建议：
  - **急不急由代码算**：截止时间是否在 24 小时内，由代码按抽取出的 ISO 日期算，不交给模型（同 §3.14 第 5 条）。抽取时另给一个“紧急程度”字段（固定选项），管“考场变更”“今天内回复”这类没有截止时间的情况。
  - **用户教的标准**：她用一个工具把用户的话写成提醒规则（比如“某门课的邮件都提醒我”），存成一张小表，每次整份带上，不靠记忆检索碰运气。信箱的配置面板里能看到、能删。配了隐私模型时，规则交给隐私模型去对原文，它只回答命中了哪一条（窄出口，§3.15）。
  - **通知本身**：只写一句她口吻的模板和截止时间，不写发件人和正文，免得出现在锁屏或投影上。几封一起到时合成一条，一小时内最多弹几次。急件在专注时也弹；熄灯时不读邮件，自然也不弹。
  - **不急的**：不弹通知。画面上信箱口露出一封信，迷你窗里她手边多一张卡片；专注时照旧攒到休息再说。
- **失败语义**：登录失败、网络失败、解析失败分别报告，都不能显示成“没有新邮件”。

## 10. 工程规范与测试

- **单元测试**（vitest）覆盖所有确定性的部分：
  - harness 的步数上限、重复调用检测和取消；
  - 番茄钟计时器在重启和睡眠后的核对；
  - 证据原文校验和相对日期换算；
  - 记忆打分、衰减与晋升；
  - 存档导出后再导入，内容一致，哈希校验能拦住损坏的存档。
- **假模型**：harness 的测试用一个按脚本回复的假模型。它只用于测试，不进演示。调试模式里的其他假依赖（邮箱、Rodin、隐私模型）同理（§3.17）。
- **时间**：业务代码不直接调用 `Date.now`、`new Date()`、`setTimeout`、`setInterval`，一律走统一时钟（§3.17），由 ESLint 拦下。
- **可断言的界面**：界面元素带 `data-*` 状态（姿势、地点、阶段），自动化测试不靠截图比对。
- **场景测试**：用 Playwright 驱动 Electron 跑场景脚本。演示流程也写成一个场景，38–44 h 真人彩排之前先自动跑通。
- **CI**：GitHub Actions 每次 push 运行类型检查、lint 和测试。
- **版本管理**：按功能开分支，通过 PR 合并，两个人的提交记录都能看到。提交信息写清改了什么。提交作品时打一个版本 tag。
- **打包**：开赛后 6 小时内打出第一个安装包；38–44 h 由队友在一台干净的机器上照部署说明从零装一遍，装通才算完成。
- **部署说明**：对应新手流程的必填步骤（名字、模型、她的名字和身份）和设置页里的可选项（邮箱、编码环境等，体验设计 §7）；列出实测过的模型供应商。评委用自己的密钥复现。
